Map کردن داده‌ها به Struct

چکیده: این بخش نگاشت داده به struct در Go را پوشش می‌دهد: rows.Scan، struct tag و reflection. الگوی mapper و library‌های sqlx، sqlc بررسی می‌شود. تفاوت با hydrate در Eloquent مشخص می‌گردد.

بعد از اجرای کوئری‌ها بخش اصلی پردازش نتایج و انتقال داده‌ها به ساختارهایی است که بتوانید به راحتی با آن‌ها کار کنید. پکیج database/sql ابزارهای متنوعی برای خواندن داده‌ها و نگاشت آن‌ها به متغیرها و ساختارها دارد.

به‌عنوان برنامه‌نویس Laravel می‌دانید که Eloquent این کار را به صورت خودکار انجام می‌دهد. در Go نیاز به کنترل و دقت بیشتری دارید اما مزیت آن سرعت و کنترل دقیق بر عملکرد است.

8.4.1 روش اول: Manual Scanning

ساده‌ترین و مستقیم‌ترین روش استفاده از rows.Scan() است:

مزایا: کنترل کامل، بدون وابستگی خارجی، عملکرد بالا. معایب: کد تکراری برای هر کوئری، احتمال خطا در تعداد و ترتیب پارامترها.

از $fillable تا Scan(): در Eloquent نگاشت ستون‌ها به فیلد به‌صورت خودکار با اسم‌گذاری camelCase ⇄ snake_case انجام می‌شود و $casts تبدیل نوع را مدیریت می‌کند. در Go این قرارداد پنهان وجود ندارد — هر فیلد را صراحتاً در Scan() می‌نویسید و ترتیب آرگومان‌ها باید دقیقاً با SELECT مطابقت داشته باشد. این کد تکراری در نگاه اول پرحجم به‌نظر می‌رسد اما یک مزیت بزرگ دارد: اگر ستونی از کوئری حذف یا اضافه شود، کامپایلر بلافاصله خطا می‌دهد نه اینکه در زمان اجرا با مقدار صفر یا NULL تصادفی خود را نشان دهد. برای پروژه‌های متوسط به بالا، sqlc همین امنیت نوع را به‌صورت خودکار با کد کمتر می‌دهد.

در این نمودار می‌بینید که چگونه هر ستون از سطر دیتابیس به فیلد متناظر در struct نگاشت می‌شود. تبدیل نوع‌ها به‌طور خودکار توسط Scan() انجام می‌شود: INT به int، VARCHAR به string و TIMESTAMP به time.Time.

اما نکته‌ی حیاتی این است که اگر ستونی مقدار NULL داشته باشد و فیلد struct از نوع غیراشاره‌ای باشد، Scan() خطا برمی‌گرداند.

به همین دلیل باید یا از انواع sql.NullString و sql.NullInt64 استفاده کنید یا فیلدها را به‌صورت pointer تعریف کنید.

همچنین ترتیب آرگومان‌های Scan() باید دقیقاً با ترتیب ستون‌ها در SELECT مطابقت داشته باشد در غیر این صورت داده‌ها به فیلد اشتباه منتقل می‌شوند.

سناریوهای عملیاتی نگاشت داده‌ها به Struct:

  • نگاشت ستون‌های nullable با sql.NullString: وقتی ستونی در دیتابیس ممکن است NULL باشد، مثلاً ستون email یا phone که اجباری نیست، باید از انواع sql.Null* استفاده کنید. این انواع دو فیلد دارند: Valid که نشان می‌دهد مقدار غیر-NULL است و String یا Int64 که مقدار واقعی را نگه می‌دارند. مزیت این روش صراحت در بیان nullable بودن ستون است اما در JSON serialization رفتار عجیبی دارد و نیاز به custom marshaler دارد.
  • استفاده از struct tag برای نگاشت نام ستون‌ها: در sqlx با اضافه کردن tag مانند `db:"column_name"` می‌توانید نام ستون دیتابیس را به فیلد struct نگاشت کنید بدون اینکه نام فیلد دقیقاً با نام ستون یکی باشد. این ویژگی وقتی ستون‌های دیتابیس از نام‌گذاری snake_case و فیلدهای struct از PascalCase استفاده می‌کنند بسیار مفید است.
  • نگاشت struct های تو در تو در JOIN: وقتی از JOIN استفاده می‌کنید، فیلدهای جدول‌های مختلف را نمی‌توان مستقیماً به struct تودرتو نگاشت کرد. باید فیلدهای زیرین struct تو در تو را جداگانه اسکن کنید مثل &user.Profile.Bio. sqlx با struct tag این محدودیت را تا حدودی حل می‌کند اما sqlc بهترین راه‌حل برای JOIN های پیچیده است.
  • اسکن دسته‌ای چندین سطر: برای خواندن صدها یا هزاران سطر، الگوی slice append در حلقه‌ی rows.Next() کارآمدتر از sqlx.Select() است چون کنترل بیشتری روی حافظه و خطاها دارید. اما sqlx.Select() کد تمیزتری تولید می‌کند و برای کاربردهای معمولی کاملاً مناسب است.
نکته عملی: دو الگوی اصلی برای مدیریت ستون‌های nullable وجود دارد: انواع sql.Null* و الگوی pointer. انواع sql.Null* صراحت بیشتری دارند و به‌خوبی مستند می‌شوند اما در JSON serialization به‌طور پیش‌فرض شیء پیچیده‌ای تولید می‌کنند مثل {"String":"test","Valid":true}. الگوی pointer در JSON به‌درستی null تولید می‌کند اما خطر nil dereference وجود دارد. پیشنهاد عملی: در API ها از pointer استفاده کنید و در لایه‌ی دسترسی داده از sql.Null*، سپس تبدیل را در لایه‌ی میانی انجام دهید.

8.4.4 مدیریت ستون‌های Nullable

همان‌طور که در بخش ۸.۲ دیدید، اگر ستونی nullable باشد و آن را به نوع غیر-pointer اسکن کنید خطا رخ می‌دهد. دو راه‌حل اصلی وجود دارد: انواع sql.Null* (مثل sql.NullString) و الگوی pointer (مثل *string). برای مشاهده‌ی مثال‌های کامل به بخش مدیریت NULL در Scan مراجعه کنید.

8.4.6 رابط sql.Scanner و driver.Valuer

با پیاده‌سازی sql.Scanner و driver.Valuer می‌توانید هر نوع پیچیده‌ای را بدون کد تکراری تبدیل کنید. مثال کامل پیاده‌سازی این رابط‌ها برای ستون‌های JSONB در بخش تبدیل سفارشی با sql.Scanner و driver.Valuer آورده شده است.

مقایسه با Eloquent: در Laravel مدل‌های Eloquent با ORM به‌صورت خودکار ستون‌ها را به فیلدهای مدل نگاشت می‌کنند — حتی JOIN‌ها و روابط با with() بدون کد اضافی کار می‌کنند. در Go شما باید صراحتاً هر فیلد را در Scan() مشخص کنید یا از ابزارهایی چون sqlx و sqlc برای کاهش کد تکراری استفاده کنید. این رویکرد اگرچه نیازمند کد بیشتری است اما شفافیت و کنترل کاملی روی عملیات نگاشت ارائه می‌دهد.
خلاصه‌ی نکات کلیدی:
  • rows.Scan با pointer به فیلدها
  • sqlx با StructScan
  • sqlc برای generate type-safe code
  • struct tag با `db:"column_name"`
  • null handling با sql.Null*
