دیباگ و ریشه‌یابی خطاها

اگر مثل بسیاری از توسعه‌دهندگان PHP رشد کرده باشید، احتمالاً با دستورهای آشنایی مثل var_dump ، print_r یا همان die سال‌ها زندگی کرده‌اید. این دستورات ساده، سریع و همیشه در دسترس بودند. کافی بود جایی از برنامه درست کار نمی‌کرد یک dd() یا die(var_dump($something)) بزنید و بلافاصله می‌فهمیدید چه خبر است. این کار واقعاً هم کار می‌کرد — البته تا حدودی.

در Go به دلیل ماهیت کامپایل‌شده، مدیریت حافظه، همزمانی و runtime متفاوت، دیگر dd() کاربردی ندارد. البته دستوراتی مشابه fmt.Println() و log.Printf() شاید کمی کمک‌حال باشند، اما نمی‌توانند مثل یک دیباگر جزئیات اجرای برنامه را نشان دهند. در این فصل قصد داریم از پایه دیباگ را به شما آموزش دهیم، طوری که هم بتوانید کدهای ساده خود را با دقت دنبال کنید و هم در محیط‌های پیچیده مثل container یا remote بتوانید مشکلات را سریع‌تر پیدا کنید.

دیباگ کردن برخلاف «کد خواندن» یا «حدس زدن» به شما امکان می‌دهد برنامه را در حین اجرا متوقف کنید و بدانید کد کجا متوقف شده، در این وضعیت مقدار متغیرها چیست و مسیر اجرای کد چگونه است. این کار یعنی شناخت دقیق‌تر و رفع سریع‌تر مشکلات. به دلیل کامپایل شدن کد به باینری، دیباگ کردن چالش‌های خاصی دارد، اما ابزارهایی مانند pprof و Delve به کمک ما آمده‌اند تا این فرآیند را کارآمد کنند.

با حدس زدن دیباگ نکنید. مؤثرترین تکنیک دیباگ این است که با دقت مشاهده کنید برنامه واقعاً چه‌کار می‌کند، نه آن‌چه فکر می‌کنید انجام می‌دهد. تشخیص اضافه کنید، فقط کد را تغییر ندهید.

Andy Hunt و Dave Thomas نویسندگان مهندسی نرم‌افزار | The Pragmatic Programmer

نکته‌ی حرفه‌ای: در Go قبل از بهینه‌سازی از pprof استفاده کنید. بیشتر مشکلات عملکردی آن‌جایی نیست که فکر می‌کنید. ابزار go tool pprof پروفایل CPU، پروفایل حافظه و goroutine dump را در اختیارتان می‌گذارد — قبل از تغییر هر کدی از آن‌ها استفاده کنید.

همان‌طور که در جدول بالا مشاهده می‌کنید، هرچند ابزارهای دیباگ در PHP و Go از نظر مفهومی شبیه هستند، اما تفاوت‌های مهمی در نحوه کار و پشتیبانی از قابلیت‌های پیشرفته وجود دارد. به‌ویژه در زمینه دیباگ Concurrency ابزارهای Go قدرتمندتر هستند چون از ابتدا برای این منظور طراحی شده‌اند.

pprof: پروفایلینگ CPU و حافظه

فرض نکنید — ثابت کنید. قبل از بهینه‌سازی، اندازه‌گیری کنید. قبل از رفع، درک کنید. پروفایلر فقط به شما نمی‌گوید چه چیزی کند است — به شما می‌گوید کجا نگاه کنید. در Go ابزار pprof پروفایلینگ CPU، حافظه و مسدودسازی گوروتین را با حداقل سربار به شما می‌دهد.

Andy Hunt و Dave Thomas | The Pragmatic Programmer

از ابزارهای مهم دیباگ عملکردی در Go، pprof است. این ابزار به شما اجازه می‌دهد بفهمید برنامه‌ی شما کجا وقت CPU را صرف می‌کند و کجا حافظه تخصیص می‌دهد. در PHP ابزار مشابهی مانند Blackfire یا Xdebug Profiler وجود دارد، اما pprof به‌صورت پیش‌فرض در اکوسیستم Go ادغام شده و نیازی به نصب جداگانه ندارد. pprof دو حالت کاری دارد: پروفایلینگ CPU که نشان می‌دهد برنامه‌تان وقت خود را کجا صرف می‌کند، و پروفایلینگ حافظه که نشان می‌دهد کجا حافظه تخصیص داده می‌شود و کجا نشت حافظه رخ می‌دهد.

وقتی net/http/pprof را import می‌کنید، چندین endpoint به‌طور خودکار روی DefaultServeMux ثبت می‌شود. هر endpoint اطلاعات خاصی ارائه می‌دهد: /debug/pprof/profile برای CPU، /debug/pprof/heap برای حافظه، /debug/pprof/goroutine برای goroutine‌ها، /debug/pprof/block برای بلاکینگ، و /debug/pprof/mutex برای lock contention. این endpoint‌ها حتی در production هم قابل استفاده هستند، به شرطی که فقط روی localhost گوش دهید.

گردش کار پروفایلینگ CPU با pprof

در نظر بگیرید برنامه‌ای دارید که کند شده و می‌خواهید بفهمید مشکل کجاست. پروفایلینگ CPU اولین قدم است. pprof CPU profile sampling انجام می‌دهد: هر ۱۰ میلی‌ثانیه (به‌صورت پیش‌فرض) stack trace تمام goroutine‌ها را ثبت می‌کند و پس از اتمام دوره، نتایج را تجمیع می‌کند:

در رابط وب pprof چندین نمای مختلف دارید: Top برای لیست توابع، Graph برای نمودار فراخوانی، Flame Graph برای نمودار شعله (بهترین روش برای شناسایی سریع نقاط داغ)، Peek برای مشاهده فراخوانی‌کنندگان یک تابع، و Source برای مشاهده کد خط‌به‌خط. Flame Graph معمولاً سریع‌ترین راه برای پیدا کردن bottleneck است.

نکته عملی: برای مقایسه دو پروفایل (مثلاً قبل و بعد از بهینه‌سازی)، از دستور go tool pprof -base profile1.prof profile2.prof استفاده کنید. این دستور فقط تفاوت بین دو پروفایل را نشان می‌دهد و به شما کمک می‌کند تأثیر تغییرات را اندازه‌گیری کنید.

پروفایلینگ حافظه با pprof (heap و allocs)

پروفایلینگ حافظه در Go دو نوع دارد: heap و allocs. پروفایل heap نشان‌دهنده حافظه تخصیص‌داده‌شده و آزادنشده (در حال استفاده) در زمان پروفایلینگ است، در حالی که allocs مجموع تمام تخصیص‌ها (حتی آزادشده) را نشان می‌دهد. برای شناسایی نشت حافظه، heap مناسب‌تر است و برای شناسایی فشار GC (Garbage Collector)، allocs مفیدتر است.

نکته مهم در تحلیل حافظه این است که pprof به‌صورت پیش‌فرض از inuse_space (حافظه در حال استفاده) استفاده می‌کند. شما می‌توانید با فلگ -inuse_objects تعداد اشیاء، با -alloc_space مجموع تخصیص‌ها و با -alloc_objects تعداد اشیاء تخصیص‌داده‌شده را ببینید. هر معیار برای شناسایی نوع خاصی از مشکل مناسب است: تعداد بالای اشیاء کوچک فشار GC را افزایش می‌دهد، در حالی که حجم بالای حافظه نشت را نشان می‌دهد.

go tool trace: تحلیل اجرا

ابزار go tool trace یکی از ابزارهای اصلی تحلیل همزمانی در Go است. برخلاف pprof که فقط زمان CPU و حافظه را نشان می‌دهد، trace رویدادهای scheduler، GC، goroutine‌ها و network poller را به‌صورت یک timeline بصری نمایش می‌دهد. این ابزار برای شناسایی مشکلاتی مثل goroutine leak، lock contention و GC pause طولانی کارآمد است. اگر با ابزارهای PHP آشنا باشید، نزدیک‌ترین معادل XHProf یا Tideways است، اما trace اطلاعاتی ارائه می‌دهد که در PHP قابل دستیابی نیست چون PHP ذاتاً تک‌نخی است.

وقتی trace را در مرورگر باز می‌کنید، چندین نمای مختلف در دسترس است: View trace (timeline کامل)، Goroutine analysis (تحلیل هر goroutine)، Network blocking profile (توقف‌های شبکه)، و Synchronization blocking profile (توقف‌های همگام‌سازی). نمای View trace بخش اصلی است: در آن می‌توانید هر goroutine، هر OS thread، هر رویداد GC و هر عملیات شبکه را به‌صورت timeline مشاهده کنید. با زوم کردن روی بازه‌های زمانی خاص، می‌توانید ببینید چه اتفاقی افتاده است.

موارد کلیدی که باید در trace جستجو کنید: اول، خطوط GC که نشان‌دهنده وقفه‌های Garbage Collector هستند. اگر خطوط GC بیش از حد مکرر یا طولانی باشند، نشان‌دهنده فشار حافظه است. دوم، goroutine‌هایی که مدت طولانی در وضعیت IO wait یا chan receive هستند، که ممکن است نشانه‌ی نشت goroutine باشد. سوم، بازه‌هایی که تمام thread‌ها فعال هستند اما work distribution نامتوازن است، که نشان‌دهنده lock contention است.

نکته فنی: فایل‌های trace می‌توانند بسیار بزرگ شوند (چند صد مگابایت برای برنامه‌های پرترافیک). برای محیط production، فقط بازه‌های کوتاه (۵-۳۰ ثانیه) را trace کنید. همچنین ابزار go tool trace در Go 1.21+ بهبودهای زیادی داشته و فایل‌های بزرگ را بهتر مدیریت می‌کند.

سناریوهای رایج دیباگ در Go

برنامه‌نویسان Go معمولاً با دسته‌ای از مشکلات تکراری مواجه می‌شوند. در اینجا سناریوهای رایج و راه‌حل‌های آن‌ها را بررسی می‌کنیم:

سناریو ۱: Goroutine Leak

یکی از مشکلات رایج در برنامه‌های Go، نشت goroutine است. وقتی goroutine‌ای شروع می‌شود اما هرگز تمام نمی‌شود (مثلاً چون روی channel‌ای منتظر می‌ماند که هیچ‌گاه مقدار دریافت نمی‌کند)، حافظه‌ی آن هرگز آزاد نمی‌شود. این مشکل در PHP بی‌معنی است چون هر درخواست PHP پس از اتمام، تمام منابع خود را آزاد می‌کند. اما در Go برنامه‌ها طولانی‌مدت هستند و نشت goroutine به‌مرور باعث از کار افتادن سرور می‌شود.

سناریو ۲: Memory Leak

در Go نشت حافظه به معنای حافظه‌ای است که دیگر قابل دسترسی نیست اما GC نمی‌تواند آن را آزاد کند چون هنوز reference به آن وجود دارد. علل اصلی: slice‌های سراسری که مدام رشد می‌کنند، map‌هایی که هرگز پاک نمی‌شوند، و closure‌هایی که به متغیرهای بزرگ ارجاع دارند. برای شناسایی این مشکل، از pprof heap استفاده کنید و حافظه را در دو لحظه مختلف مقایسه نمایید:

سناریو ۳: Slow Request

وقتی یک درخواست خاص کندتر از حد انتظار است، باید بفهمید زمان کجا صرف می‌شود. برای این کار ترکیبی از pprof و trace مؤثر است. ابتدا با pprof CPU profile ببینید کدام توابع بیشترین زمان را مصرف می‌کنند، سپس با trace ببینید آیا goroutine‌ها بلاک شده‌اند یا GC pause طولانی وجود دارد.

سناریو ۴: Data Race

وقتی دو goroutine به‌صورت همزمان به یک متغیر دسترسی دارند و حداقل یکی از آن‌ها نوشتن است، data race رخ می‌دهد. این باگ‌ها خطرناک هستند چون رفتار غیرقطعی دارند و ممکن است فقط در شرایط خاصی ظاهر شوند. Race detector داخلی Go ابزار اصلی شناسایی این مشکلات است:

Runtime دیباگ با GODEBUG

متغیر محیطی GODEBUG یکی از کمتر شناخته‌شده اما از ابزارهای قدرتمند دیباگ Go است. این متغیر به شما اجازه می‌دهد بدون تغییر کد، رفتار runtime را کنترل کنید. مقادیر مختلفی قابل تنظیم است که هر کدام اطلاعاتی درباره بخش خاصی از runtime ارائه می‌دهند:

خروجی schedtrace شامل اطلاعات ارزشمندی است: gomaxprocs تعداد CPU‌های منطقی، idleprocs تعداد CPU‌های بیکار، threads تعداد OS thread‌ها، و runqueue تعداد goroutine‌های در انتظار اجرا. اگر runqueue به‌صورت مداوم بالاست، یعنی برنامه CPU-bound است و نیاز به بهینه‌سازی دارد. خروجی gctrace هم اطلاعاتی درباره مدت زمان GC، حجم حافظه قبل و بعد از GC و تعداد اشیاء ارائه می‌دهد.

نکته عملی: تابع runtime.ReadMemStats باعث stop-the-world می‌شود (تمام goroutine‌ها متوقف می‌شوند). در برنامه‌های حساس به تأخیر، از این تابع با احتیاط استفاده کنید. جایگزین سبک‌تر، runtime.NumGoroutine() است که بدون توقف کار می‌کند و برای مانیتورینگ نشت goroutine مناسب است.

گردش کار دیباگ: از کامپایل تا بازرسی

فرآیند دیباگ در Go برخلاف PHP یک فرآیند چندمرحله‌ای است که از نوشتن کد با باگ شروع شده و با رفع مشکل و کامپایل مجدد پایان می‌یابد. در PHP کافیست صفحه را refresh کنید تا تغییرات منعکس شود، اما در Go باید برنامه را مجدداً کامپایل و اجرا نمایید. این تفاوت بنیادین به معنای آن است که هر چرخه دیباگ در Go زمان‌برتر است و به همین دلیل انتخاب ابزار و روش مناسب اهمیت بسیار بیشتری دارد. درک کامل این گردش کار به شما کمک می‌کند زمان دیباگ را به حداقل برسانید و از ابزار مناسب در هر مرحله استفاده کنید.

همان‌طور که در نمودار بالا مشاهده می‌کنید، فرآیند دیباگ در Go هشت مرحله مشخص دارد که هر کدام ابزار و دستورات خاص خود را نیاز دارند. در PHP با Xdebug فرآیند ساده‌تر است چون extension در همان process اجرا می‌شود و نیازی به کامپایل مجدد ندارید، اما در Go باید هر بار پس از تغییر کد، برنامه را با فلگ‌های دیباگ کامپایل و دیباگر را مجدداً متصل کنید. این تفاوت مهمی است که برنامه‌نویسان مهاجر از PHP باید به آن عادت کنند. خوشبختانه دستور restart در Delve این فرآیند را ساده می‌کند و نیازی به خروج و ورود مجدد به دیباگر نیست.

سناریوهای عملیاتی دیباگ

علاوه بر سناریوهای رایجی که بررسی کردیم، در محیط‌های عملیاتی واقعی با شرایط پیچیده‌تری مواجه می‌شوید که نیاز به ابزارها و رویکردهای تخصصی‌تر دارند. این سناریوها معمولاً در محیط production یا staging رخ می‌دهند و دیباگ آن‌ها چالش‌برانگیزتر است چون دسترسی مستقیم به محیط اجرا محدودتر است و باید با دقت بیشتری عمل کنید تا به عملکرد سیستم اختلالی وارد نشود. در ادامه مهم‌ترین سناریوهای عملیاتی و روش‌های مربوط به آن‌ها را بررسی می‌کنیم:

  • دیباگ Race Condition با فلگ -race: وقتی رفتار برنامه غیرقطعی است و خروجی در اجراهای مختلف تغییر می‌کند، احتمالاً با race condition مواجه هستید. ابزار go test -race و go run -race می‌توانند این مشکلات را شناسایی کنند. race detector با ثبت تمام دسترسی‌های همزمان به حافظه کار می‌کند و در صورت شناسایی دسترسی همزمان بدون همگام‌سازی، گزارش دقیقی شامل stack trace هر دو goroutine درگیر ارائه می‌دهد. توجه کنید که race detector فقط مشکلاتی را شناسایی می‌کند که در زمان اجرای تست واقعاً رخ دهند، بنابراین باید تست‌هایی بنویسید که شرایط race را تولید کنند.
  • دیباگ Deadlock با pprof goroutine: وقتی برنامه کاملاً قفل می‌شود و هیچ goroutine‌ای پیشرفت نمی‌کند، deadlock رخ داده است. runtime خودکار deadlock‌هایی که تمام goroutine‌ها در حالت sleep هستند را شناسایی می‌کند و پیام «all goroutines are asleep - deadlock!» را چاپ می‌کند. اما برای deadlock‌های جزئی که فقط برخی goroutine‌ها درگیر هستند، از go tool pprof http://localhost:6060/debug/pprof/goroutine استفاده کنید تا وضعیت هر goroutine و stack trace آن را ببینید. goroutine‌هایی که در وضعیت [semacquire] یا [chan send] هستند، احتمالاً درگیر deadlock هستند.
  • دیباگ راه‌دور در Container: وقتی برنامه در Docker container اجرا می‌شود و مشکلی فقط در محیط container رخ می‌دهد (نه محلی)، باید از remote debugging استفاده کنید. Delve را در حالت headless داخل container اجرا کنید (dlv exec --headless --listen=:2345 --api-version=2)، پورت ۲۳۴۵ را map کنید (-p 2345:2345)، و از محیط محلی با dlv connect localhost:2345 یا VS Code متصل شوید. حتماً برنامه را با -gcflags="all=-N -l" بسازید و remotePath را در launch.json تنظیم کنید.
  • دیباگ مشکلات Production با Core Dump: وقتی برنامه در production crash می‌کند و امکان دیباگ زنده ندارید، core dump بهترین ابزار تحلیل بعدی است. با ulimit -c unlimited تولید core dump را فعال کنید. پس از crash، فایل core را با dlv core ./myapp core باز کنید تا وضعیت برنامه در لحظه crash را بررسی کنید. همچنین GOTRACEBACK=crash باعث تولید core dump هنگام panic می‌شود.
  • استفاده از strace برای مشکلات سیستم‌عامل: وقتی مشکل مربوط به خود برنامه نیست بلکه از تعامل با سیستم‌عامل نشأت می‌گیرد (مثلاً file descriptor leak، permission denied، یا network timeout)، ابزار strace در Linux می‌تواند تمام system call‌ها و signal‌ها را رهگیری کند. دستور strace -p <PID> -e trace=network,open,close فقط فراخوانی‌های شبکه و فایل را نشان می‌دهد. این ابزار در PHP هم کاربرد دارد اما در Go اهمیت بیشتری دارد چون برنامه‌ها مستقیماً با syscall کار می‌کنند.
نکته کلیدی: همیشه از ساده‌ترین روش دیباگ شروع کنید — fmt.Println یا log.Printf — قبل از اینکه به سراغ دیباگر کامل بروید. اغلب یک log.Printf("value=%v err=%v", val, err) در جای مناسب، مشکل را سریع‌تر از هر دیباگری آشکار می‌کند. دیباگر برای مشکلات پیچیده‌ای مناسب است که با log ساده قابل ریشه‌یابی نیستند. اگر بتوانید مشکل را با یک log ساده حل کنید، وقت بسیار زیادی صرفه‌جویی شده است. فقط یادتان باشد بعد از رفع مشکل، log‌های موقتی را حذف کنید!
