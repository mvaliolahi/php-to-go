gomock

پیش در در مورد mock کردن توضیحاتی داده شد ولی در پروژه‌های واقعی اغلب نیاز داریم در هنگام تست، dependency های خارجی مثل دیتابیس، سرویس‌های دیگر یا APIها را mock کنیم تا side affect ها را کنترل کنیم. یعنی به‌جای اجرای واقعی آن‌ها یک نسخه‌ی شبیه‌سازی‌شده ایجاد می‌کنیم که رفتار مورد انتظار را تقلید می‌کند. این کار:

تست‌ها را سریع‌تر و قابل پیش‌بینی‌تر می‌کند

از وابستگی به منابع بیرونی مثل پایگاه‌داده یا سرویس های شخص ثالث جلوگیری می‌کند

امکان تست سناریوهای خطا و edge caseها را فراهم می‌کند

در دنیای Go ابزار استاندارد و قدرتمند برای ایجاد mockها پکیج از تیم گوگل است.

چیزی که مالک آن نیستید را mock نکنید. فقط interfaceهایی که کنترل آن‌ها در دست شماست را mock کنید، نه کتابخانه‌های خارجی را. اگر نیاز دارید یک کتابخانه شخص ثالث را mock کنید، ابتدا آن را درون interfaceای که خودتان مالکش هستید بپیچید.

Andy Hunt و Dave Thomas نویسندگان مهندسی نرم‌افزار | The Pragmatic Programmer

نکته‌ی حرفه‌ای: در Go بهترین mockها interfaceهای حداقلی هستند که توسط مصرف‌کننده تعریف شده‌اند. به‌جای ساخت یک interface بزرگ که کل API خارجی را بازتاب می‌دهد، یک interface کوچک با فقط متدهایی که کدتان واقعاً فراخوانی می‌کند تعریف کنید.

ابزار رسمی پایدار و قابل اطمینان برای پروژه‌های حرفه‌ای

مقایسه با PHP: در PHP معمولاً از PHPUnit Mock یا Mockery برای شبیه‌سازی وابستگی‌ها استفاده می‌شود. در PHPUnit با $this->createMock(Repository::class) یک Mock می‌سازید و با $mock->method('find')->willReturn($user) رفتار آن را تعریف می‌کنید. در Go اما mock به‌صورت خودکار از interface تولید می‌شود و type-safety کامل دارد. یعنی اگر interface تغییر کند، mock هم باید دوباره تولید شود و کامپایلر خطا را نشان می‌دهد.
نکته درباره بهترین روش‌های gomock: ۱) از نسخه go.uber.org/mock استفاده کنید (فورک رسمی گوگل که اکنون در Uber نگهداری می‌شود)؛ پکیج قدیمی github.com/golang/mock دیگر فعال نیست. ۲) برای پایداری بازتولید mock، از //go:generate mockgen ... در همان فایلی که interface تعریف شده استفاده کنید و دستور go generate ./... را در Makefile قرار دهید. ۳) فایل‌های تولیدشده mock را در git commit کنید تا CI نیازی به mockgen نداشته باشد. ۴) از Go 1.20+ دیگر نیازی به defer ctrl.Finish() نیست چون t.Cleanup خودکار است. ۵) هرگز interfaceهایی که مالک آن‌ها نیستید (مثل http.ResponseWriter) را مستقیماً mock نکنید — آنها را در interface بومی خودتان بپیچید.

چه زمان Mock و چه زمان Fake؟

از تصمیمات کلیدی در تست‌نویسی، انتخاب بین Mock و Fake است. هر دو روش برای ایزوله کردن تست‌ها از وابستگی‌های خارجی استفاده می‌شوند، اما رویکرد و فلسفه متفاوتی دارند. درک تفاوت این دو به شما کمک می‌کند تست‌های بهتری بنویسید.

Mock یک شیء است که رفتار آن را به‌صورت دقیق و از قبل تعریف می‌کنید. هر فراخوانی متد و مقدار بازگشتی آن باید صریحاً مشخص شود. اگر فراخوانی‌ای انجام شود که تعریف نشده، تست شکست می‌خورد. Mockها برای behavior testing مناسب هستند — یعنی بررسی اینکه آیا کد شما متدهای درست را با پارامترهای درست فراخوانی کرده یا نه.

Fake یک پیاده‌سازی واقعی اما ساده‌شده از interface است که واقعاً کار می‌کند. مثلاً یک InMemoryUserRepository که به‌جای دیتابیس واقعی، از یک map در حافظه استفاده می‌کند. Fakestate testing مناسب هستند — یعنی بررسی اینکه آیا نتیجه نهایی درست است یا نه.

توصیه عملی: از Mock برای وابستگی‌هایی استفاده کنید که کنترلی روی آن‌ها ندارید (مثل API خارجی، سرویس Payment، سرویس ایمیل). از Fake برای وابستگی‌هایی استفاده کنید که پیاده‌سازی ساده‌ای دارند (مثل Repository، Cache، Queue). Fakeها تست‌های شما را مقاوم‌تر در برابر refactor می‌کنند و خوانایی بهتری دارند.

الگوهای مشکل Mock در Go

یکی از چالش‌های رایج در Go این است که برخی توابع جزو interface نیستند و نمی‌توان آن‌ها را مستقیماً mock کرد. مثلاً time.Now() یا http.Get() یا توابع پکیج os. برای حل این مشکل، الگوی استاندارد این است که آن توابع را پشت یک interface قرار دهید:

نکته: Dependency Injection via Interface از الگوهای مهم Go برای تست‌پذیری است. در PHP با فریمورک‌هایی مثل Laravel این مشکل کمتر احساس می‌شود چون Container و Facadeها امکان جایگزینی ساده‌تر را فراهم می‌کنند. اما در Go باید صریحاً interface تعریف و تزریق کنید.

خط لوله تولید و تزریق Mock

یکی از مهم‌ترین مفاهیم در کار با gomock درک خط لوله کامل تولید و تزریق mock است. این خط لوله از تعریف interface شروع می‌شود، با ابزار mockgen فایل mock تولید می‌شود، و در نهایت mock در تست استفاده می‌شود. هر مرحله از این خط لوله نقش حیاتی دارد: اگر interface بیش از حد بزرگ باشد، mock کردن سخت می‌شود. اگر mock به‌درستی تولید نشود، رفتار تست اشتباه خواهد بود. و اگر تزریق mock به‌درستی انجام نشود، کد واقعی به‌جای mock اجرا می‌شود.

در PHP با PHPUnit این خط لوله ساده‌تر است: با $this->createMock() یک mock می‌سازید و با $mock->method()->willReturn() رفتار آن را تعریف می‌کنید. اما در Go این فرآیند ساختاریافته‌تر و type-safe است. تولید خودکار mock از interface تضمین می‌کند که اگر interface تغییر کند، mock باید دوباره تولید شود و کامپایلر خطا را نشان می‌دهد. این مکانیزم ایمنی بزرگی است که در PHPUnit وجود ندارد.

سناریوهای عملیاتی gomock

در پروژه‌های واقعی، کار با mock فراتر از مثال‌های ساده است. هر سناریو عملیاتی زیر یک چالش رایج در تست‌نویسی را پوشش می‌دهد که توسعه‌دهندگان مهاجر از PHP احتمالاً با آن مواجه خواهند شد. این الگوها به شما کمک می‌کنند تست‌های قابل اعتماد و قابل نگهداری بنویسید که در برابر تغییرات کد مقاوم هستند و رفتار واقعی سیستم را به‌درستی تأیید می‌کنند.

  • Mock کردن Repository دیتابیس برای تست سرویس: وقتی سرویسی دارید که به Repository وابسته است، نیازی به دیتابیس واقعی در تست سرویس نیست. با mock کردن Repository می‌توانید رفتار سرویس را در حالت‌های مختلف (موفقیت، خطا، خالی بودن نتیجه) تست کنید. این الگو مشابه mock کردن Eloquent Model در Laravel است اما در Go با type-safety کامل انجام می‌شود.
  • Mock کردن HTTP Client برای تست API: وقتی کد شما با API خارجی ارتباط برقرار می‌کند، نباید در تست واقعاً درخواست HTTP ارسال کنید. با تعریف interface HTTPClient و mock کردن آن، می‌توانید پاسخ‌های مختلف (موفق، خطای شبکه، timeout) را شبیه‌سازی کنید. این کار تست‌ها را سریع، قابل تکرار و مستقل از سرویس‌های خارجی می‌کند.
  • Mock کردن زمان برای تست‌های قطعی: توابعی که از time.Now() استفاده می‌کنند در تست‌ها غیرقطعی هستند. با تعریف interface Clock و mock کردن آن، می‌توانید زمان ثابت را تزریق کنید و نتایج تست را قابل پیش‌بینی کنید. این الگو در PHP با Carbon::setTestNow() قابل انجام است اما در Go باید صریحاً interface تعریف شود.
  • تست مسیرهای خطا با شکست mock: یکی از مهم‌ترین کاربردهای mock، تست رفتار کد در زمان خطای وابستگی است. با EXPECT().Return(nil, errors.New("connection lost")) می‌توانید سناریوهای خطا را شبیه‌سازی کنید و مطمئن شوید کد شما به‌درستی خطاها را مدیریت می‌کند. در PHPUnit این کار با $mock->method()->willThrowException() انجام می‌شود.
  • تأیید ترتیب و تعداد فراخوانی: گاهی نه تنها نتیجه mock مهم است، بلکه ترتیب و تعداد فراخوانی‌ها هم اهمیت دارد. با gomock.InOrder() می‌توانید ترتیب فراخوانی‌ها و با EXPECT().Times(n) تعداد دقیق فراخوانی‌ها را تأیید کنید. این قابلیت در PHPUnit با expects($this->exactly(n)) قابل انجام است.
نکته درباره اندازه Interface و Mock: اگر mock شما بیش از ۲۰ EXPECT دارد، Interface شما خیلی بزرگ است! این بوی ضعیف (Code Smell) نشان‌دهنده نقض اصل تفکیک interface (Interface Segregation Principle) است. Interface بزرگ را به چند interface کوچک‌تر بشکنید. هر interface باید فقط متدهایی داشته باشد که مصرف‌کننده واقعی آن نیاز دارد. این کار نه تنها mock کردن را آسان‌تر می‌کند، بلکه طراحی کلی سیستم را هم بهبود می‌بخشد.
