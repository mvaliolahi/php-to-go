OpenTelemetry

OpenTelemetry یک پروژه متن‌باز تحت نظر بنیاد CNCF است که ابزارها و استانداردهایی را برای جمع‌آوری پردازش و ارسال داده‌های Observability ارائه می‌دهد. این پروژه سه نوع داده اصلی را مدیریت می‌کند:

Metrics : داده‌های عددی که وضعیت سیستم را نشان می‌دهند (Counter ، Histogram ، Gauge).

Traces : ردیابی مسیر یک درخواست در سیستم از لحظه ورود تا خروج.

Logs : گزارش‌های متنی که وقایع مهم یا خطاها را ثبت می‌کنند.

مزیت بزرگ OpenTelemetry یکپارچگی و استانداردسازی است. دیگر نیازی نیست برای هر نوع داده ابزار جداگانه‌ای یاد بگیرید. برای برنامه‌نویس PHP این ابزار مانند نسخه‌ی پیشرفته‌تر و مقیاس‌پذیرتر از Monolog یا New Relic است اما با انعطاف‌پذیری بیشتر و پشتیبانی از سیستم‌های توزیع‌شده.

نمی‌توانید چیزی را تعمیر کنید که نمی‌بینید. کدتان را ابزارسازی کنید تا وقتی در محیط تولید مشکلی پیش می‌آید، دقیقاً ببینید چه اتفاقی افتاده، کِی و کجا افتاده.

نکته‌ی حرفه‌ای: همان‌طور که در آغاز فصل دیدیم، سه رکن Observability اهداف متفاوتی دارند. OpenTelemetry هر سه را با یک API ابزارسازی واحد در اختیارتان می‌گذارد تا به‌جای یادگیری سه ابزار مجزا، یک مدل یکپارچه برای Logs، Metrics و Traces داشته باشید.

اجزای اصلی OpenTelemetry

مطالعه موردی Tracing توزیع‌شده در Courier

Courier از OpenTelemetry برای ردیابی مسیر هر پیام از دریافت تا تحویل استفاده می‌کند. هر پیام از چندین مایکروسرویس عبور می‌کند: صف پیام، پردازشگر، ارائه‌دهنده (ایمیل/SMS/Push)، و ثبت نتیجه. بدون Tracing توزیع‌شده، عیب‌یابی تأخیر یا شکست تحویل غیرممکن بود چون هر مایکروسرویس فقط بخشی از تصویر را می‌دید و هیچ راهی برای پیوند دادن لاگ‌های سرویس‌های مختلف وجود نداشت. وقتی یک پیام تحویل داده نمی‌شد، تیم باید لاگ‌های هر سرویس را جداگانه بررسی می‌کرد و سعی می‌کرد با تطبیق زمان‌بندی‌ها مسیر پیام را بازسازی کند — فرآیندی که ساعت‌ها طول می‌کشید.

با OpenTelemetry، تیم Courier می‌تواند یک trace ID را از هر نقطه گرفت و کل مسیر پیام را با زمان‌بندی دقیق هر مرحله مشاهده کند. هر span شامل اطلاعات غنی‌ای است: نام سرویس، عملیات انجام‌شده، زمان شروع و پایان، و هر خطا یا هشداری که رخ داده. این قابلیت زمان عیب‌یابی را از ساعت‌ها به دقیقه‌ها کاهش داد. علاوه بر این، تیم می‌تواند bottleneck‌ها را شناسایی کند — مثلاً اگر پردازشگر پیام بیش از حد طول می‌کشد، می‌توان دقیقاً دید که کدام بخش از پردازش زمان‌بر است و آن را بهینه‌سازی کرد.

انتشار Context ترس بین سرویس‌ها

یکی از ویژگی‌های کلیدی OpenTelemetry انتشار خودکار Trace Context بین سرویس‌هاست. وقتی سرویس A درخواستی به سرویس B ارسال می‌کند Trace ID و Span ID به‌صورت خودکار در HTTP headers (طبق استاندارد W3C Trace Context) منتقل می‌شوند:

اهمیت انتشار Context: بدون انتشار Trace Context هر سرویس Trace مستقلی ایجاد می‌کند و نمی‌توانید مسیر کامل یک درخواست را در سیستم توزیع‌شده ردیابی کنید. این یکی از تفاوت‌های کلیدی OpenTelemetry با ابزارهای سنتی PHP است که در آن هر درخواست یک فرآیند مجزا است و Context بین سرویس‌ها به‌طور طبیعی منتقل نمی‌شود.
نکته پیکربندی Propagator: قبل از ساخت اولین Span، حتماً W3C Trace Context را به‌عنوان propagator سراسری تنظیم کنید: otel.SetTextMapPropagator(propagation.TraceContext{}) و در سمت گیرنده نیز propagation.Baggage{} را برای انتقال baggageها اضافه کنید. این کار را در init() انجام دهید؛ اگر بعد از اولین درخواست انجام شود، Span‌های قبلی بدون parent می‌مانند. ساده‌ترین راه برای فریم‌ورک‌های وب، استفاده از otelhttp.NewHandler است که انتشار را به‌صورت خودکار انجام می‌دهد (به بخش Auto-Instrumentation در ادامه مراجعه کنید).

معماری داخلی SDK

TracerProvider : نقطه ورودی اصلی SDK. SpanProcessor : پردازشگر Span ها (BatchSpanProcessor برای production ، SimpleSpanProcessor برای development). Sampler : تصمیم می‌گیرد کدام Span ها ثبت شوند.

نکته عملی: همیشه tp.Shutdown(ctx) را با defer فراخوانی کنید تا Span های باقیمانده در بافر قبل از خروج برنامه به Exporter ارسال شوند.

ملاحظات عملکرد در Production

اضافه کردن OpenTelemetry به برنامه overhead ایجاد می‌کند. با رعایت نکات زیر می‌توانید این overhead را به کمتر از ۲ درصد کاهش دهید:

استفاده از BatchSpanProcessor: هرگز در production از SimpleSpanProcessor استفاده نکنید. Batch پردازشی Span ها را در دسته‌ها جمع‌آوری و ارسال می‌کند.

تنظیم Sampling: در سیستم‌های پرترافیک ثبت تمام Span ها غیرعملی است. از TraceIDRatioBased با نسبت مناسب استفاده کنید.

انتخاب Exporter: ارسال مستقیم به Tempo یا Jaeger ساده‌تر است اما OTel Collector امکان retry ، buffering و routing را فراهم می‌کند.

کاهش Attributes: هر Attribute حافظه و پهنای باند مصرف می‌کند. فقط Attributes ضروری را ثبت کنید.

هشدار عملکرد: اگر Sampling تنظیم نکنید و SimpleSpanProcessor استفاده کنید در سیستم‌های پرترافیک overhead می‌تواند به ۱۰-۲۰ درصد برسد. حتماً BatchSpanProcessor و Sampling مناسب تنظیم کنید.

درخت Span و انتشار Context

درک ساختار درختی Span‌ها و context propagation برای عیب‌یابی مؤثر در سیستم‌های توزیع‌شده حیاتی است. هر trace یک درخت از Span‌هاست که ریشه آن root span (معمولاً درخواست ورودی HTTP) و شاخه‌های آن عملیات فرعی در سرویس‌های مختلف هستند. هر Span شامل شناسه یکتای خود (span ID)، شناسه والد (parent span ID) و شناسه کل trace (trace ID) است. انتشار Context از طریق هدرهای HTTP (مثل traceparent و tracestate) طبق استاندارد W3C Trace Context انجام می‌شود و تضمین می‌کند که تمام سرویس‌های درگیر در یک درخواست، بخشی از همان trace باشند. بدون این انتشار خودکار، هر سرویس trace مستقلی ایجاد می‌کند و ردیابی مسیر کامل درخواست غیرممکن می‌شود.

در نمودار بالا ریشه درخت Span درخواست HTTP GET /api/order در سرویس gateway است. این root span چهار child span دارد که هر کدام در یک سرویس متفاوت اجرا می‌شوند. خطوط نقطه‌چین نارنجی مرزهای سرویسی را نشان می‌دهند — هر بار که درخواست از یک سرویس به سرویس دیگر عبور می‌کند، trace context از طریق هدرهای HTTP (traceparent و tracestate) منتقل می‌شود. این انتشار تضمین می‌کند که تمام Span‌ها دارای یک trace ID یکسان هستند و در Grafana Tempo به‌صورت یک trace واحد نمایش داده می‌شوند. بدون این مکانیزم هر سرویس trace مستقلی ایجاد می‌کرد و ردیابی مسیر کامل درخواست از gateway تا user service غیرممکن بود. بخش پایینی نمودار سه رکن observability و نقش هر یک را نشان می‌دهد: tracing برای مسیریابی بین سرویس‌ها، metrics برای اعداد تجمیعی و logging برای جزئیات رویدادها.

سناریوهای عملیاتی

  • شناسایی سرویس کند در زنجیره درخواست: وقتی کاربران از کندی پاسخ‌دهی شکایت دارند، trace به شما نشان می‌دهد کدام سرویس در زنجیره بیشترین زمان را مصرف کرده. مثلاً اگر api.GetUserInfo در نمودار بالا ۱۸۰ میلی‌ثانیه طول بکشد در حالی که سایر سرویس‌ها زیر ۱۰۰ میلی‌ثانیه هستند، مشکل در user service است. با اضافه‌کردن span‌های دقیق‌تر (مثل db.Query و cache.Lookup) می‌توانید دقیقاً ببینید کدام عملیات درون سرویس کند است.
  • کشف الگوی N+1 query در trace‌ها: اگر در یک trace ده‌ها span تکراری با نام db.Query ببینید، احتمالاً با مشکل N+1 مواجه هستید. یعنی به‌جای یک کوئری JOIN، برای هر آیتم یک کوئری جداگانه اجرا می‌شود. این الگو با بررسی trace در Grafana به‌سرعت قابل تشخیص است و معمولاً با eager loading یا batch query حل می‌شود.
  • افزودن span سفارشی برای منطق کسب‌وکار: علاوه بر auto-instrumentation، باید span دستی برای عملیات کسب‌وکار مهم اضافه کنید. مثلاً tracer.Start(ctx, "calculate_pricing") یا tracer.Start(ctx, "validate_inventory"). این span‌ها به شما نشان می‌دهند کدام بخش از منطق کسب‌وکار زمان‌بر است و آیا نیاز به بهینه‌سازی دارد.
  • Sampling: در سیستم‌های پرترافیک ثبت تمام trace‌ها غیرعملی است. head-based sampling در ابتدای درخواست تصمیم می‌گیرد آیا این trace ثبت شود یا خیر — مزیت آن سادگی است اما ممکن است trace‌های خطادار را از دست بدهید. tail-based sampling پس از پایان درخواست تصمیم می‌گیرد و می‌تواند تمام trace‌های خطادار یا کند را ثبت کند — اما به زیرساخت پیچیده‌تری نیاز دارد.
  • همبستگی trace با لاگ و متریک: برای عیب‌یابی کامل باید بتوانید از trace به لاگ و متریک پرش کنید. با افزودن trace_id به هر رکورد لاگ و trace_id به exemplar‌های متریک، در Grafana می‌توانید از نمودار متریک مستقیماً به trace مربوطه و سپس به لاگ‌های همان درخواست بروید. این همبستگی سه‌جانبه کلید observability واقعی است.
همبسته‌سازی سه رکن با trace_id: کلید observability واقعی، توانایی پرش از یک رکن به دیگری است: از نمودار Metrics به Trace مربوطه، و از آن به Logs همان درخواست. این همبستگی سه‌جانبه با افزودن trace_id به هر رکورد لاگ و trace_id به exemplar‌های متریک در Grafana ممکن می‌شود. توضیح کامل سه رکن و نقش هر یک را در آغاز این فصل (بخش ۹.۰۰) بخوانید.
