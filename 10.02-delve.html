Delve

چکیده: این بخش Delve debugger را پوشش می‌دهد: breakpoint، step و variable inspection. الگوی dlv cli و IDE integration بررسی می‌شود. کاربردهای production debug پوشش داده می‌گردد.

Delve یک دیباگر منبع‌باز است که به‌صورت تخصصی برای Go طراحی شده است.

برخلاف دیباگرهای عمومی مانند GDB که برای زبان‌های C/C++ ساخته شده‌اند، Delve از قابلیت‌های runtime Go و اطلاعات نمادهای کامپایل‌شده استفاده می‌کند تا به شما امکان اجرای دقیق، توقف، بررسی وضعیت متغیرها و تحلیل مسیر اجرای برنامه را بدهد.

مزیت اصلی Delve نسبت به GDB این است که ساختارهای داخلی Go مانند goroutine‌ها، channel‌ها، interface‌ها و slice‌ها را به‌درستی پشتیبانی می‌کند، در حالی که GDB نمی‌تواند حتی goroutine‌ها را نمایش دهد.

برای برنامه‌نویسانی که از PHP می‌آیند، Delve معادل Xdebug است اما با تفاوت‌های مهم: Xdebug یک extension بومی PHP است که در همان process اجرا می‌شود، اما Delve یک process جداگانه است که از طریق سیستم‌عامل (ptrace در Linux/Mac) به باینری Go متصل می‌شود.

این رویکرد مزیت مهمی دارد: Delve هیچ overhead در production ندارد چون فقط زمان دیباگ فعال است، در حالی که Xdebug حتی وقتی استفاده نمی‌شود ۲۰-۴۰٪ عملکرد را کاهش می‌دهد.

10.2.1 نصب Delve

پس از نصب، دستور dlv version را اجرا کنید تا از نصب صحیح مطمئن شوید. برای نصب روی لینوکس یا مک ممکن است نیاز به دسترسی‌های خاص یا تنظیمات امنیتی مثل Seccomp در لینوکس داشته باشید. مستندات رسمی Delve راهنمای خوبی برای رفع مشکلات احتمالی است.

همچنین در macOS ممکن است نیاز باشد Developer Tools را نصب کنید و اجازه‌ی debug را به terminal بدهید.

10.2.4 دیباگ goroutine‌ها و channel‌ها

از مزیت‌های اصلی Delve نسبت به GDB، پشتیبانی بومی از goroutine‌هاست. در برنامه‌های Go که صدها یا هزاران goroutine فعال دارند، پیدا کردن اینکه کدام goroutine مشکل‌ساز است می‌تواند چالش‌برانگیز باشد. Delve ابزارهای مفیدی برای این کار ارائه می‌دهد:

وضعیت‌های مختلف goroutine‌ها اطلاعات مهمی درباره مشکل ارائه می‌دهند: [running] یعنی در حال اجرا، [chan receive] یعنی منتظر دریافت از channel، [chan send] یعنی منتظر ارسال به channel، [IO wait] یعنی منتظر عملیات ورودی/خروجی، [select] یعنی در دستور select منتظر، و [semacquire] یعنی mutex.

اگر تعداد زیادی goroutine در وضعیت [chan receive] یا [semacquire] هستند، احتمالاً مشکل deadlock یا goroutine leak دارید.

10.2.6 آشنایی با Stack Trace و Panic

وقتی برنامه با شرایط بحرانی مواجه می‌شود که نمی‌تواند ادامه دهد (مثلاً دسترسی به اشاره‌گر nil یا ارجاع به آرایه خارج از محدوده)، دستور panic فراخوانی می‌شود که باعث توقف ناگهانی برنامه می‌شود و یک stack trace تولید می‌کند.

Stack trace در واقع نقشه‌ای از مسیر خطاست و به شما نشان می‌دهد که برنامه در هنگام بروز خطا کدام توابع را فراخوانی کرده و مسیر اجرای کد کجا بوده است.

می‌توانید Delve را طوری تنظیم کنید که تا زمانی که برنامه panic می‌کند متوقف شود و سپس وضعیت کامل برنامه را بررسی کنید:

این روش دقیق‌تر از صرفاً خواندن خروجی panic است چون امکان بررسی وضعیت کامل برنامه را در لحظه خطا می‌دهد. می‌توانید مقادیر تمام متغیرها، وضعیت سایر goroutine‌ها و محتوای channel‌ها را در همان لحظه‌ای که panic رخ داده بررسی کنید.

10.2.7 دیباگ Docker و Remote Debugging

در محیط‌های مدرن، برنامه‌ها اغلب در container‌ها یا سرورهای راه‌دور اجرا می‌شوند. Docker محیطی ایزوله است و دسترسی مستقیم به محیط اجرا محدود است. همچنین منابع شبکه باید به درستی پورت‌ها را باز کنند تا ابزار دیباگ بتواند به آن متصل شود. Delve دو رویکرد اصلی برای دیباگ راه‌دور ارائه می‌دهد:

10.2.8 داخلی Delve: DWARF و پروتکل دیباگ

فهم نحوه کار داخلی Delve به شما کمک می‌کند مشکلات دیباگ را بهتر ریشه‌یابی کنید. وقتی dlv debug را اجرا می‌کنید، Delve مراحل زیر را طی می‌کند:

۱. کامپایل با اطلاعات دیباگ: Delve برنامه را با فلگ -gcflags="all=-N -l" کامپایل می‌کند. فلگ -N optimization را غیرفعال می‌کند و -l inlining توابع را غیرفعال می‌کند. بدون این فلگ‌ها، کامپایلر ممکن است متغیرها را حذف کند یا توابع را ترکیب کند که دیباگ را ناممکن یا بسیار سخت می‌سازد.

۲. خواندن اطلاعات DWARF: باینری Go حاوی اطلاعات DWARF (Debugging With Attributed Record Formats) است. این اطلاعات شامل نگاشت بین آدرس‌های ماشین و خطوط کد منبع، نام و نوع متغیرها، و ساختار Stack Frame است. Delve از این اطلاعات برای نمایش متغیرها و خطوط کد به‌جای آدرس‌های حافظه استفاده می‌کند.

۳. کنترل اجرا با ptrace: در Linux و macOS، Delve از syscall ptrace برای کنترل اجرای برنامه استفاده می‌کند. ptrace به Delve اجازه می‌دهد برنامه را متوقف کند، ادامه دهد، breakpoint‌ها را تنظیم کند و حافظه‌ی process را بخواند. در Windows از API مشابه DebugActiveProcess استفاده می‌شود.

۴. پروتکل دیباگ: Delve از پروتکل DAP (Debug Adapter Protocol) استفاده می‌کند که توسط Microsoft تعریف شده و توسط VS Code و بسیاری IDE‌های دیگر پشتیبانی می‌شود. این پروتکل به IDE امکان ارسال دستورات دیباگ (break, step, continue) و دریافت اطلاعات (متغیرها، stack, goroutine‌ها) را می‌دهد.

نکته فنی: برخلاف GDB که یک دیباگر عمومی است و زبان‌های مختلف را پشتیبانی می‌کند، Delve مخصوص Go طراحی شده و از ساختارهای داخلی Go مانند goroutine‌ها، channel‌ها، interface‌ها و slice‌ها به‌درستی پشتیبانی می‌کند. GDB نمی‌تواند goroutine‌ها را نمایش دهد یا مقادیر interface را به‌درستی تفسیر کند.
نکته: اگر باینری را با go build دستی می‌سازید و سپس با dlv exec یا dlv attach دیباگ می‌کنید، حتماً فلگ -gcflags="all=-N -l" را اضافه کنید. dlv debug این فلگ‌ها را خودکار اضافه می‌کند، اما dlv exec برنامۀ از پیش ساخته‌شده را اجرا می‌کند و کنترلی روی فلگ‌های کامپایل ندارد. بدون این فلگ‌ها، متغیرها ممکن است در register نگه داشته شوند و در print ظاهر نشوند، یا توابع کوتاه inline شوند و breakpoint روی آن‌ها هرگز فعال نشود. این خطا معمولاً به‌صورت breakpoint‌های خاکستری در VS Code یا پیام "could not find function" در Delve ظاهر می‌شود.

10.2.9 Runtime دیباگ با GODEBUG و pprof

علاوه بر Delve، Go ابزارهای دیگری برای دیباگ در زمان اجرا دارد که بدون توقف برنامه قابل استفاده هستند:

GODEBUG: متغیر محیطی GODEBUG به شما امکان می‌دهد رفتار runtime را بدون تغییر کد کنترل کنید. دستورات و فلگ‌های مختلف GODEBUG (مثل schedtrace، gctrace و allocfreetrace) در بخش ۱۰.۱ به‌تفصیل شرح داده شده‌اند.

pprof برای دیباگ زنده: وقتی net/http/pprof فعال باشد، می‌توانید در زمان اجرا وضعیت goroutine‌ها، حافظه، block‌ها و mutex‌ها را بدون توقف برنامه بررسی کنید. endpoint‌های /debug/pprof/goroutine، heap، block و mutex به‌تفصیل در بخش ۱۰.۱ شرح داده شده‌اند.

در اینجا صرفاً به یادآوری می‌پردازیم که ترکیب این endpoint‌ها با دستور goroutines در Delve (که در ادامه می‌آید) مؤثرترین روش ریشه‌یابی مشکلات هم‌روندی است.

10.2.10 معماری Delve: دیباگر و پردازش هدف

همان‌طور که در بخش قبل بررسی کردیم، Delve برخلاف Xdebug یک process جداگانه است که از طریق رابط‌های سیستم‌عامل به باینری Go متصل می‌شود. نمودار زیر جزئیات این معماری و ارتباط بین دیباگر و پردازش هدف را نشان می‌دهد:

نمودار بالا نشان می‌دهد که Delve چگونه از طریق ptrace (در Linux و macOS) یا DebugActiveProcess (در Windows) با برنامه هدف ارتباط برقرار می‌کند. وقتی شما دستوری مثل break main.go:42 صادر می‌کنید، Delve دستورالعمل ماشین مناسب را در آن آدرس حافظه جایگزین می‌کند تا برنامه در آن نقطه متوقف شود.

وقتی برنامه به breakpoint می‌رسد، سیستم‌عامل سیگنال SIGTRAP ارسال می‌کند و Delve کنترل را به دست می‌گیرد. سپس می‌تواند حافظه process را بخواند، مقادیر متغیرها را ارزیابی کند و اطلاعات DWARF را برای نمایش نام متغیرها و انواع آن‌ها به جای آدرس‌های خام استفاده نماید.

این معماری کاملاً متفاوت از Xdebug است که مستقیماً در همان process اجرا می‌شود و از opcode‌های PHP برای کنترل جریان استفاده می‌کند.

10.2.11 سناریوهای عملیاتی Delve

در محیط‌های عملیاتی واقعی، Delve فراتر از دیباگ ساده کاربرد دارد. ترکیب قابلیت‌های breakpoint شرطی، بازرسی goroutine و تحلیل call stack به شما امکان می‌دهد مشکلات پیچیده‌ای را ریشه‌یابی کنید که با log ساده قابل شناسایی نیستند.

این سناریوها معمولاً در برنامه‌های production-grade با صدها goroutine فعال و منطق پیچیده رخ می‌دهند و بدون ابزار مناسب، پیدا کردن ریشه مشکل ممکن است ساعت‌ها یا حتی روزها طول بکشد.

در ادامه مهم‌ترین سناریوهای عملیاتی و روش‌های دیباگ آن‌ها را بررسی می‌کنیم:

  • دیباگ با Breakpoint شرطی: وقتی تابعی هزاران بار فراخوانی می‌شود اما مشکل فقط در حالت خاصی رخ می‌دهد، breakpoint ساده بی‌فایده است. با break main.process if x == 5 یا break main.handler if err != nil فقط در شرایط خاص متوقف شوید. همچنین می‌توانید با condition 1 userID == 999 شرطی را به breakpoint موجود اضافه کنید. این قابلیت یکی از قدرتمندترین ابزارهای Delve است و معادل Conditional Breakpoint در PhpStorm/Xdebug می‌باشد، اما در Delve انعطاف‌پذیری بیشتری در نوشتن شرایط دارید.
  • بازرسی وضعیت Goroutine: در برنامه‌های همزمان، مشکل ممکن است در goroutine‌ای غیر از main رخ دهد. دستور goroutines لیست تمام goroutine‌ها را نمایش می‌دهد، goroutines -t stack trace هر کدام را نشان می‌دهد، و goroutine 5 به goroutine شماره ۵ سوئیچ می‌کند. پس از سوئیچ، می‌توانید با stack و locals وضعیت کامل آن goroutine را بررسی کنید. این قابلیتی است که در PHP/Xdebug وجود ندارد چون PHP تک‌نخی است.
  • بررسی Call Stack: وقتی در یک breakpoint متوقف می‌شوید، دستور stack (یا bt) مسیر فراخوانی کامل را نشان می‌دهد. با frame 2 می‌توانید به فریم خاصی از stack بروید و متغیرهای محلی آن فریم را ببینید. دستور up و down هم برای حرکت بین فریم‌های stack استفاده می‌شوند. این قابلیت برای فهمیدن اینکه چگونه به نقطه فعلی رسیده‌اید بسیار مفید است، به‌ویژه وقتی تابع از چند مسیر مختلف فراخوانی می‌شود.
  • دیباگ در Docker Container: وقتی مشکل فقط در محیط container قابل بازتولید است، Delve را در حالت headless اجرا کنید: dlv exec ./app --headless --listen=:2345 --api-version=2 --accept-multiclient. سپس از محیط محلی با dlv connect localhost:2345 متصل شوید. حتماً پورت ۲۳۴۵ را در Docker map کنید و برنامه را با -gcflags="all=-N -l" بسازید. برای امنیت بیشتر، از SSH tunnel استفاده کنید و هرگز پورت Delve را به اینترنت باز نگذارید.
  • Breakpoint شرطی برای مقادیر خاص: وقتی می‌خواهید فقط وقتی مقدار خاصی در slice یا map وجود دارد متوقف شوید، از شرایط پیچیده‌تر استفاده کنید: break main.process if len(items) > 100 یا break main.validate if user.Role == "admin". همچنین با دستور on 1 print userID می‌توانید هر بار که breakpoint فعال می‌شود مقدار متغیر خاصی را بدون توقف برنامه چاپ کنید (معادل Logpoint در VS Code).
نکته کلیدی: از breakpoint شرطی استفاده کنید تا از گذراندن هزاران فراخوانی بی‌ربط جلوگیری کنید! مثلاً break main.go:42 if x == 5 فقط وقتی x برابر ۵ است برنامه را متوقف می‌کند. بدون این شرط، اگر حلقه ۱۰۰۰۰ بار اجرا شود، باید ۱۰۰۰۰ بار دستور continue بزنید تا به مورد موردنظر برسید. breakpoint شرطی زمان دیباگ را از ساعت‌ها به ثانیه کاهش می‌دهد!
خلاصه‌ی نکات کلیدی:
  • dlv debug برای شروع session
  • break با b file:line
  • step، next، continue برای navigation
  • print و locals برای variable
  • attach به process در حال اجرا
