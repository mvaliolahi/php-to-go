استفاده در VSCode

چکیده: این بخش استفاده از VSCode برای Go development را پوشش می‌دهد: debug، test و refactoring. الگوی launch.json و کاربردهای عملی بررسی می‌شود. تفاوت با PHPStorm و کاربردهای IDE پوشش داده می‌گردد.

اگر کار با خط فرمان را دوست ندارید یا پروژه به اندازه‌ی کافی بزرگ است، بهترین راه استفاده از VS Code با افزونه رسمی Go است. VS Code با افزونه Go، رابط گرافیکی قدرتمند برای دیباگ ارائه می‌دهد که تجربه کار با Delve را ساده‌تر و بصری‌تر می‌کند.

در PhpStorm با Xdebug دیباگ به‌صورت خودکار پیکربندی می‌شود، اما در VS Code با Go باید تنظیمات را دستی انجام دهید که البته انعطاف‌پذیری بسیار بیشتری به شما می‌دهد و می‌توانید سناریوهای پیچیده‌تری را پیکربندی کنید.

هدف این بخش این است که شما را از نصب اولیه تا تنظیمات پیشرفته دیباگ در VS Code همراهی کند.

خواهید آموخت چگونه breakpoint‌ها، watch expressions، conditional breakpoints و logpoints را در محیط گرافیکی استفاده کنید، چگونه برنامه‌ای که در Docker container اجرا می‌شود را دیباگ کنید، و چگونه تست‌های Go را به‌صورت تعاملی دیباگ نمایید.

10.3.1 نصب و راه‌اندازی افزونه Go

برای شروع دیباگ در VS Code ابتدا باید افزونه رسمی Go را نصب کنید و ابزارهای مورد نیاز آن را راه‌اندازی نمایید.

افزونه Go توسط تیم رسمی Google توسعه داده می‌شود و قابلیت‌های زیر را ارائه می‌دهد: IntelliSense، Go to Definition، Find References، Refactor و از همه مهم‌تر دیباگ گرافیکی با breakpoint، watch و call stack.

10.3.2 تنظیمات launch.json: سناریوهای مختلف دیباگ

فایل launch.json قلب دیباگ در VS Code است. این فایل در پوشه .vscode قرار می‌گیرد و سناریوهای مختلف دیباگ را تعریف می‌کند.

در PhpStorm نیازی به فایل مشابه نیست چون Xdebug به‌صورت خودکار پیکربندی می‌شود، اما launch.json انعطاف‌پذیری بسیار بیشتری می‌دهد و می‌توانید مشخص کنید کدام برنامه، با چه آرگومان‌ها و متغیرهای محیطی، در چه مد دیباگ اجرا شود.

برای ساخت فایل launch.json، روی آیکون Debug در نوار کناری کلیک کنید، سپس «create a launch.json file» را انتخاب و Go را به‌عنوان environment انتخاب کنید. VS Code یک فایل با چند configuration پیش‌فرض می‌سازد که می‌توانید آن‌ها را سفارشی کنید.

در ادامه هر configuration را بررسی می‌کنیم: Debug Current File فایل فعلی را دیباگ می‌کند و برای کدهای ساده مناسب است. Debug Package یک package خاص را با آرگومان‌ها و متغیرهای محیطی اجرا می‌کند. Debug Tests برای دیباگ تست‌هاست. Attach to Remote برای دیباگ برنامه‌ای است که در Docker یا سرور راه‌دور اجرا می‌شود. Attach to Process به process در حال اجرا متصل می‌شود و Debug with Race Detector race detector را فعال می‌کند.

10.3.3 دیباگ در Container

از سناریوهای رایج دیباگ در پروژه‌های مدرن، دیباگ برنامه‌ای است که در Docker container اجرا می‌شود. برای این کار باید Delve را در container نصب کنید و آن را در حالت headless اجرا نمایید.

VS Code از نسخه ۱.۴۰+ از Docker Compose و Dev Containers پشتیبانی می‌کند که تجربه دیباگ container را بسیار ساده‌تر کرده است.

روش ۳: Dev Containers

VS Code قابلیت Dev Containers را دارد که به شما اجازه می‌دهد کل محیط توسعه را داخل container اجرا کنید. در این حالت، نیازی به remote attach نیست چون VS Code مستقیماً داخل container اجرا می‌شود و دیباگ مثل حالت محلی کار می‌کند:

نکته مهم: برای دیباگ صحیح در container، حتماً برنامه را با فلگ‌های -gcflags="all=-N -l" بسازید تا بهینه‌سازی کامپایلر غیرفعال شود. بدون این فلگ‌ها، ممکن است breakpoint‌ها کار نکنند یا متغیرها قابل مشاهده نباشند. همچنین remotePath باید مسیر کد داخل container باشد.
نکته: تنظیم نادرست remotePath یکی از رایج‌ترین دلایل کار نکردن breakpoint‌ها در دیباگ container است. این مقدار باید دقیقاً با مسیر کد Go داخل container مطابقت داشته باشد (مثلاً "/app" یا "/workspace")، نه مسیر محلی شما. وقتی VS Code روی یک خط breakpoint می‌گذارد اما برنامه متوقف نمی‌شود، ابتدا remotePath و mode: "remote" را بررسی کنید. ابزار Delve برای نگاشت خط کد محلی به خط کد داخل container به این مسیر وابسته است و هرگونه عدم تطابق باعث می‌شود breakpoint‌ها به خط اشتباه یا اصلاً متصل نشوند.

10.3.4 دیباگ تست‌ها

یکی از قابلیت‌های بسیار مفید VS Code برای توسعه Go دیباگ تعاملی تست‌هاست. در PhpStorm با PHPUnit دیباگ تست‌ها به‌صورت خودکار پشتیبانی می‌شود اما در VS Code با Go باید configuration مناسب بسازید. با این حال VS Code قابلیت‌هایی دارد که PhpStorm فاقد آن‌هاست مانند دیباگ تست‌های race-sensitive.

10.3.5 امکانات پیشرفته دیباگ در VS Code

Watch Expressions: می‌توانید عبارات پویا اضافه کنید که در هر توقف برنامه محاسبه می‌شوند. مثلاً len(users)، resp.StatusCode یا time.Since(start).Milliseconds(). این قابلیت مشابه watch در PhpStorm است اما در Go امکان مشاهده مقادیر struct‌ها و slice‌tree view دارد. برای اضافه‌کردن watch، در پنل Variables روی بخش Watch کلیک کنید و عبارت مورد نظر را تایپ نمایید.

Conditional Breakpoints: با کلیک راست روی خط breakpoint می‌توانید شرط تعیین کنید. مثلاً userID == 999، len(items) > 100 یا err != nil. این قابلیت برای دیباگ در حلقه‌های بزرگ یا handler‌هایی که هزاران بار فراخوانی می‌شوند بسیار مفید است. Conditional breakpoint در VS Code مشابه break main.func if condition در Delve است.

Logpoints: به‌جای توقف برنامه، می‌توانید یک پیام لاگ اضافه کنید. این قابلیت برای دیباگ بدون توقف برنامه مفید است. مثلاً وقتی می‌خواهید مقدار یک متغیر را در هر فراخوانی ببینید بدون اینکه جریان اجرا را متوقف کنید.

Logpoint معادل on <bp> print <expr> در Delve است. در داخل Logpoint می‌توانید از {variableName} برای نمایش مقدار متغیر استفاده کنید.

Debug Console: در حین دیباگ می‌توانید عبارات Go را مستقیماً در Debug Console ارزیابی کنید. مثلاً تایپ کنید user.Name و Enter بزنید تا مقدار فعلی نمایش داده شود. این قابلیت معادل دستور print در Delve است اما در محیط گرافیکی. شما می‌توانید هر عبارت معتبر Go را ارزیابی کنید، حتی فراخوانی تابع.

Hit Count Breakpoints: می‌توانید تعیین کنید breakpoint فقط بار N-ام فعال شود. مثلاً 5 به‌معنای توقف فقط در فراخوانی پنجم، یا % 10 == 0 به‌معنای توقف هر ۱۰ فراخوانی یک‌بار. این قابلیت برای دیباگ مشکلاتی که فقط بعد از چند بار تکرار ظاهر می‌شوند مفید است.

Data Breakpoints: می‌توانید روی یک متغیر خاص breakpoint که هر بار مقدار آن تغییر کند، برنامه متوقف شود. این قابلیت در VS Code 1.60+ اضافه شده و برای شناسایی اینکه کجا یک متغیر مقدار غیرمنتظره می‌گیرد بسیار مفید است.

10.3.6 رفع مشکلات رایج دیباگ در VS Code

هنگام دیباگ Go در VS Code ممکن است با مشکلاتی مواجه شوید. در اینجا مشکلات رایج و راه‌حل آن‌ها آورده شده است:

مشکل: Breakpoint‌ها کار نمی‌کنند (خاکستری هستند)

این مشکل معمولاً به دلیل فعال بودن بهینه‌سازی کامپایلر رخ می‌دهد. راه‌حل: مطمئن شوید برنامه با فلگ -gcflags="all=-N -l" کامپایل شده باشد. در launch.json این فلگ به‌صورت خودکار اضافه می‌شود، اما اگر باینری را جداگانه ساخته‌اید باید دستی اضافه کنید. همچنین اگر از go run استفاده می‌کنید، به‌جای آن از dlv debug استفاده کنید.

مشکل: متغیرها قابل مشاهده نیستند

وقتی بهینه‌سازی فعال باشد، کامپایلر ممکن است متغیرها را حذف کند یا در register نگه دارد. راه‌حل: غیرفعال‌سازی بهینه‌سازی با -gcflags="all=-N -l". اگر متغیر در closure استفاده شده، ممکن است با نام & شروع شود. از دستور args و locals در Debug Console استفاده کنید.

مشکل: Cannot find Delve debugger

Delve نصب نشده یا در PATH نیست. راه‌حل: go install github.com/go-delve/delve/cmd/dlv@latest را اجرا کنید و مطمئن شوید $GOPATH/bin در PATH شماست. در VS Code می‌توانید مسیر Delve را با "go.alternateTools.dlv": "/path/to/dlv" مشخص کنید.

مشکل: Remote attach نمی‌شود

پورت Delive در container باز نیست یا فایروال جلوگیری می‌کند. راه‌حل: مطمئن شوید پورت ۲۳۴۵ در Docker map شده (-p 2345:2345)، api-version=2 در دستور Delve مشخص شده، و SSH tunnel برقرار است.

مقایسه با PHP: در PhpStorm دیباگ Xdebug به‌صورت خودکار پیکربندی می‌شود و نیازی به فایل مشابه launch.json ندارید. PhpStorm از قابلیت «Zero Configuration Debugging» برخوردار است که با نصب Xdebug و تنظیم یک پورت، همه‌چیز خودکار کار می‌کند. اما در VS Code با Go، فایل launch.json انعطاف‌پذیری بیشتری می‌دهد و می‌توانید سناریوهای مختلف (local، remote، test، race detector) را به‌صورت جداگانه تعریف کنید. این انعطاف‌پذیری برای پروژه‌های پیچیده با معماری microservice بسیار مفید است.

10.3.8 نقشه ویژگی‌های افزونه Go و جریان پیکربندی دیباگ

افزونه رسمی Go در VS Code مجموعه‌ای جامع از ویژگی‌های توسعه را ارائه می‌دهد که تجربه برنامه‌نویسی Go را به سطح بالایی می‌رساند. در PhpStorm این ویژگی‌ها به‌صورت پیش‌فرض و بدون نیاز به پیکربندی اضافی در دسترس هستند، اما در VS Code باید افزونه مناسب را نصب و تنظیم کنید.

مزیت این رویکرد انعطاف‌پذیری بسیار بیشتر است: می‌توانید هر ویژگی را مستقل تنظیم کنید و ترکیب دلخواه خود را بسازید.

درک نقشه ویژگی‌ها و نحوه پیکربندی دیباگ به شما کمک می‌کند از حداکثر ظرفیت VS Code برای توسعه Go بهره ببرید و گردش کار خود را بهینه‌سازی کنید.

نمودار بالا دو بخش اصلی را نشان می‌دهد: بخش اول نقشه ویژگی‌های افزونه Go است که شامل ابزارهای ناوبری کد (Go to Definition، Find References، Rename Symbol)، IntelliSense، Diagnostics و دیباگ گرافیکی است.

بخش دوم جریان پیکربندی دیباگ را نشان می‌دهد که از فایل launch.json شروع شده و با فشردن F5 به دیباگر متصل می‌شود.

هر مرحله از این جریان پیکربندی مشخص دارد و اگر هر کدام نادرست باشد، دیباگ کار نمی‌کند. به همین دلیل مهم است که هر پارامتر launch.json را بشناسید و برای سناریوی خود تنظیم کنید.

10.3.9 سناریوهای عملیاتی VS Code برای توسعه Go

در محیط‌های عملیاتی واقعی، پیکربندی دیباگ در VS Code فراتر از یک فایل launch.json ساده است. هر پروژه نیازمندی‌های خاص خود را دارد: برخی برنامه‌ها باید با آرگومان‌های خط فرمان اجرا شوند، برخی در Docker container دیباگ می‌شوند، و برخی نیاز به build tags خاص دارند.

همچنین دیباگ تست‌ها و remote debugging سناریوهای متفاوتی را ایجاد می‌کنند. در ادامه مهم‌ترین سناریوهای عملیاتی و روش‌های پیکربندی آن‌ها را بررسی می‌کنیم:

  • تنظیم launch.json برای دیباگ: اولین و مهم‌ترین قدم، ساخت فایل .vscode/launch.json صحیح است. حداقل یک configuration برای دیباگ محلی و یک configuration برای دیباگ تست نیاز دارید. برای برنامه‌هایی که از stdin می‌خوانند، حتماً "console": "integratedTerminal" را تنظیم کنید — مقدار پیش‌فرض "internalConsole" از ورودی stdin پشتیبانی نمی‌کند و برنامه قفل می‌شود. همچنین "showLog": true و "logOutput": "rpc" را برای رفع مشکلات دیباگ فعال کنید.
  • دیباگ فایل‌های تست: برای دیباگ تست‌ها، از "mode": "test" در launch.json استفاده کنید. با "args": ["-test.run", "^TestUserService$"] فقط تست خاصی اجرا می‌شود. افزونه Go همچنین لینک‌های debug test و run test بالای هر تابع تست اضافه می‌کند که ساده‌ترین روش دیباگ تست‌های منفرد است. برای تست‌های همزمان، از "buildFlags": "-race" استفاده کنید تا race detector فعال شود.
  • دیباگ راه‌دور با Delve: همان‌طور که در بخش «دیباگ در Container» بالاتر شرح داده شد، Delve را در حالت headless روی سرور یا داخل container اجرا کنید (dlv exec --headless --listen=:2345 --api-version=2)، سپس در launch.json یک configuration با "request": "attach"، "mode": "remote"، "port": 2345 و "remotePath" متناظر با مسیر کد داخل container اضافه کنید. برای امنیت، همیشه از SSH tunnel استفاده کنید و پورت 2345 را مستقیماً به اینترنت باز نگذارید (توضیحات کامل‌تر و Dockerfile نمونه در بخش Container آمده است).
  • استفاده از Go Test Explorer: افزونه Go یک Test Explorer در نوار کناری VS Code اضافه می‌کند که تمام تست‌های پروژه را به‌صورت درختی نمایش می‌دهد. می‌توانید با کلیک راست روی هر تست، آن را مستقیماً دیباگ کنید. همچنین آیکون‌های سبز و قرمز وضعیت موفقیت یا شکست هر تست را نشان می‌دهند. این قابلیت مشابه Test Runner در PhpStorm است اما رابط کاربری ساده‌تری دارد.
  • پیکربندی Build Tags برای دیباگ: وقتی پروژه از build tags استفاده می‌کند (مثلاً //go:build integration)، باید آن‌ها را در launch.json مشخص کنید: "buildFlags": "-tags=integration". بدون این تنظیم، VS Code فایل‌هایی که build tag دارند را نادیده می‌گیرد و breakpoint‌ها روی آن‌ها کار نمی‌کند. همچنین می‌توانید در settings.json مقدار "go.buildTags": "integration" را تنظیم کنید تا همیشه اعمال شود.
نکته کلیدی: اگر برنامه شما از stdin می‌خواند (مثلاً ورودی کاربر یا pipe)، حتماً در launch.json مقدار "console": "integratedTerminal" را تنظیم کنید. مقدار پیش‌فرض "internalConsole" از stdin پشتیبانی نمی‌کند و برنامه در منتظر ورودی می‌ماند! همچنین اگر خروجی رنگی یا کاراکترهای خاص دارید، "integratedTerminal" بهترین گزینه است چون رفتار یکسانی با terminal واقعی دارد.
