تست پیشرفته APIهای RESTful با httpexpect

پیش تر در مورد تست کردن http handler ها توضیح داده شد. در سیستم‌های واقعی بخش مهمی از برنامه APIهای HTTP هستند که با کلاینت‌ها، مرورگر یا سیستم‌های دیگر ارتباط برقرار می‌کنند. تست این APIها هم از نظر صحت عملکرد و هم از جهت امنیت، ساختار پاسخ و سازگاری اهمیت دارد.

در Go برای تست کردن APIهای RESTful ابزار httpexpect از گزینه‌های قدرتمند است. این ابزار امکان نوشتن تست‌هایی شبیه به Postman اما در قالب کد Go و با قابلیت‌های assertion بسیار قوی را فراهم می‌کند. از جمله ویژگی های این پکیج:

بررسی دقیق status code، header، body، JSON و فرم‌ها

پشتیبانی از cookie و session

قابل اجرا به صورت in-process یا real HTTP request

پشتیبانی از chain‌های assertion خوانا و دقیق

نکته درباره طراحی قابل‌تست API: پیش از نوشتن تست، مطمئن شوید هندلرهای شما قابل تزریق http.Handler هستند. یعنی به‌جای وابستگی به http.DefaultServeMux یا متغیرهای سراسری، یک NewRouter(deps) یا NewHandler(deps) بسازید که وابستگی‌ها را به‌صورت پارامتر بپذیرد. این الگو به شما اجازه می‌دهد در تست، همان router را با mock یا دیتابیس تستی بسازید و به httptest.NewServer بدهید. در Laravel این کار با Service Provider و Container خودکار است، اما در Go صریح بودن آن مزیت محسوب می‌شود چون وابستگی‌ها شفاف می‌مانند.

جریان کامل تست HTTP: از درخواست تا اعتبارسنجی

برای درک جامع نحوه تست API‌های RESTful، بیایید کل جریان را از ایجاد سرور تست تا اعتبارسنجی نهایی مرحله‌به‌مرحله بررسی کنیم. هر تست HTTP از هفت مرحله تشکیل شده است: ابتدا سرور تست با httptest.NewServer ایجاد می‌شود که بدون نیاز به پورت واقعی یا شبکه، هندلرهای شما را اجرا می‌کند. سپس درخواست با متد، مسیر، بدنه و هدرهای مناسب ساخته شده و ارسال می‌شود. پس از دریافت پاسخ، سه سطح اعتبارسنجی انجام می‌شود: کد وضعیت، بدنه JSON و هدرها. httpexpect این مراحل را در یک API روان (fluent) ترکیب می‌کند که هر مرحله به مرحله بعد متصل می‌شود و خوانایی تست را به‌شدت افزایش می‌دهد.

در نمودار بالا هفت مرحله‌ی تست HTTP به‌صورت کامل نمایش داده شده است. نکته کلیدی این است که در Go با httptest.NewServer هیچ نیاز به شبکه واقعی نیست — سرور تست کاملاً درون فرآیند (in-process) اجرا می‌شود و درخواست‌ها بدون عبور از شبکه پردازش می‌شوند. این ویژگی باعث می‌شود تست‌ها بسیار سریع‌تر از تست‌های واقعی HTTP باشند و در عین حال دقیقاً همان کدی را اجرا کنند که در تولید استفاده می‌شود. httpexpect با ارائه fluent API زنجیره‌ای، مراحل ساخت درخواست، ارسال و اعتبارسنجی را در یک عبارت خوانا ترکیب می‌کند که از نظر نگهداری و خوانایی بسیار برتر از روش دستی است.

سناریوهای عملیاتی تست API

در پروژه‌های واقعی، تست API بسیار فراتر از یک درخواست ساده GET است. سناریوهای متعددی وجود دارند که هر کدام نیاز به رویکرد خاصی دارند و توجه به جزئیات متفاوتیrequire می‌کنند. از تست عملیات CRUD کامل تا بررسی رفتار سرور در شرایط خطا، هر سناریو نکات ظریف خود را دارد که در زیر به تفصیل بررسی می‌شوند.

  • تست CRUD کامل: هر endpoint را با تمام عملیات Create، Read، Update و Delete تست کنید. ابتدا یک منبع جدید بسازید (POST)، سپس آن را بخوانید (GET) و اعتبارسنجی کنید، بعد به‌روزرسانی کنید (PUT) و در نهایت حذف کنید (DELETE). هر مرحله باید پاسخ مناسبی برگرداند و تغییرات در مرحله بعد قابل مشاهده باشند.
  • تست middleware احراز هویت: هر سه حالت را تست کنید: بدون توکن (باید ۴۰۱ برگرداند)، با توکن نامعتبر (باید ۴۰۱ برگرداند) و با توکن معتبر (باید ۲۰۰ برگرداند). همچنین دسترسی بر اساس نقش (role) را بررسی کنید: کاربر عادی نباید به endpoint مدیریت دسترسی داشته باشد.
  • تست صفحه‌بندی (Pagination): صفحه اول، صفحه آخر و صفحه میانی را جداگانه تست کنید. بررسی کنید که meta شامل تعداد کل، شماره صفحه و حد مجاز باشد و تعداد آیتم‌های هر صفحه از حد مجاز تجاوز نکند. همچنین صفحه خارج از محدوده باید ۴۰۴ یا آرایه خالی برگرداند.
  • تست پاسخ‌های خطا (۴۰۰، ۴۰۴، ۵۰۰): ورودی نامعتبر باید ۴۰۰ با پیام خطای واضح برگرداند. منبع ناموجود باید ۴۰۴ برگرداند. خطای سرور باید ۵۰۰ با ساختار ثابت و بدون نشت اطلاعات حساس برگرداند. هر کد خطا باید فرمت JSON یکسانی داشته باشد.
  • تست endpoint آپلود فایل: فایل معتبر و نامعتبر (فرمت اشتباه، حجم بیش از حد) را تست کنید. بررسی کنید که فایل ذخیره شده و URL بازگشتی معتبر باشد. فایل خالی و فایل بسیار بزرگ نیز باید به‌درستی مدیریت شوند.
نکته کلیدی درباره httptest.NewServer: از httptest.NewServer برای تست هندلرها بدون راه‌اندازی سرور واقعی استفاده کنید — این روش سریع، ایزوله و بدون نیاز به دسترسی شبکه است. سرور تست کاملاً درون فرآیند اجرا می‌شود و درخواست‌ها بدون عبور از پشته شبکه پردازش می‌شوند. این یعنی تست‌های شما چند مرتبه سریع‌تر از تست‌های واقعی HTTP اجرا می‌شوند و هیچ وابستگی به پورت‌ها یا وضعیت شبکه ندارند. همچنین چون سرور تست پس از هر تست بسته می‌شود، هیچ تداخلی بین تست‌ها وجود ندارد و هر تست در محیطی کاملاً تمیز اجرا می‌شود.
