درک error در Go

در Go خطاها از طریق نوع داده‌ی error که در واقع یک interface است مدیریت می‌شوند.

یعنی هر چیزی که متدی با امضای Error() string داشته باشد می‌تواند به عنوان یک error استفاده شود.

error در سطح اجرا: چگونه کار می‌کند؟

در زمان اجرا مقدار از نوع error در واقع یک interface value است که از دو بخش تشکیل شده: یک اشاره‌گر به اطلاعات نوع type descriptor و یک اشاره‌گر به داده‌ی واقعی. وقتی می‌نویسید var err error هر دو مؤلفه nil هستند. وقتی errors.New("msg") را فراخوانی می‌کنید، یک *errors.errorString ساخته شده و مقادیر type و data آن‌ها در interface value قرار می‌گیرند.

نکته‌ی فنی: به این دلیل که errors.New یک اشاره‌گر برمی‌گرداند، دو فراخوانی errors.New("same") با هم برابر نیستند — حتی اگر رشته‌ی یکسانی داشته باشند. این رفتار عمدی است تا مقایسه‌ی == بین خطاها گمراه‌کننده نباشد. برای مقایسه‌ی خطاها همیشه از errors.Is استفاده کنید.

errors.Is و errors.As: جستجو در زنجیره‌ی خطا

وقتی خطاها با fmt.Errorf("%w", err) wrap می‌شوند، type assertion ساده دیگر کار نمی‌کند — زیرا نوع بیرونی دیگر همان نوع اصلی نیست. errors.Is و errors.As این مشکل را حل می‌کنند:

errors.Is زنجیره‌ی خطا را با فراخوانی متد Unwrap() پیمایش می‌کند و هر حلقه را با خطای هدف مقایسه می‌کند. errors.As نیز همان مسیر را طی می‌کند اما به‌جای مقایسه‌ی برابری، از interface matching استفاده می‌کند.

مهم: به errors.As باید اشاره‌گر به متغیر از نوع موردنظر بدهید، نه خود نوع را. این‌گونه اگر تطبیق پیدا شود، مقدار خطا در متغیر قرار می‌گیرد و به فیلدهای آن دسترسی دارید.
قانون تصمیم‌گیری errors.Is در برابر errors.As: اگر می‌خواهید بدانید «آیا این خطا (یا خطای پنهان‌شده در زنجیره) همان خطای از پیش تعریف‌شده‌ی فلان است؟» از errors.Is استفاده کنید — معادل err == sentinel اما در کل زنجیره. اگر می‌خواهید فیلدهای یک نوع خطای سفارشی (مثل Path در NotFoundError) را استخراج کنید، از errors.As استفاده کنید — معادل instanceof در PHP. به‌طور خلاصه: Is برای مقدار، As برای نوع و استخراج داده.

زنجیره‌ی Error Wrapping

خطاها را فقط بررسی نکنید، آن‌ها را با ظرافت مدیریت کنید. خطاهای نگهبان اتصال بین پکیج‌ها ایجاد می‌کنند. بسته‌بندی خطاها با زمینه و بررسی آن‌ها با errors.Is یا errors.As را ترجیح دهید. این کار زنجیره‌های خطا را صریح و قابل ردیابی می‌کند.

الگوهای ضد در مدیریت خطا

برنامه‌نویسان PHP هنگام مهاجرت به Go معمولاً الگوهای زیر را تکرار می‌کنند که همگی anti-pattern محسوب می‌شوند:

۱. نادیده گرفتن خطا: بدترین الگوی ممکن — خطا را کلاً بررسی نکردن.

۲. فقط ثبت خطا بدون برگرداندن: خطا را ثبت می‌کنند اما به فراخوانی‌کننده اطلاع نمی‌دهند.

۳. برگرداندن خطا بدون context: فقط return err بدون اضافه کردن اطلاعات اضافی.

قانون طلایی خطا در Go: هر خطا باید دو چیز داشته باشد: ۱) Context — اطلاعاتی درباره‌ی اینکه خطا در چه زمینه‌ای رخ داده، ۲) زنجیره — خطای اصلی باید با %w بسته‌بندی شود تا errors.Is و errors.As کار کنند.

تابع جدید errors.AsType generic از errors.As است. این تابع type-safe، سریع‌تر و در بیشتر موارد آسان‌تر برای استفاده است. برخلاف errors.As که نیاز به ایجاد متغیر هدف دارد، errors.AsType مستقیماً نوع هدف را مشخص می‌کند:

مزیت اصلی errors.AsType علاوه بر type-safety، حذف نیاز به ایجاد متغیر هدف قبل از فراخوانی و خوانایی بهتر کد است. رفتار errors.As بدون تغییر باقی می‌ماند و هر دو تابع می‌توانند در کنار هم استفاده شوند.

مدیریت خطا نباید کنترل جریان برنامه باشد. خطاها ارزشی هستند که باید منتقل شوند، نه استثنائی که باید گرفته شوند. این رویکرد به کد اجازه می‌دهد خواناتر باشد و خطاها را در سطح مناسب مدیریت کنند.

جریان خطا در پشته فراخوانی: از Database تا Handler

در یک برنامه‌ی وب واقعی، خطا معمولاً در پایین‌ترین لایه (مثلاً Database) رخ می‌دهد و باید از طریق لایه‌های میانی به بالاترین لایه منتقل شود. هر لایه باید خطا را با fmt.Errorf و فعل %w بسته‌بندی کند تا ضمن حفظ زنجیره‌ی خطا، زمینه‌ی خود را نیز اضافه نماید. این رویکرد تضمین می‌کند که وقتی خطا به Handler می‌رسد، پیام آن شامل مسیر کامل از منبع خطا تا لایه‌ی بالاست. بدون این بسته‌بندی، ردیابی علت واقعی خطا در یک سیستم چندلایه بسیار دشوار خواهد بود.

در لایه‌ی Repository خطا با اطلاعاتی درباره‌ی عملیات پایگاه‌داده بسته‌بندی می‌شود، مثلاً fmt.Errorf("query user: %w", err). در لایه‌ی Service همان خطا با زمینه‌ی منطق کسب‌وکار بسته‌بندی می‌شود مثل fmt.Errorf("get user: %w", err). در نهایت HTTP Handler خطا را بررسی کرده و تصمیم می‌گیرد چه کد وضعیت مناسبی به کلاینت برگردانده شود. این الگوی لایه‌ای بسته‌بندی، ردیابی خطا را در سیستم‌های بزرگ ساده‌تر و قابل‌اتکاتر می‌کند.

سناریوهای عملیاتی مدیریت خطا

در پروژه‌های واقعی، مدیریت خطا فراتر از if err != nil ساده است. هر لایه‌ی برنامه مسئولیت‌های متفاوتی در برخورد با خطا دارد و باید بر اساس نقش خود تصمیم‌گیری کند. برنامه‌نویسان PHP که به try-catch عادت دارند، باید در Go به‌صورت صریح‌تری درباره‌ی نحوه‌ی مدیریت و انتقال خطا فکر کنند. در ادامه مهم‌ترین سناریوهای عملیاتی مدیریت خطا در برنامه‌های Go را بررسی می‌کنیم که هر یک در عمل روزمره به‌طور مکرر استفاده می‌شوند.

  • مدیریت خطا در HTTP Handlerها: در لایه‌ی Handler باید خطا را به کد وضعیت مناسب تبدیل کنید. خطای اعتبارسنجی باید 400 Bad Request برگرداند، خطای عدم وجود منبع باید 404 Not Found باشد و خطای داخلی سرور باید 500 Internal Server Error شود. هرگز جزئیات خطای داخلی را به کلاینت نفرستید — این هم مشکل امنیتی دارد و هم برای کاربر بی‌فایده است. به‌جای آن خطا را در لاگ ثبت کرده و پیام عمومی برگردانید.
  • انتشار خطا در لایه‌های سرویس: لایه‌ی سرویس نباید درباره‌ی HTTP status code بداند — وظیفه‌ی آن فقط اجرای منطق کسب‌وکار و بسته‌بندی خطا با fmt.Errorf است. این جداسازی مسئولیت‌ها باعث می‌شود لایه‌ی سرویس از پروتکل انتقال مستقل بماند و بتوان آن را در زمینه‌های دیگر مثل CLI یا gRPC نیز استفاده کرد.
  • ثبت خطا با زمینه: هنگام لاگ کردن خطا، همیشه اطلاعات زمینه‌ای اضافه کنید: شناسه‌ی درخواست، شناسه‌ی کاربر، نام عملیات و پارامترهای ورودی. بدون این اطلاعات، پیدا کردن علت خطا در میان هزاران خط لاگ مانند پیدا کردن سوزن در انبار کاه خواهد بود. از structured logging مثل slog استفاده کنید تا زمینه‌ها به‌صورت کلید-مقدار ثبت شوند.
  • تمایز بین خطای کلاینت (4xx) و خطای سرور (5xx): این تمایز حیاتی است. خطای 4xx یعنی کلاینت درخواست اشتباهی فرستاده و باید درخواستش را اصلاح کند. خطای 5xx یعنی سرور مشکل داخلی دارد و کلاینت بعداً دوباره تلاش کند. برای تمایز، از خطاهای سفارشی با فیلد StatusCode یا از errors.As برای تشخیص نوع خطا استفاده کنید.
  • استفاده از errors.Is برای بررسی خطاهای Sentinel: وقتی می‌خواهید بدانید آیا خطای خاصی (مثل sql.ErrNoRows یا os.ErrNotExist) در زنجیره‌ی خطا وجود دارد، از errors.Is استفاده کنید. هرگز از err == sentinelErr استفاده نکنید زیرا اگر خطا wrap شده باشد، مقایسه‌ی برابری false برمی‌گرداند. errors.Is تمام زنجیره را با فراخوانی Unwrap() پیمایش می‌کند.
  • استفاده از errors.As برای بررسی نوع خطا: وقتی نیاز به دسترسی به فیلدهای خطای سفارشی دارید (مثل فیلد Path در NotFoundError)، از errors.As استفاده کنید. این تابع زنجیره‌ی خطا را پیمایش کرده و اولین خطایی که نوع موردنظر را داشته باشد استخراج می‌کند. به‌یاد داشته باشید که به errors.As باید اشاره‌گر به متغیر بدهید، نه خود نوع را.
نکته‌ی عملی — بسته‌بندی خطا بدون تکرار: هر لایه باید خطا را فقط یک‌بار با fmt.Errorf("context: %w", err) بسته‌بندی کند. اگر در یک لایه خطا را دو بار wrap کنید، پیام خطا تکراری و گنگ می‌شود: "failed to get user: failed to get user: query error". الگوی صحیح این است: هر لایه فقط یک زمینه‌ی جدید اضافه کند و خطای wrap شده را همان‌طور که هست به لایه‌ی بالاتر منتقل کند. همچنین هرگز از %v به‌جای %w استفاده نکنید، زیرا %v زنجیره‌ی خطا را قطع می‌کند و errors.Is/As دیگر قادر به پیمایش آن نخواهد بود.
