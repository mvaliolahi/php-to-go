ماژول‌ها و مدیریت dependency ها

در زبان Go مدیریت dependency ها به‌صورت رسمی و ساختار یافته از طریق ماژول‌ها انجام می‌شود. این سیستم که از نسخه 1.11 به بعد معرفی شده و جایگزین روش‌های قدیمی مبتنی بر GOPATH شده و اکنون ابزار اصلی برای مدیریت کد و dependency ها و نسخه‌بندی پروژه‌هاست.

برای توسعه‌دهندگانی که از PHP می‌آیند می‌توان این ساختار را مشابه Composer در نظر گرفت با این تفاوت که در Go ساده‌تر، سریع‌تر و tightly integrated در خود زبان است. در واقع در زبان Go ماژول مجموعه‌ای از Package هاست که با هم در یک پروژه قرار دارند و توسط یک فایل به‌نام go.mod مدیریت می‌شوند. این فایل اطلاعاتی درباره‌ی نام ماژول نسخه‌های dependency ها و نیازهای پروژه را نگهداری می‌کند.

فایل go.sum

go.sum فایلی است که هش‌های رمزنگاری‌شده‌ای از dependency ها را ذخیره می‌کند. این فایل تضمین می‌کند که هر بار پروژه را build می‌کنید دقیقاً همان نسخه‌ای از کتابخانه استفاده شود که در گذشته دانلود شده. توجه کنید که هیچ‌گاه نباید go.sum را حذف کنید یا آن را از commit خارج کنید.

مدیریت dependency ها

مدیریت وابستگی‌ها یکی از بخش های کلیدی‌ است. این فرآیند با استفاده از Go Modules و مجموعه‌ای از دستورات ساده ولی قدرتمند انجام می‌شود که باعث می‌شود برنامه‌ها پایدار، قابل حمل و قابل بازتولید باشند.

1. go mod tidy

این دستور تمام dependency‌های اضافی را حذف می‌کند و هر بسته‌ای که استفاده شده اما در فایل go.mod ذکر نشده باشد را افزودن می‌کند. به عبارت دیگر go mod tidy تضمین می‌کند که لیست dependency‌ها به‌طور دقیق مطابق با نیاز پروژه باشد و از وجود ماژول‌های بلااستفاده جلوگیری می‌کند. این دستور به ویژه قبل از commit یا انتشار پروژه ضروری است تا پروژه سبک و مرتب باقی بماند.

2. go list -m all

برای مشاهده تمام ماژول‌ها و نسخه‌های دقیق آن‌ها از دستور go list -m all استفاده می‌کنیم. این دستور به توسعه‌دهنده امکان می‌دهد نگاهی شفاف به تمام وابستگی‌ها و نسخه‌های استفاده شده داشته باشد که برای بررسی سازگاری و حل تعارضات نسخه بسیار مفید است.

3. go mod verify

با اجرای go mod verify، Go بررسی می‌کند که فایل‌های دانلود شده با مقادیر موجود در go.sum مطابقت دارند یا خیر. این فرآیند امنیت و یکپارچگی پروژه را تضمین می‌کند و از مشکلات ناشی از تغییرات ناخواسته در بسته‌های خارجی جلوگیری می‌کند.

4. go get

دستور go get برای افزودن یا به‌روزرسانی یک بسته یا ماژول استفاده می‌شود. این دستور نسخه مناسب بسته را دانلود می‌کند و در فایل go.mod ثبت می‌کند، به طوری که پروژه همیشه بتواند نسخه مشخصی از هر dependency را بازتولید کند.

استفاده از ماژول‌های لوکال

در پروژه‌های بزرگ یا هنگامی که چند ماژول Go به صورت هم‌زمان در حال توسعه هستند ممکن است نیاز داشته باشید تغییرات یک ماژول را بدون انتشار نسخه جدید روی پروژه‌های دیگر تست کنید. برای این منظور Go امکان استفاده از ماژول‌های محلی را فراهم می‌کند.

با استفاده از دستور replace در فایل go.mod می‌توانید به Go بگویید که به جای دریافت ماژول از remote repository از یک مسیر محلی مشخص‌شده استفاده کند:

replace github.com/username/mylib => ../mylib

مسیر سمت راست یا mylib می‌تواند هر مسیر دلخواه روی سیستم شما باشد که حاوی ماژول Go است. این امکان باعث می‌شود بتوانید تغییرات یک ماژول را به صورت فوری و بدون انتشار رسمی بررسی کنید.به عبارتی می‌توانید روی چند کتابخانه یا ماژول به صورت موازی کار کنید و تغییرات یک ماژول را در پروژه اصلی سریعاً تست کنید.و یا بدون نیاز به commit یا push نسخه محلی ماژول در پروژه اصلی مورد استفاده قرار می‌گیرد.همچنین کنترل کامل روی مسیر و نسخه ماژول‌ها دارید و می‌توانید به راحتی بین نسخه محلی و آنلاین سوئیچ کنید.

توجه داشته باشید که پس از پایان توسعه و اطمینان از عملکرد ماژول حتماً خط replace را از go.mod حذف کنید تا پروژه به نسخه رسمی آنلاین وابسته شود و مسیرهای محلی باعث مشکلات بعدی نشوند.

الگوریتم Minimal Version Selection

یکی از تفاوت‌های بنیادین بین Go Modules و Composer در نحوه‌ی انتخاب نسخه‌ی وابستگی‌هاست. Composer از الگوریتمی شبیه به بالاترین نسخه‌ی ممکن استفاده می‌کند: اگر پروژه‌ی شما به پکیج X نیاز داشته باشد و دو وابستگی مختلف به‌ترتیب نسخه‌های ^1.2 و ^1.5 را بخواهند، Composer نسخه‌ی جدیدتر (مثلاً 1.8) را انتخاب می‌کند.

اما Go از الگوریتم MVS استفاده می‌کند که کاملاً متفاوت است: حداقل نسخه‌ای که تمام محدودیت‌ها را برآورده کند انتخاب می‌شود. اگر وابستگی A بخواهد X نسخه >=1.2.0 و وابستگی B بخواهد X نسخه >=1.5.0 ، MVS نسخه‌ی 1.5.0 را انتخاب می‌کند — نه 1.8.0 یا جدیدترین نسخه.

چرا MVS؟ الگوریتم MVS توسط Russ Cox (یکی از طراحان Go) طراحی شده و سه مزیت کلیدی دارد: ۱) قطعیت — خروجی MVS فقط به فایل‌های go.mod بستگی دارد نه به زمان اجرا، ۲) سادگی — الگوریتم بدون نیاز به backtracking یا حل تعارضات پیچیده کار می‌کند، ۳) تکرارپذیری — build امروز دقیق همان build ماه آینده خواهد بود.
مقایسه با Composer: در PHP با Composer، composer update همیشه جدیدترین نسخه‌های سازگار را نصب می‌کند. این یعنی دو توسعه‌دهنده ممکن است با اجرای composer update در زمان‌های مختلف نسخه‌های متفاوتی دریافت کنند. اما در Go، go get با MVS همیشه حداقل نسخه را انتخاب می‌کند و نتایج قطعی و تکرارپذیر هستند. فایل go.sum نیز یک لایه‌ی اطمینان اضافه فراهم می‌کند.

ساختار داخلی go.sum

هر خط در فایل go.sum از سه بخش تشکیل شده:

خط اول (h1:...): هش SHA-256 از محتوای زیپ‌شده‌ی ماژول. این هش توسط go mod verify بررسی می‌شود تا مطمئن شود محتوای ماژول در cache با آنچه انتظار می‌رود مطابقت دارد.

خط دوم (/go.mod h1:...): هش SHA-256 از فایل go.mod خود ماژول. این حتی برای ماژول‌هایی که مستقیماً استفاده نمی‌شوند ولی در گراف وابستگی حضور دارند ذخیره می‌شود.

هشدار امنیتی: اگر هش‌های موجود در go.sum با محتوای دانلودشده مطابقت نداشته باشد، Go از build جلوگیری می‌کند. این مکانیزم از حمله‌ی supply chain جلوگیری می‌کند — سناریویی که یک ماژول مخرب جایگزین ماژول اصلی شود. هرگز go.sum را از .gitignore حذف نکنید و همیشه آن را در repository نگه دارید.

گروه GOPROXY و پروتکل Module Proxy

وقتی go get اجرا می‌شود، Go مستقیماً به GitHub متصل نمی‌شود. بلکه از یک زنجیره‌ی proxy استفاده می‌کند که توسط متغیر محیطی GOPROXY کنترل می‌شود:

proxy.golang.org یک سرور کش است که توسط تیم Go نگهداری می‌شود. وقتی ماژولی درخواست می‌شود، proxy ابتدا بررسی می‌کند که آیا نسخه‌ی درخواست‌شده قبلاً ذخیره شده یا خیر. اگر بله، مستقیماً از cache سرو می‌دهد. مزایای این پروکسی:

۱. سرعت: ماژول‌ها از CDN دانلود می‌شوند نه مستقیماً از GitHub.

۲. ثبات: وقتی نسخه‌ای از یک ماژول در proxy ذخیره شد، هرگز حذف یا تغییر نمی‌کند — حتی اگر نویسنده ماژول آن را از GitHub حذف کند ( immutability guarantee ).

۳. امنیت: proxy فایل go.sum را تولید و ذخیره می‌کند که می‌توان آن را با هش‌های محلی مقایسه کرد.

Semantic Versioning

Go ماژول‌ها از نسخه‌بندی معنایی (SemVer) با قالب vMAJOR.MINOR.PATCH پیروی می‌کنند. این قالب سه عدد دارد: عدد اصلی (MAJOR) برای تغییرات ناسازگار API، عدد فرعی (MINOR) برای قابلیت‌های جدید سازگار و عدد اصلاحی (PATCH) برای رفع باگ. در Go دو قانون حیاتی وجود دارد:

۱. نسخه‌های v0.x.x و v1.x.x: ماژول‌هایی که هنوز به v2 نرسیده‌اند، مسیر import معمولی دارند. اما از v2 به بعد، مسیر import باید شامل عدد نسخه‌ی اصلی باشد:

این قانون عجیب به‌نظر می‌رسد اما دلیل مهمی دارد: Go اجازه می‌دهد نسخه‌های مختلف یک ماژول همزمان در یک پروژه استفاده شوند. وقتی مسیر import متفاوت باشد، کامپایلر آن‌ها را پکیج‌های کاملاً مجزا در نظر می‌گیرد و تداخلی پیش نمی‌آید.

۲. +incompatible: اگر ماژولی قبل از سیستم ماژول‌ها (pre-module) ساخته شده باشد و نسخه‌ی v2+ داشته باشد اما مسیر import آن شامل شماره نسخه نباشد، Go آن را با پسوند +incompatible نشان می‌دهد. مثلاً v2.1.0+incompatible. این یعنی ماژول هنوز به سیستم ماژول‌ها مهاجرت نکرده و باید با احتیاط استفاده شود.

قانون طلایی نسخه‌بندی: اگر API ماژول خود را به‌صورت ناسازگار تغییر می‌دهید (مثلاً امضای تابعی را عوض می‌کنید یا فیلدی را حذف می‌کنید)، حتماً عدد MAJOR را افزایش دهید و مسیر import را به‌روز کنید. اگر فقط قابلیت جدید اضافه می‌کنید، عدد MINOR را بالا ببرید. اگر فقط باگ رفع می‌کنید، عدد PATCH را تغییر دهید.

دایرکتوری Vendor

دستور go mod vendor تمام وابستگی‌های پروژه را در دایرکتوری vendor/ در ریشه‌ی پروژه کپی می‌کند. این شبیه دایرکتوری vendor/ در Composer است اما با یک تفاوت مهم: در Go دایرکتوری vendor/ معمولاً در .gitignore قرار نمی‌گیرد و می‌توان آن را در repository نگه داشت.

چه زمانی از vendor استفاده کنیم؟ در محیط‌های تولیدی با الزامات امنیتی سخت‌گیرانه (مثل سازمان‌هایی که دسترسی اینترنتی ندارند)، در CI/CD برای تضمین تکرارپذیری کامل build، یا وقتی می‌خواهید مطمئن شوید وابستگی‌ها حتی اگر منبع اصلی حذف شد در دسترس هستند.

Go Workspaces

از Go 1.18 ویژگی جدیدی به‌نام Go Workspaces معرفی شده که کار روی چندین ماژول Go به‌صورت همزمان را ساده می‌کند. فایل go.work در ریشه‌ی فضای‌کاری قرار می‌گیرد و ماژول‌های محلی را فهرست می‌کند:

بدون go.work برای کار همزمان روی چند ماژول باید از replace در go.mod استفاده می‌کردید. اما go.work این کار را متمرکز و موقت می‌کند — فایل go.work نباید در repository کامیت شود و فقط برای توسعه‌ی محلی است.

نکته‌ی حرفه‌ای — راهنمای انتخاب بین replace، vendor و go.work: این سه ابزار برای سه سناریوی متفاوت طراحی شده‌اند و اشتباه گرفتن آن‌ها عامل رایج دردسر در تیم‌هاست. از replace فقط برای رفع موقت یک باگ در وابستگی خارجی استفاده کنید و حتماً قبل از commit آن را حذف کنید. از vendor برای تضمین تکرارپذیری build در محیط‌های ایزوله‌ی CI/CD بدون دسترسی اینترنت استفاده کنید. از go.work (Go 1.18+) برای توسعه‌ی هم‌زمان روی چند ماژول وابسته در همان ماشین استفاده کنید و هرگز آن را در repository قرار ندهید. این طبقه‌بندی ساده از ترکیب شدن این ابزارها و ایجاد وضعیت غیرقابل تکرار در build جلوگیری می‌کند.

پرچم جدید -tool برای go get باعث اضافه شدن دستورالعمل tool به ماژول فعلی می‌شود. همچنین الگوی متا tool به تمام ابزارهای ماژول فعلی ارجاع می‌دهد و می‌توان از آن برای ارتقای همزمان همه ابزارها استفاده کرد.

مطالعه موردی مهاجرت به tool directive در Uber

تیم مهندسی Uber در GopherCon 2024 تجربه مهاجرت بیش از ۲۰۰۰ ماژول Go به دستورالعمل جدید tool را به اشتراک گذاشت. قبل از این تغییر، هر ماژول یک فایل tools.go با import خالی داشت که نیاز به نگهداری داشت. این الگوی قدیمی چندین مشکل داشت: اولاً، فایل tools.go فقط برای اطمینان از نصب ابزارها در go.mod بود و هیچ استفاده منطقی نداشت. دوماً، وقتی یک ابزار آپدیت می‌شد، همه ماژول‌ها باید go mod tidy را اجرا می‌کردند. سوماً، مرور کد برای تشخیص ابزارهای واقعی از وابستگی‌های پروژه دشوار بود.

با مهاجرت به tool directive، آن‌ها توانستند بیش از ۶۰۰۰ خط کد بوییده را حذف کنند و فرآیند مدیریت ابزارها را متمرکزتر و قابل‌اتکاتر نمایند. دستورالعمل tool به‌طور صریح مشخص می‌کند که یک وابستگی فقط برای توسعه استفاده می‌شود و وارد باینری نهایی نمی‌شود. این جداکردن واضح بین وابستگی‌های اجرایی و توسعه‌ای، نگهداری پروژه را بسیار ساده‌تر کرد و خطر تصادفی اضافه‌شدن ابزار توسعه به وابستگی‌های production را از بین برد.

جریان تأیید Checksum در go.sum

یکی از مهم‌ترین مکانیزم‌های امنیتی در Go Modules سیستم تأیید checksum است که یکپارچگی وابستگی‌ها را تضمین می‌کند. وقتی دستور go get اجرا می‌شود، Go نه‌تنها وابستگی را دانلود می‌کند، بلکه هش SHA-256 آن را محاسبه کرده و با مقدار ثبت‌شده در go.sum مقایسه می‌کند. اگر هش‌ها مطابقت نداشته باشند، Go از ادامه‌ی build جلوگیری می‌کند و خطای امنیتی صادر می‌شود. این مکانیزم از حمله‌ی supply chain جلوگیری می‌کند — سناریویی که در آن یک وابستگی مخرب جایگزین نسخه‌ی اصلی شود. در PHP مشابه این مکانیزم وجود دارد (composer.lock) اما checksum database متمرکزی برای تأیید یکپارچگی وجود ندارد. نمودار زیر این جریان را به‌صورت گام‌به‌گام نشان می‌دهد.

سناریوهای عملیاتی

مدیریت وابستگی‌ها یکی از حساس‌ترین بخش‌های هر پروژه‌ی نرم‌افزاری است و اشتباه در آن می‌تواند به مشکلات جدی در محیط تولید منجر شود. در ادامه پنج سناریوی عملیاتی رایج را بررسی می‌کنیم که هر توسعه‌دهنده‌ای که از PHP به Go مهاجرت می‌کند باید با آن‌ها آشنا باشد. این سناریوها شامل افزودن وابستگی جدید، به‌روزرسانی ایمن وابستگی‌ها، استفاده از replace برای توسعه‌ی محلی، درک تفاوت MVS با Composer و تنظیم proxy خصوصی برای سازمان‌هاست. تسلط بر این سناریوها به شما کمک می‌کند پروژه‌های Go خود را با اطمینان و ایمنی مدیریت کنید.

  • افزودن وابستگی جدید: برای افزودن یک کتابخانه جدید به پروژه، کافی است آن را در کد import کنید و سپس go mod tidy اجرا نمایید. این دستور به‌طور خودکار وابستگی را شناسایی، دانلود و به go.mod و go.sum اضافه می‌کند. در PHP معادل این کار composer require vendor/package است. تفاوت مهم این است که در Go هیچ اسکریپت نصبی اجرا نمی‌شود — وابستگی فقط دانلود و کش می‌شود که از دیدگاه امنیتی بسیار ایمن‌تر است.
  • به‌روزرسانی ایمن وابستگی‌ها: برای به‌روزرسانی یک وابستگی خاص از go get github.com/foo/bar@v1.3.0 استفاده کنید. برای به‌روزرسانی تمام وابستگی‌ها به جدیدترین نسخه‌ی سازگار از go get -u ./... استفاده کنید. اما همیشه قبل از به‌روزرسانی، تست‌ها را اجرا کنید: go test ./.... در PHP دستور composer update مشابه است اما رفتار متفاوتی دارد — Composer بالاترین نسخه‌ی سازگار را انتخاب می‌کند در حالی که Go از MVS استفاده می‌کند و حداقل نسخه را انتخاب می‌نماید.
  • استفاده از replace برای توسعه‌ی محلی: وقتی روی دو ماژول Go به‌صورت همزمان کار می‌کنید، می‌توانید با replace github.com/username/mylib => ../mylib در فایل go.mod از نسخه‌ی محلی استفاده کنید. این امکان بدون نیاز به انتشار نسخه‌ی جدید، تغییرات را فوراً در پروژه‌ی اصلی تست می‌کند. به‌یاد داشته باشید که قبل از commit نهایی خط replace را حذف کنید. در PHP مشابه این کار با repositories در composer.json قابل انجام است اما پیچیده‌تر است.
  • درک تفاوت MVS با Composer در حل تعارض: در PHP اگر دو پکیج به نسخه‌های مختلف یک وابستگی نیاز داشته باشند، Composer ممکن است خطای تعارض بدهد. در Go این مشکل کمتر رخ می‌دهد چون MVS حداقل نسخه‌ی مشترک را انتخاب می‌کند. اما اگر واقعاً ناسازگاری وجود داشته باشد، Go نیز خطا می‌دهد. در این صورت می‌توانید با replace یک نسخه‌ی خاص را اجبار کنید یا کد یکی از وابستگی‌ها را برای سازگاری تغییر دهید.
  • تنظیم proxy خصوصی برای سازمان: در سازمان‌هایی که ماژول‌های خصوصی دارند، باید GOPRIVATE، GONOSUMCHECK و GONOSUMDB را تنظیم کنید تا ماژول‌های خصوصی به proxy و checksum database عمومی ارسال نشوند. همچنین می‌توانید از Athens به‌عنوان proxy سازمانی استفاده کنید: GOPROXY=https://athens.company.com,https://proxy.golang.org,direct. این تنظیمات در PHP معادلی ندارند چون Composer مستقیماً از Packagist دانلود می‌کند.
نکته‌ی حرفه‌ای: go mod tidy بهترین دوست شماست — همیشه بعد از افزودن یا حذف import آن را اجرا کنید تا go.mod و go.sum همگام بمانند. این دستور وابستگی‌های استفاده‌نشده را از go.mod حذف و وابستگی‌های استفاده‌شده ولی ثبت‌نشده را اضافه می‌کند. فراموش نکنید که go.sum باید همیشه در repository کامیت شود — برخلاف composer.lock که برخی پروژه‌ها آن را در .gitignore قرار می‌دهند. حذف go.sum معادل از دست دادن تاریخچه‌ی تأیید یکپارچگی وابستگی‌هاست و ممکن است باعث شود وابستگی‌های مخرب بدون تشخیص وارد پروژه شوند.
