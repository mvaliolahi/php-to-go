اجرای Query

چکیده: این بخش اجرای query در Go را پوشش می‌دهد: Query، Exec و prepared statement. الگوی placeholder و SQL injection prevention بررسی می‌شود. تفاوت با PDO::query در PHP مشخص می‌گردد.

پس از اتصال موفق به پایگاه‌داده، قدم بعدی اجرای کوئری‌ها و تعامل با داده‌هاست. برخلاف Laravel که با Query Builder یا Eloquent عملیات را ساده می‌کند، در Go مستقیماً با SQL خام کار می‌کنید.

8.3.1 انواع متدهای اجرا

پکیج database/sql سه متد اصلی برای اجرای کوئری ارائه می‌دهد:

db.Query() : برای خواندن چند سطر. خروجی *sql.Rows است که باید با Next() پیمایش و با Close() بسته شود.

db.QueryRow() : برای خواندن یک سطر. خروجی *sql.Row است. اگر سطری یافت نشود sql.ErrNoRows برگردانده می‌شود.

db.Exec() : برای عملیات نوشتاری (INSERT، UPDATE، DELETE). خروجی sql.Result است که شامل LastInsertId و RowsAffected است.

برای هرکدام از این متدها یک نسخه‌ی Context-aware نیز وجود دارد: db.QueryContext، db.QueryRowContext و db.ExecContext. الگوی توصیه‌شده در Go مدرن آن است که در کد تولیدی همیشه از نسخه‌های Context استفاده کنید و از نسخه‌های بدون Context صرفاً در اسکریپت‌های کوتاه یا نمونه‌های آموزشی بهره ببرید. دلیل این توصیه عملی است: نسخه‌های بدون Context هیچ مهلت زمانی (deadline) و مکانیزمی برای لغو ندارند؛ اگر دیتابیس در حال lock باشد یا شبکه قطع شود، Goroutine فراخواننده تا ابد مسدود می‌ماند و اتصال از Pool نشت می‌کند. در مقابل، QueryContext(ctx, ...) به‌محض لغو شدن ctx، اجرای کوئری را قطع می‌کند و اتصال را آزاد می‌سازد.

8.3.2 خواندن چند سطر با Query

نکات: rows.Close() را فراموش نکنید. بررسی خطا بعد از rows.Next() با rows.Err() ضروری است.

در این خط لوله هر مرحله وظیفه مشخصی دارد. مرحله‌ی Prepare کوئری SQL را فقط یک‌بار پارس و کامپایل می‌کند و شیء Statement را برمی‌گرداند. مرحله‌ی Query مقادیر پارامترها را جایگزین کرده و cursor نتایج را ایجاد می‌کند. حلقه‌ی Next/Scan سطر به سطر داده‌ها را می‌خواند و نوع‌های SQL را به نوع‌های Go تبدیل می‌کند.

در نهایت Close منابع اتصال و cursor را آزاد می‌کند. فراموش کردن هر کدام از این مراحل می‌تواند منجر به نشت اتصال، خطاهای پنهان یا کاهش عملکرد شود.

سناریوهای عملیاتی اجرای Query:

  • کوئری‌های تکراری با Prepared Statement: وقتی یک کوئری SQL را ده‌ها یا صدها بار با پارامترهای مختلف اجرا می‌کنید، استفاده از db.Prepare() به‌جای db.Query() مستقیم، عملکرد را به‌طور قابل‌توجهی افزایش می‌دهد. دلیل آن این است که کوئری فقط یک‌بار در سمت دیتابیس پارس و بهینه‌سازی می‌شود و در دفعات بعد فقط مقادیر جایگزین می‌شوند. در سیستم‌هایی با بار بالا، این بهینه‌سازی می‌تواند زمان پاسخ‌دهی را تا ۳۰ تا ۵۰ درصد کاهش دهد.
  • جستجوی تک‌سطری با QueryRow: زمانی که مطمئن هستید نتیجه فقط یک سطر است، مثلاً جستجوی کاربر با ID یکتا، از db.QueryRow() استفاده کنید. این متد از Query سبک‌تر است چون نیازی به حلقه‌ی Next() و بستن rows ندارد. فقط یادتان باشد که خطای sql.ErrNoRows را بررسی کنید تا اگر سطری یافت نشد، برنامه دچار رفتار غیرمنتظره نشود.
  • عملیات نوشتاری با Exec: برای INSERT، UPDATE و DELETE همیشه از db.Exec() استفاده کنید. این متد sql.Result برمی‌گرداند که شامل LastInsertId() برای کلید اصلی تولیدشده و RowsAffected() برای تعداد سطرهای تغییریافته است. هرگز از Query برای عملیات نوشتاری استفاده نکنید چون منابع اتصال بیهوده اشغال می‌شود.
  • مدیریت مقادیر NULL: ستون‌های nullable در دیتابیس اگر به متغیرهای معمولی Go اسکن شوند باعث خطای زمان اجرا می‌شوند. باید از انواع sql.NullString، sql.NullInt64 و مشابه آن‌ها استفاده کنید یا از الگوی pointer بهره ببرید. این یکی از تفاوت‌های اساسی با PHP است که در آن NULL به‌صورت خودکار مدیریت می‌شود.
نکته عملی: دو قانون طلایی برای کار با database/sql وجود دارد: اول، همیشه rows.Close() را بلافاصله بعد از دریافت rows با defer فراخوانی کنید تا حتی در صورت بروز خطا منابع آزاد شوند. دوم، برای کوئری‌هایی که بیش از یک‌بار اجرا می‌شوند حتماً از Prepared Statement استفاده کنید. بدون rows.Close() اتصالات دیتابیس نشت کرده و در نهایت connection pool پر می‌شود و برنامه قفل می‌شود. بدون Prepare هر کوئری از نو پارس و کامپایل می‌شود که سربار قابل‌توجهی روی دیتابیس ایجاد می‌کند.

8.3.3 خواندن یک سطر با QueryRow

متد db.QueryRow یک میان‌بر قراردادی برای کوئری‌هایی است که انتظار دارید حداکثر یک سطر برگردانند. تفاوت فلسفی با db.Query در این است که QueryRow خطا را به‌صورت تنبل (lazy) به تعویق می‌اندازد: خود فراخوانی هیچ خطایی برنمی‌گرداند و خطا تنها هنگام فراخوانی .Scan() آشکار می‌شود. این طراحی عمداً انتخاب شده تا بتوان زنجیره‌ی db.QueryRow(...).Scan(&...) را در یک خط نوشت؛ اما برنامه‌نویس باید بداند که اگر سطری یافت نشود، Scan مقدار sql.ErrNoRows را برمی‌گرداند که باید صراحتاً بررسی شود. در مقابل، db.Query خطا را فوراً اعلام می‌کند و نیاز به مدیریت rows.Close() و حلقه‌ی Next() دارد؛ بنابراین انتخاب بین این دو به این بستگی دارد که آیا انتظار دارید دقیقاً یک سطر برگردد (تساوی با QueryRow) یا صفر/چند سطر (Query).

8.3.4 عملیات نوشتاری با Exec

تله‌ی LastInsertId() در PostgreSQL: متد sql.Result.LastInsertId() وابسته به درایور است. در MySQL به‌درستی کار می‌کند، اما در PostgreSQL با درایور lib/pq همیشه خطای no LastInsertId available برمی‌گرداند. راه‌حل استاندارد برای PostgreSQL استفاده از عبارت RETURNING id در SQL و خواندن نتیجه با QueryRow به‌جای Exec است؛ این تفاوت یکی از تله‌های رایج برای مهاجران از MySQL به PostgreSQL است.

8.3.5 استفاده از Prepared Statements

از ابزارهای مهم امنیتی و بهینه‌سازی، Prepared Statements است. کوئری تنها یک‌بار پارس و کامپایل می‌شود و در دفعات بعد فقط مقادیر جایگزین می‌شوند:

اتصال و Stmt: در database/sql هر Prepared Statement به یک اتصال خاص متصل می‌شود. برای جلوگیری از مشکل در برنامه‌های با بار بالا از tx.Prepare() در داخل تراکنش استفاده کنید.
رفتار پنهان Prepare در database/sql: برخلاف PDO در PHP که prepared statement را به‌صورت شفاف روی اتصال جاری نگه می‌دارد، در Go پکیج database/sql برای هر Stmt فقط در صورتی PREPARE واقعی روی سرور اجرا می‌کند که همان اتصال دوباره استفاده شود؛ در غیر این‌صورت روی اتصال دیگری دوباره PREPARE می‌شود. به همین دلیل db.Prepare در تراکنش‌های کوتاه و پرتکرار می‌تواند سربار غیرمنتظره ایجاد کند. اگر کوئری فقط یک‌بار اجرا می‌شود، db.Query/Exec با پارامترهای bind کافی است — Prepare را برای مواردی نگه دارید که همان کوئری ده‌ها بار در یک نشست اجرا می‌شود.
