Migration

چکیده: این بخش migration پایگاه داده در Go را پوشش می‌دهد: golang-migrate، goose و الگوی embed SQL. تفاوت با Laravel migration و الگوی version-controlled بررسی می‌شود. کاربردهای production پوشش داده می‌گردد.

از بخش‌های کلیدی هر پروژه نرم‌افزاری که با دیتابیس کار می‌کند مدیریت ساختار دیتابیس و به‌روزرسانی‌های منظم آن است. اگر شما با Laravel کار کرده باشید به خوبی با مفهوم Migration و نسخه‌بندی دیتابیس آشنا هستید ابزاری که تغییرات ساختاری جدول‌ها و داده‌ها را به صورت کد نگهداری و اعمال می‌کند.

در لاراول migration ها به صورت کد PHP با کلاس‌ها و متدهای ساده تعریف می‌شوند و بسیاری از کارها مثل ساخت فیلد، جدول، تغییرات و rollback به صورت پیش‌فرض به کمک این متدها انجام می‌شود. Go بیشتر به اجرای مستقیم SQL و ابزارهای خط فرمان متکی است که انعطاف بیشتر اما نیازمند دقت بالاتر است.

در Go شما کنترل بیشتری روی فرآیند Migration دارید. در این فصل ابتدا به مفهوم Migration و اهمیت آن می‌پردازیم سپس بهترین روش‌ها و ابزارهای رایج در اکوسیستم Go را معرفی می‌کنیم و در نهایت با مثال‌های کاربردی نحوه استفاده از ابزار محبوب golang-migrate و goose را توضیح می‌دهیم.

8.1.1 چرایی استفاده

نسخه‌بندی ساختار دیتابیس: تغییرات در جداول، ستون‌ها، ایندکس‌ها و... به صورت کد ثبت می‌شود تا همیشه تاریخچه تغییرات مشخص باشد. بدون Migration، تغییرات دستی روی دیتابیس به‌زودی فراموش می‌شوند و محیط‌های مختلف ناهماهنگ می‌گردند.

همگام‌سازی تیم توسعه: اعضای تیم با اجرای Migration به راحتی ساختار دیتابیس را به‌روز می‌کنند.

محیط‌های مختلف: تضمین می‌شود که محیط‌های توسعه، تست و تولید همه یک ساختار دیتابیس یکسان دارند.

بازگشت به نسخه‌های قبلی: امکان rollback و اصلاح سریع اشتباهات ساختاری.

تولید خودکار در CI/CD: اجرای Migration به عنوان بخشی از pipeline استقرار.

8.1.2 ابزارهای رایج

golang-migrate : ابزار پرکاربرد با پشتیبانی از چندین دیتابیس و منبع. از شماره‌گذاری متوالی استفاده می‌کند.

goose : از هر دو فرمت SQL و Go پشتیبانی می‌کند.

atlas : ابزاری جدیدتر با رویکرد اعلامی (declarative).

کدام ابزار را انتخاب کنیم؟ برای پروژه‌های جدید golang-migrate پیشنهاد می‌شود. اگر نیاز به منطق پیچیده دارید goose گزینه‌ی بهتری است. برای پروژه‌های بزرگ‌تر atlas قابل‌توجه است.

8.1.7 مدیریت نسخه Migration

یکی از چالش‌های مهم در کار تیمی مدیریت نسخه‌های Migration است. در golang-migrate شماره‌گذاری متوالی است و اگر دو توسعه‌دهنده همزمان Migration جدیدی با شماره‌ی یکسان ایجاد کنند تداخل پیش می‌آید. راه‌حل‌ها: قفل دیتابیس (advisory lock)، اجرای Migration در CI/CD، و هماهنگی تیمی.

وضعیت Dirty: اگر Migration‌ای در حین اجرا با خطا مواجه شود دیتابیس وارد حالت dirty می‌شود. برای رفع مشکل ابتدا علت خطا را برطرف کنید و سپس با migrate force VERSION وضعیت dirty را پاک کنید. هرگز بدون رفع علت اصلی خطا از force استفاده نکنید.

8.1.9 استفاده از goose

همچنین می‌توانید Migration با کد Go بنویسید:

نکته‌ی ساختاری: در golang-migrate ساختار داخلی migrate.Migrate شامل دو رابط source.Driver و database.Driver است. source.Driver مسئول خواندن فایل‌های Migration از منبع و database.Driver مسئول اجرای Migration روی دیتابیس است.
مقایسه ابزارهای Migration در Go و PHP: در Laravel از Phinx استفاده می‌شود که از کد PHP با Builder API بهره می‌برد. در Go ابزارهای مبتنی بر SQL خام مثل golang-migrate کنترل بیشتری می‌دهند. goose با پشتیبانی از Migration‌های Go یک حد واسط ارائه می‌دهد و atlas با رویکرد declarative فاصله‌ی بین Go و ORM های مدرن را کم می‌کند.

8.1.10 نکات مهم Migration

تفکیک Migration‌ها: هر تغییر بزرگ را در یک Migration جداگانه قرار دهید.

برنامه‌ریزی برای rollback: همیشه فایل .down.sql را بنویسید و تست کنید.

اجرای Migration در محیط CI/CD: تضمین می‌کند دیتابیس به‌روز است.

مدیریت تراکنش: برخی دستورات مثل ALTER TABLE در PostgreSQL نمی‌توانند در تراکنش اجرا شوند.

نگهداری در کنترل نسخه: فایل‌های Migration باید در گیت ذخیره شوند.

اجتناب از Migrationهای طولانی: Migration‌های کوچک و قابل فهم نگه دارید.

وقتی ساختار دیتابیس را تغییر می‌دهید، هرگز آن را به شکلی تغییر ندهید که کد موجود را بشکند. از مایگریشن‌های افزایشی استفاده کنید که سازگاری رو به عقب را تا زمان به‌روزرسانی همه‌ی کد حفظ کنند.

نکته‌ی حرفه‌ای: همیشه مایگریشن‌هایی بنویسید که هم رو به جلو و هم رو به عقب قابل اجرا باشند. در Go از ابزارهایی مثل golang-migrate یا goose استفاده کنید و هرگز فایل مایگریشنی را که قبلاً روی محیط تولید اعمال شده تغییر ندهید — به‌جای آن یک مایگریشن جدید بنویسید.

8.1.11 خط زمانی نسخه‌های Migration

خط زمانی نسخه‌های Migration نشان می‌دهد که دیتابیس چگونه از یک حالت خالی به ساختار نهایی می‌رسد. هر نسخه یک تغییر مشخص را اعمال می‌کند و فایل‌های .up.sql و .down.sql به ترتیب مسئول اعمال و بازگشت آن تغییر هستند.

وقتی دستور migrate up اجرا می‌شود، تمام نسخه‌هایی که هنوز اعمال نشده‌اند به ترتیب اجرا می‌شوند و شماره نسخه در جدول schema_migrations ثبت می‌گردد. وقتی دستور migrate down N اجرا می‌شود، N نسخه‌ی آخر به ترتیب معکوس بازگشت می‌خورند.

یکی از مهم‌ترین چالش‌ها در کار تیمی تداخل شماره‌گذاری است. اگر دو توسعه‌دهنده به‌طور همزمان Migration جدیدی با شماره‌ی یکسان بسازند، ابزار golang-migrate نمی‌داند کدام را اول اجرا کند.

راه‌حل‌های متعددی وجود دارد: استفاده از advisory lock روی دیتابیس برای جلوگیری از اجرای همزمان، اجرای Migration فقط در CI/CD pipeline تا یک نقطه‌ی کنترل واحد وجود داشته باشد، و استفاده از شماره‌گذاری مبتنی بر timestamp به‌جای شماره‌گذاری ترتیبی که احتمال تداخل را کاهش می‌دهد.

8.1.12 سناریوهای عملیاتی

  • جریان کاری توسعه با Migration: توسعه‌دهنده شاخه‌ی جدیدی در گیت می‌سازد، Migration جدید ایجاد می‌کند، تغییرات را روی دیتابیس محلی اعمال می‌کند (migrate up)، کد مربوطه را می‌نویسد، و در نهایت هر دو فایل Migration و کد برنامه را در Pull Request ارسال می‌کند. بررسی‌کننده باید فایل‌های .up.sql و .down.sql را با دقت بررسی کند.
  • یکپارچه‌سازی در CI/CD Pipeline: مرحله‌ای در pipeline استقرار اضافه کنید که قبل از deploy کد جدید، Migration‌ها را اعمال کند. این تضمین می‌کند که دیتابیس همیشه همگام با کد است. از پرچم migrate up استفاده کنید تا فقط نسخه‌های اعمال‌نشده اجرا شوند. در صورت خطا، deploy باید متوقف شود.
  • استراتژی‌های بازگشت (Rollback): همیشه قبل از اعمال Migration در محیط تولید، یک پشتیبان از دیتابیس بگیرید. اگر Migration با مشکل مواجه شد ابتدا علت خطا را بررسی کنید. اگر خطا در خود SQL است آن را اصلاح کنید و migrate force اجرا کنید. اگر تغییر ساختاری ناخواسته بوده از migrate down استفاده کنید. هرگز بدون تست rollback در محیط توسعه از آن در تولید استفاده نکنید.
  • Migration بدون توقف (Zero-Downtime) — الگوی Expand/Contract: تغییرات مخرب مثل حذف ستون را در سه مرحله اعمال کنید: ابتدا ستون جدید را اضافه کنید (expand) و کد را طوری بنویسید که هم ساختار قدیم و هم جدید را پشتیبانی کند. سپس کد را برای استفاده فقط از ساختار جدید به‌روز کنید. در نهایت ستون قدیمی را حذف کنید (contract). این الگو تضمین می‌کند که در هیچ لحظه‌ای سرویس قطع نمی‌شود.
تست دوجهتِ Migration قبل از ادغام: قاعده‌ی «Migration قابل بازگشت» را در ابتدای همین فصل بررسی کردیم — در اینجا فقط تأکید می‌کنیم که هر Migration جدید را در محیط محلی ابتدا up و بلافاصله down اجرا کنید تا از صحت هر دو جهت مطمئن شوید. این کار کم‌هزینه‌ترین لحظه‌ای است که می‌توانید نقص فایل .down.sql را کشف کنید؛ کشف همان نقص در محیط تولید بسیار پرخطر و زمان‌بر خواهد بود.
خلاصه‌ی نکات کلیدی:
  • golang-migrate با فایل SQL جدا
  • goose با annotation در فایل SQL
  • embed برای جاسازی migration در باینری
  • version-controlled schema تکامل‌پذیر
  • rollback با down migration
