ارسال موازی ایمیل‌ یا نوتیفیکیشن‌

معماری Worker Pool با اتصال کانال‌ها

یکی از مهم‌ترین الگوهای همزمانی در Go، الگوی Worker Pool است. این الگو به شما اجازه می‌دهد تعداد مشخصی goroutine برای پردازش موازی کارها ایجاد کنید و از طریق channel‌ها ورودی و خروجی آن‌ها را مدیریت کنید. برخلاف PHP که برای هر Worker نیاز به Process جداگانه دارید، در Go تمام Workerها درون یک Process با حافظه مشترک اجرا می‌شوند. ترکیب Worker Pool با Context برای لغو عملیات و WaitGroup برای انتظار روی اتمام تمام Workerها، یک سیستم مقیاس‌پذیر و امن ایجاد می‌کند.

در این معماری، Job Producer کارها را در jobs کانال قرار می‌دهد و هر Worker از کانال می‌خواند، پردازش می‌کند و نتیجه را در results کانال می‌نویسد. Result Collector نتایج را جمع‌آوری می‌کند. Context مسیر لغو فراهم می‌کند و WaitGroup تضمین می‌کند که تمام Workerها قبل از بسته شدن برنامه به پایان برسند. این الگو شبیه به سیستم Queue در Laravel است اما بدون نیاز به Redis یا RabbitMQ و با هزینه بسیار کمتر.

سناریوهای عملیاتی

در پروژه‌های واقعی، الگوهای همزمانی در سناریوهای متنوعی کاربرد دارند. هر سناریو نیازمند ترکیب متفاوتی از الگوهای Worker Pool، Rate Limiting، Context و Channel است. در ادامه رایج‌ترین سناریوهای عملیاتی را بررسی می‌کنیم که هر توسعه‌دهنده‌ای در پروژه‌های واقعی با آن‌ها روبه‌رو خواهد شد. این سناریوها نشان می‌دهند که چگونه مفاهیم تئوری این فصل در عمل پیاده‌سازی می‌شوند.

  • کلاینت API با محدودیت نرخ: وقتی با APIهای خارجی کار می‌کنید که محدودیت درخواست دارند (مثلاً ۱۰۰ درخواست در دقیقه)، باید از الگوی Rate-Limited Worker Pool استفاده کنید. یک ticker نرخ ارسال را کنترل می‌کند و Workerها فقط در صورت وجود token درخواست ارسال می‌کنند. در PHP این کار با Redis Throttle انجام می‌شود اما در Go با time.Ticker و channel بسیار ساده‌تر است.
  • پردازش موازی تصویر: وقتی کاربر چند تصویر آپلود می‌کند، هر تصویر باید تغییر اندازه، فشرده‌سازی و ذخیره شود. یک Worker Pool با تعداد Worker برابر تعداد هسته‌های CPU بهینه‌ترین عملکرد را دارد زیرا پردازش تصویر کار محاسباتی است. هر Worker یک تصویر را از jobs کانال می‌گیرد و نتیجه را در results کانال می‌فرستد.
  • ارسال دسته‌ای ایمیل: در سیستم‌های اطلاع‌رسانی که هزاران ایمیل باید ارسال شود، Worker Pool با buffered channel بهترین راه‌حل است. Producer ایمیل‌ها را در صف قرار می‌دهد و Workerها به صورت موازی ارسال می‌کنند. اگر سرور SMTP محدودیت داشته باشد، Rate Limiter نرخ ارسال را کنترل می‌کند و از مسدود شدن اتصال جلوگیری می‌کند.
  • خزش وب همزمان با محدودیت نرخ: در ابزارهای Web Scraping، باید چندین صفحه را همزمان دانلود کنید اما نرخ درخواست محدود باشد تا سرور مقصد مسدودتان نکند. ترکیب Worker Pool با time.Ticker و Context با timeout راه‌حل ایده‌آل است. هر Worker قبل از ارسال درخواست جدید منتظر token از ticker می‌ماند.
نکته درباره اندازه Worker Pool: تعداد Workerها باید متناسب با نوع کار باشد. برای CPU-bound مثل پردازش تصویر یا رمزنگاری، از runtime.NumCPU() استفاده کنید — تعداد بیشتر فقط باعث context switching اضافی می‌شود. اما برای I/O-bound مثل درخواست HTTP یا کوئری دیتابیس، می‌توانید تعداد بسیار بیشتری Worker داشته باشید (مثلاً ۱۰۰ یا بیشتر) زیرا هر Worker بیشتر وقتش منتظر پاسخ شبکه است و CPU اشغال نمی‌کند. یک الگوی رایج شروع با runtime.NumCPU() * 2 و تنظیم بر اساس نتایج بنچمارک است.
یادداشت: در سرورهای HTTP تولیدی، هرگز در Handler مستقیماً go func(){...} ننویسید بدون اینکه Context درخواست را به آن پاس بدهید. وقتی کاربر مرورگر را می‌بندد، r.Context() لغو می‌شود و اگر Goroutine پس‌زمینه آن را بررسی نکند، به‌جای توقف، منابع سرور را مصرف می‌کند و در نهایت نشت می‌دهد. الگوی امن: go func(ctx context.Context){ select { case <-ctx.Done(): return; case result := <-ch: ... } }(r.Context()). در PHP این مشکل رخ نمی‌دهد زیرا فرآیند PHP-FPM با تمام درخواست از بین می‌رود، اما در Go سرور طول‌عمر دارد و نشت‌ها تجمعی هستند.
