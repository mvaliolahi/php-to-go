استفاده از Redis

Redis یک data structure key-value سریع و درون حافظه‌ای است که در کشینگ، صف‌بندی پیام‌ها و ذخیره‌سازی داده‌های موقتی کاربرد دارد. در Go کتابخانه go-redis یکی از پرکاربردترین کلاینت‌های Redis است.

معماری اتصال و خط لوله دستورات Redis

درک معماری اتصال Redis در Go برای نوشتن برنامه‌های کارآمد و مقیاس‌پذیر ضروری است. کلاینت go-redis از یک Connection Pool داخلی استفاده می‌کند که چندین اتصال همزمان به سرور Redis برقرار می‌کند. هر درخواست از یک اتصال آزاد در استخر استفاده می‌کند و پس از اتمام آن را برمی‌گرداند. این مکانیزم در محیط‌های با بار بالا بسیار مهم است زیرا ایجاد و تخریب مکرر اتصال‌ها هزینه‌ی شبکه‌ی بالایی دارد. علاوه بر دستورات تک‌تکی، Pipeline امکان ارسال دسته‌ای چندین دستور در یک درخواست شبکه‌ای را فراهم می‌کند که تأخیر را به‌شدت کاهش می‌دهد.

سناریوهای عملیاتی

در سیستم‌های واقعی، Redis فراتر از یک کش ساده عمل می‌کند و نقش‌های متعددی در معماری نرم‌افزار ایفا می‌کند. شناخت الگوهای مختلف استفاده از Redis به شما کمک می‌کند راه‌حل‌های مقیاس‌پذیر و کارآمد طراحی کنید. هر الگوی استفاده مزایا و محدودیت‌های خاص خود را دارد و انتخاب الگوی مناسب به نیازهای عملیاتی و مشخصات بار سیستم بستگی دارد. در ادامه پنج سناریوی عملیاتی کلیدی بررسی می‌شوند که هر مهندس نرم‌افزار باید در ابزار خود داشته باشد.

  • کش کردن نتایج پرس‌وجوی دیتابیس: الگوی Cache-Aside رایج‌ترین روش کشینگ است. ابتدا کلید کش بررسی می‌شود، در صورت عدم وجود از دیتابیس خوانده و با TTL مشخص در کش ذخیره می‌شود. همیشه TTL تعیین کنید تا داده‌ی کهنه انباشته نشود و در صورت تغییر دیتابیس، کش به‌طور خودکار منقضی شود. در Go کلید کش را با فرمت entity:id نام‌گذاری کنید تا قابل پیش‌بینی باشد.
  • محدود کردن نرخ درخواست با پنجره‌ی لغزان: با ترکیب INCR و EXPIRE یک شمارنده‌ی ساده می‌سازید. وقتی شمارنده برابر ۱ شود زمان انقضا تنظیم می‌شود. اگر شمارنده از حد مجاز بیشتر شد درخواست رد می‌شود. برای پنجره‌ی لغزان دقیق‌تر از Sorted Set با امتیاز زمان‌برچسب استفاده کنید تا درخواست‌ها در هر بازه‌ی زمانی دقیقاً شمرده شوند.
  • قفل توزیع‌شده برای انتخاب رهبر: در سیستم‌های توزیع‌شده فقط یک نمونه باید وظیفه‌ی خاصی را انجام دهد. با SET NX EX قفل اتمیک به‌دست می‌آید. نمونه‌ای که بتواند کلید قفل را تنظیم کند رهبر می‌شود و TTL تضمین می‌کند اگر رهبر crash کند قفل خودبه‌خور آزاد شود. برای محیط‌های حساس از الگوریتم Redlock استفاده کنید.
  • اعلان بلادرنگ با Pub/Sub: برای ارسال پیام فوری به همه‌ی سرویس‌های فعال، Pub/Sub ایده‌آل است. سرویس منتشرکننده پیام را روی کانال ارسال می‌کند و همه‌ی مشترکان همزمان آن را دریافت می‌کنند. در Go از goroutine برای گوش دادن به کانال pubsub.Channel() استفاده کنید تا جریان اصلی مسدود نشود.
  • ذخیره‌سازی نشست با TTL: داده‌ی نشست کاربر را با SETEX و زمان انقضا ذخیره کنید. وقتی کاربر فعالیت کند TTL تمدید می‌شود. پس از انقضای خودکار نشست حذف می‌شود بدون نیاز به پاکسازی دستی. این روش بسیار کارآمدتر از ذخیره‌ی نشست در دیتابیس رابطه‌ای است و مقیاس‌پذیری بهتری دارد.
نکته‌ی مهم: همیشه روی کلیدهای کش TTL تعیین کنید و برای قفل توزیع‌شده حتماً از SET NX EX اتمیک استفاده کنید. بدون TTL داده‌ی کهنه و بلااستفاده برای همیشه در Redis باقی می‌ماند و حافظه‌ی سرور به‌تدریج پر می‌شود. ترکیب SET NX و EX در یک دستور اتمیک تضمین می‌کند که هیچ شرایط مسابقه‌ای رخ نمی‌دهد — هرگز این دو عمل را به‌صورت جداگانه فراخوانی نکنید.
قانون طلایی: هرگز کلید کش بدون TTL نسازید و هرگز قفل توزیع‌شده بدون TTL نگیرید. داده‌ی بدون انقضا معادل نشت حافظه‌ی Redis است و در محیط عملیاتی فاجعه‌بار خواهد بود.
