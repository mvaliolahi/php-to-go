جنریک‌ها

چکیده: جنریک‌های Go (از 1.18) تعادل بین انعطاف‌پذیری و سادگی را جستجو می‌کنند. این بخش type constraints، comparable، انواع و توابع جنریک و زمان عدم استفاده را پوشش می‌دهد. تصمیم بین جنریک و واسط با مثال‌های عملی بررسی می‌شود.

از نسخه 1.18 به بعد Go قابلیت تعریف جنریک را دارد که روی انواع مختلف داده قابل استفاده‌اند. این قابلیت اجازه می‌دهد توابع، متدها و ساختارها به‌صورت جنریک نوشته شوند تا روی انواع مختلف داده بدون تکرار کد کار کنند.

مسیر رسیدن به این ویژگی شایان توجه است: Go برای بیش از یک دهه بدون generics زندگی کرد و این نبود عمدی بود. تیم زبان از سال ۲۰۱۰ طرح‌های متعددی (از Type Functions تا Contracts) را ارزیابی کرد و هر بار زمانی که پیچیدگی طرح، با فلسفه‌ی سادگی Go در تضاد قرار می‌گرفت، آن را رد می‌کرد. در نهایت طراحی نهایی type parameters با محدودیت‌های مبتنی بر type set در سال ۲۰۲۱ منتشر شد؛ طرحی که هم type safety کامل در زمان کامپایل ارائه می‌کرد و هم سینتکس را به حداقل ممکن نگه می‌داشت. این تأخیر ده‌ساله بازتاب قانون نانوشته‌ی Go است: «Don't ship it until it's right» — تا زمانی که درست نشده، منتشر نکنید. در نتیجه، generics در Go از روز اول با کتابخانه‌ی استاندارد هماهنگ است و با مدل GCshape stenciling به‌گونه‌ای پیاده‌سازی شده که هزینه‌ی اجرایی را به حداقل برساند.

T یک Type Parameter است که در زمان کامپایل با نوع واقعی جایگزین می‌شود. محدودیت any یعنی می‌تواند هر نوعی باشد. در نتیجه تابع Map می‌تواند روی []int، []string یا هر نوع دیگری اعمال شود.

در PHP تا نسخه‌های اخیر فقط می‌شد از Doc Block ها یا Type Hinting محدود استفاده کرد. از PHP 8.1 به بعد مفهومی شبیه جنریک‌ها اضافه شده ولی همچنان در سطح زبان به‌اندازه‌ی Go سخت‌گیر و ایمن نیست. در Go همه‌چیز در زمان کامپایل بررسی می‌شود و هیچ هزینه‌ی اضافی در زمان اجرا ندارد.

به همین دلیل جنریک‌های Go هم ایمن‌تر و هم سریع‌تر هستند.

2.6.1 Type Constraints

جنریک‌ها در Go قرار نیست Go را به یک زبان برنامه‌نویسی تابعی تبدیل کنند. آن‌ها راهی برای بیان نوع‌ها و توابعی هستند که روی انواع مختلف کار می‌کنند، در حالی که تأکید Go بر وضوح و سادگی را حفظ می‌کنند.

ساختار داخلی جنریک‌ها در Go — GCshape Stenciling: کامپایلر Go برای پیاده‌سازی جنریک‌ها از روشی ترکیبی به نام GCshape Stenciling استفاده می‌کند. این روش ترکیبی از دو رویکرد اصلی است:

۱. Stenciling (Monomorphization): برای هر «شکل GC» متفاوت، یک نسخه‌ی مجزا از کد تولید می‌شود. شکل GC به نوع ساختار حافظه اشاره دارد — مثلاً همه‌ی انواع pointer‌ها یک شکل GC دارند و همه‌ی structهای با اندازه‌ی یکسان نیز یک شکل. این روش سرعت اجرای بالایی دارد اما ممکن است حجم باینری افزایش یابد.

۲. Dictionaries: برای انواعی که شکل GC یکسانی دارند، از یک جدول دیکشنری در زمان اجرا استفاده می‌شود که اطلاعات اختصاصی هر نوع (مثل اندازه و عملیات‌ها) را نگه می‌دارد. این روش حافظه‌ی کمتری مصرف می‌کند اما کمی overhead دارد.

برخلاف C++ که از Monomorphization کامل استفاده می‌کند (یک نسخه کد برای هر نوع) و Java که از Type Erasure استفاده می‌کند (یک نسخه کد با cast در زمان اجرا)، Go راه میانه‌ای را طی کرده تا تعادل بین سرعت و حجم باینری برقرار شود.
جنریک‌ها در Go در مقابل Type Hinting در PHP:

Go: بررسی نوع در زمان کامپایل. هیچ هزینه‌ی اضافی در زمان اجرا (به‌جز overhead جزئی dictionary). کد ایمن و بهینه. مثلاً تابع Sum[int] و Sum[float64] هرکدام نسخه‌ی اختصاصی خود را دارند.

PHP (Type Hints / Generics): PHP هنوز جنریک واقعی ندارد. Type Hinting فقط در سطح تابع و پارامتر کار می‌کند. DocBlock Generics (مثل @param iterable<int>) فقط مستندسازی هستند و توسط کامپایلر بررسی نمی‌شوند. PHP 8.1 Enum و PHP 8.2 Readonly Class کمی از فاصله را کم کرده‌اند اما همچنان جای راه دارد.

مقایسه‌ی عملی: در Go اگر بنویسید Max([]int{1,2}, []string{"a","b"}) خطای کامپایل دریافت می‌کنید. در PHP تابع max([1,2], ["a","b"]) بدون خطا اجرا می‌شود اما نتیجه‌ی غیرمنتظره‌ای دارد.

جنریک‌ها ابزار قدرتمندی هستند اما همیشه بهترین راه‌حل نیستند. در موارد زیر بهتر است از روش‌های ساده‌تر استفاده کنید:

وقتی فقط یک یا دو نوع نیاز دارید: اگر فقط int و string را پشتیبانی می‌کنید، دو تابع ساده بنویسید نه یک تابع جنریک.

وقتی interface کافی است: اگر فقط چند متد مشترک نیاز دارید، واسط ساده‌تر و قابل فهم‌تر از جنریک است. مخصوصاً وقتی رفتار متفاوتی برای انواع مختلف نمی‌خواهید.

وقتی خوانایی کاهش می‌یابد: اگر امضای تابع با چندین type parameter و constraint پیچیده می‌شود، بهتر است کد را ساده‌تر بنویسید.

وقتی performance بهبود واقعی ندارد: جنریک‌ها در Go هزینه‌ی اجرایی ندارند اما اگر interface هم همان عملکرد را بدهد، سادگی interface ارجح است.

قانون تجربی: جنریک‌ها وقتی ارزش دارند که (۱) الگوریتم یکسانی برای چندین نوع تکرار شود، (۲) type safety در زمان کامپایل مهم باشد، (۳) استفاده از interface باعث cast یا reflection شود. در غیر این صورت، سادگی را ترجیح دهید.

2.6.8 محدودیت comparable: عمق‌تر ببینیم

محدودیت comparable در Go اجازه‌ی استفاده از عملگرهای == و != روی نوع پارامتر را می‌دهد.

این محدودیت به‌طور خودکار توسط کامپایلر برای هر نوعی که قابل مقایسه باشد برآورده می‌شود — شامل اعداد، رشته‌ها، بولی‌ها، اشاره‌گرها، آرایه‌ها با عناصر قابل مقایسه، و struct هایی که همه‌ی فیلدهایشان قابل مقایسه باشند. اما slice، map و function قابل مقایسه نیستند. دلیل این استثنا مهم است: slice و map از نظر معنایی «هویت محتوایی» دارند نه «هویت مرجعی»، و مقایسه‌ی دو slice با محتوای یکسان می‌توانست هم true و هم false معنا بدهد. طراحان Go ترجیح دادند چنین مقایسه‌ای را در سطح زبان غیرممکن کنند تا به جای ابهام، توسعه‌دهنده را وادار به استفاده از توابع صریحی چون slices.Equal یا reflect.DeepEqual کنند. این انتخاب بازتاب فلسفه‌ی کلی Go است: یک راه درست به‌جای چند راه مبهم.

از Go 1.20 به بعد، comparable حتی برای انواعی که شامل فیلدهای غیر قابل مقایسه‌ی (slice یا map) به‌صورت اشاره‌گر هستند نیز به‌صورت satisfiable در نظر گرفته می‌شود؛ یعنی کامپایلر تخصصی‌تر شده و تشخیص می‌دهد که یک struct که حاوی slice نیست اما حاوی اشاره‌گر به slice است، در سطح خود همچنان قابل مقایسه است. این تغییر، کاربرد generic‌ها را در عمل گسترش داد و انواع پیچیده‌تر را نیز پوشش داد.

نکته‌ی عملی: اگر می‌خواهید تابعی بنویسید که هم از == و هم از عملگرهای مرتب‌سازی (<, >) استفاده کند، comparable کافی نیست — باید از constraints.Ordered استفاده کنید. comparable فقط عملگرهای تساوی را فراهم می‌کند نه مرتب‌سازی را. توجه داشته باشید که از Go 1.21 به بعد، بسته‌ی استاندارد cmp با نوع cmp.Ordered به‌عنوان جایگزین رسمی برای constraints.Ordered (که در golang.org/x/exp بود) معرفی شد. توابع کاربردی چون cmp.Compare و cmp.Or نیز در همین بسته قرار دارند و در کد جدید توصیه می‌شوند.

2.6.9 توابع، انواع و متدهای جنریک

جنریک‌ها در Go سه شکل اصلی دارند: توابع جنریک، انواع جنریک، و متدهای روی انواع جنریک. هرکدام کاربرد خاصی دارند و درک تفاوت آن‌ها برای استفاده‌ی مؤثر ضروری است.

2.6.10 چه زمانی از جنریک استفاده نکنیم؟ عمق‌تر

جنریک‌ها ابزار قدرتمندی هستند اما مانند هر ابزار دیگری، استفاده‌ی نابجا از آن‌ها کد را پیچیده‌تر و نگهداری را دشوارتر می‌کند. در اینجا الگوهایی را بررسی می‌کنیم که بهتر است از جنریک استفاده نکنید و به‌جای آن از راه‌حل‌های ساده‌تر بهره ببرید. مفهوم واسط به‌عنوان جایگزین رایج، در بخش ۳.۶ به‌تفصیل بررسی شده است.

چک‌لیست تصمیم‌گیری: جنریک یا interface؟ از جنریک استفاده کنید وقتی: (۱) الگوریتم یکسانی برای چندین نوع تکرار می‌شود، (۲) type safety در زمان کامپایل مهم باشد، (۳) استفاده از interface باعث cast یا reflection شود، (۴) نیاز به بازگشت نوع خاص (نه interface{}) دارید. از interface استفاده کنید وقتی: (۱) فقط چند متد مشترک نیاز دارید، (۲) رفتار متفاوتی برای پیاده‌سازی‌های مختلف می‌خواهید، (۳) سادگی و خوانایی مهم‌تر از type safety عمومی است.

2.6.11 استنتاج نوع: قوانین و محدودیت‌ها

کامپایلر Go می‌تواند نوع پارامتر جنریک را در بسیاری از موارد از آرگومان‌ها استنتاج کند. اما همیشه این امکان وجود ندارد و در برخی موارد باید نوع را صراحتاً تعیین کنید. درک قوانین استنتاج به شما کمک می‌کند کدی تمیزتر بنویسید و از خطاهای عجیب کامپایلر جلوگیری کنید.

قوانین استنتاج نوع: کامپایلر Go از دو مکانیزم برای استنتاج استفاده کند: (۱) Type Unification — بررسی سازگاری نوع آرگومان با پارامتر، و (۲) Constraint Inference — استفاده از محدودیت‌ها برای حدس زدن نوع ناشناخته. وقتی هر دو مکانیزم کافی نباشند، باید نوع را صراحتاً تعیین کنید. این برخلاف PHP است که هیچ نوع‌دهی جنریک واقعی ندارد و همه‌چیز در زمان اجرا تعیین می‌شود.

2.6.14 مجموعه‌ی محدودیت‌های نوع: نگاهی بصری

یکی از مفاهیم کلیدی در جنریک‌های Go درک رابطه‌ی بین محدودیت‌های مختلف نوع است. هر محدودیت یک مجموعه از انواع را تعریف می‌کند و این مجموعه‌ها دارای رابطه‌ی زیرمجموعه‌ای هستند. محدودیت any بزرگ‌ترین مجموعه است و شامل همه‌ی انواع می‌شود. محدودیت comparable زیرمجموعه‌ای از any است که فقط انواع قابل مقایسه با == را شامل می‌شود.

محدودیت constraints.Ordered زیرمجموعه‌ی کوچک‌تری است که فقط انواع قابل مرتب‌سازی (<، >) را در بر می‌گیرد. محدودیت‌های سفارشی نیز می‌توانند هر زیرمجموعه‌ای را با ترکیب عملگر | و تعریف متدها ایجاد کنند.

در نمودار زیر این رابطه‌ی زیرمجموعه‌ای به‌صورت Venn diagram نمایش داده شده است. هر دایره نشان‌دهنده‌ی یک محدودیت است و دایره‌های درونی زیرمجموعه‌ی دایره‌های بیرونی هستند.

همچنین instantiation جنریک‌ها نشان داده شده: وقتی Max[int] را صدا می‌زنید، کامپایلر یک نسخه‌ی اختصاصی از تابع با T=int ایجاد می‌کند. این برخلاف PHP است که هیچ مکانیزم مشابهی ندارد و همه‌چیز در زمان اجرا با نوع mixed مدیریت می‌شود.

همان‌طور که نمودار ون نشان می‌دهد، محدودیت‌ها لایه‌لایه هستند: هر لایه‌ی درونی زیرمجموعه‌ی لایه‌ی بیرونی است و عملگرهای بیشتری فراهم می‌کند. وقتی تابع جنریک Max[T constraints.Ordered] را با نوع int نمونه‌سازی می‌کنید، کامپایلر بررسی می‌کند که int در مجموعه‌ی Ordered قرار دارد.

اگر سعی کنید Max[[]int] را صدا بزنید، خطای کامپایل دریافت می‌کنید چون []int نه در Ordered و نه حتی در comparable قرار دارد. این ایمنی در زمان کامپایل یکی از بزرگ‌ترین مزیت‌های Go نسبت به PHP است که هیچ مکانیزم مشابهی ندارد.

محدودیت‌های سفارشی قدرت واقعی جنریک‌های Go را نشان می‌دهند. با ترکیب عملگر | (اتحاد) و تعریف متدها، می‌توانید دقیقاً مشخص کنید تابع جنریک شما به چه نوع‌هایی نیاز دارد.

مثلاً محدودیت Stringer در نمودار بالا فقط انواع int، float64 و string را می‌پذیرد و همچنین الزام می‌کند که آن‌ها متد String() را پیاده‌سازی کنند.

این سطح از دقت در PHP غیرممکن است — نزدیک‌ترین معادل DocBlock‌هایی مثل @param int|float $value هستند که فقط مستندسازی هستند و توسط کامپایلر بررسی نمی‌شوند.

2.6.15 سناریوهای عملیاتی جنریک‌ها

  • ساختارهای داده‌ی جنریک (Stack، Queue، Set): رایج‌ترین کاربرد جنریک‌ها تعریف ساختارهای داده‌ی نوع‌ایمن است. یک Stack[T any] می‌تواند هم برای int و هم برای string و هم برای هر نوع سفارشی استفاده شود، بدون اینکه کد تکراری بنویسید یا از interface{} با type assertion استفاده کنید. کتابخانه‌هایی مثل golang.org/x/exp/slices و golang.org/x/exp/maps نمونه‌های عملی از این الگو هستند.
  • توابع filter/map/reduce جنریک: می‌توانید توابع کاربردی جنریک بنویسید که روی هر نوع slice کار کنند. مثلاً Filter[T any](s []T, fn func(T) bool) []T یا Map[T any, R any](s []T, fn func(T) R) []R. این توابع در PHP با array_filter و array_map موجود هستند اما هیچ ایمنی نوعی ندارند — در Go ایمنی نوع در زمان کامپایل تضمین می‌شود.
  • هلپرهای HTTP نوع‌ایمن با جنریک‌ها: می‌توانید handler جنریک بنویسید که درخواست HTTP را به نوع خاصی decode کند و پاسخ نوع‌ایمن برگرداند. مثلاً HandleJSON[Req any, Resp any](fn func(Req) (Resp, error)) این الگو از json.Marshal و json.Unmarshal با نوع‌های مشخص استفاده می‌کند و هم خوانایی و هم ایمنی کد را افزایش می‌دهد.
  • الگوی Repository جنریک برای دسترسی دیتابیس: به‌جای نوشتن repository جداگانه برای هر موجودیت، یک repository جنریک تعریف کنید: Repository[T any, ID comparable] با متدهای GetByID، List، Create و Delete. این الگو در PHP با Doctrine EntityRepository قابل مقایسه است اما بدون ایمنی نوع در زمان کامپایل.
  • توابع کمکی slice و map جنریک: بسته‌ی slices استاندارد Go توابع جنریک مثل slices.Contains، slices.Sort، slices.Index و maps.Keys را ارائه می‌دهد. این توابع جایگزین کدهای تکراری می‌شوند و با محدودیت comparable یا Ordered ایمنی نوع را تضمین می‌کنند.
نکته‌ی کلیدی — از جنریک‌ها بیش‌ازحد استفاده نکنید: در Go فلسفه‌ی سادگی همیشه اولویت دارد. با انواع مشخص و بتن شروع کنید و فقط وقتی الگوی یکسانی ۳ بار یا بیشتر با انواع مختلف تکرار شد، آن را به جنریک تبدیل کنید. جنریک‌ها ابزار قدرتمندی هستند اما پیچیدگی کد را افزایش می‌دهند: امضاهای طولانی‌تر، خطاهای کامپایل مبهم‌تر، و کد کمتر خوانا. اگر interface ساده نیازتان را برآورده می‌کند (بدون نیاز به type assertion یا reflection)، از آن استفاده کنید. قانون تجربی: «سه بار تکرار، بعد جنریک».
