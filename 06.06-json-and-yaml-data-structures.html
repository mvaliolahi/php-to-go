ساختارهای داده‌ای JSON و YAML

چکیده: این بخش serialize و deserialize JSON و YAML در Go را پوشش می‌دهد: struct tags، custom marshaler و handling پیشرفته. تفاوت با json_encode/json_decode در PHP و مدیریت type بررسی می‌شود. الگوهای tagged struct و omitEmpty توضیح داده می‌شود.

در دنیای مدرن نرم‌افزار، تبادل داده بین سرویس‌ها و پیکربندی برنامه‌ها عمدتاً با فرمت‌های JSON و YAML انجام می‌شود. در PHP کار با این فرمت‌ها بسیار ساده است: json_decode() و json_encode() برای JSON و افزونه‌های YAML در دسترس هستند.

در Go اما رویکرد متفاوتی وجود دارد: تبدیل داده‌ها به و از struct‌ها با استفاده از struct tag ها.

این رویکرد ابتدا ممکن است پیچیده به نظر برسد اما مزیت‌های بزرگی دارد: نوع‌داری ایستا، عملکرد بالا و امنیت بیشتر.

6.6.1 کار با JSON

ساختار encoding/json برای تبدیل بین JSON و struct بسیار مفید است. برخلاف PHP که json_decode() یک آرایه یا شیء پویا برمی‌گرداند، در Go داده‌ها به یک struct با نوع مشخص نگاشت می‌شوند.

ساختارهای داده، داده‌هایشان را آشکار می‌کنند و توابع معناداری ندارند. اشیاء توابع را آشکار می‌کنند و داده‌هایشان را پنهان می‌سازند. برنامه‌نویسان خوب می‌دانند کِی از کدام استفاده کنند.

6.6.3 کار با YAML

YAML ساختاری خواناتر از JSON دارد و در پروژه‌های DevOps یا پیکربندی بسیار محبوب است. برخلاف JSON که پکیج داخلی دارد، YAML در Go از پکیج خارجی استفاده می‌شود:

الگوی کار با YAML مشابه JSON است: تعریف struct با tag مناسب، استفاده از Unmarshal برای خواندن و Marshal برای نوشتن. تنها تفاوت استفاده از `yaml:"key"` به‌جای `json:"key"` و ایمپورت پکیج yaml.v3 است.

نکته: در PHP تابع yaml_parse() نیاز به نصب افزونه دارد و در بسیاری از هاست‌ها موجود نیست. در Go کافیست یک پکیج خارجی اضافه کنید (go get) و همه چیز در باینری نهایی گنجانده می‌شود.

6.6.4 عملکرد داخلی encoding/json: Reflection مبتنی بر بازتاب

پکیج encoding/json از بسته‌ی reflect برای بررسی فیلدهای struct در زمان اجرا استفاده می‌کند. وقتی json.Marshal() فراخوانی می‌شود:

  1. نوع مقدار ورودی با reflect بررسی می‌شود
  2. اگر struct باشد، exported پیمایش می‌شوند
  3. struct tag‌های `json:"..."` خوانده می‌شوند تا نام کلید JSON و گزینه‌های اضافی مشخص شوند
  4. مقادیر فیلدها یکی‌یکی به JSON تبدیل می‌شوند
هزینه‌ی Reflection: استفاده از reflect در زمان اجرا هزینه‌ای دارد و کندتر از کد دستی است. برای برنامه‌های معمولی این هزینه ناچیز است، اما در hot paths که میلیون‌ها بار JSON تولید/مصرف می‌شود، ابزارهایی مثل easyjson یا sonic کد مارشالینگ را در زمان کامپایل تولید می‌کنند و سرعت چند برابری دارند.

6.6.12 بسته experimental encoding/json/v2 — Go 1.25

Go 1.25 یک پیاده‌سازی جدید و آزمایشی JSON را شامل می‌شود که با تنظیم متغیر محیطی GOEXPERIMENT=jsonv2 فعال می‌شود. این پیاده‌سازی شامل دو بسته جدید است:

  • encoding/json/v2: بازنگری عمده بسته encoding/json با عملکرد بهتر
  • encoding/json/jsontext: پردازش سطح‌پایین‌تر نحو JSON

پیاده‌سازی جدید در بسیاری از سناریوها عملکرد بسیار بهتری دارد. به‌طور کلی، عملکرد encoding در هر دو پیاده‌سازی برابر است، اما decoding در پیاده‌سازی جدید به‌طور قابل‌توجهی سریع‌تر است.

هر تصمیم طراحی یک مبادله است. هنر مهندسی نرم‌افزار دانستن این است که کدام مبادله‌ها ارزش انجام دارند و کدام‌ها نه. ساده‌ترین راه برای جلوگیری از مبادله، پرهیز از تصمیم‌گیری است — اما این خود بزرگ‌ترین مبادله است.

6.6.13 نگاشت نوع‌های Go به JSON در Marshal/Unmarshal

درک دقیق نگاشت نوع‌های Go به نوع‌های JSON برای جلوگیری از باگ‌های پنهان بسیار مهم است. برخی نگاشت‌ها مستقیم و ساده هستند مانند تبدیل string به رشته‌ی JSON یا bool به boolean، اما برخی دیگر نیاز به توجه ویژه دارند. مثلاً time.Time به رشته‌ی RFC3339 تبدیل می‌شود و []byte به رشته‌ی base64 تبدیل می‌شود.

همچنین فیلدهای unexported (که با حرف کوچک شروع می‌شوند) به‌طور کامل نادیده گرفته می‌شوند و هرگز در خروجی JSON ظاهر نمی‌شوند. این رفتار می‌تواند برای برنامه‌نویسان PHP که به دسترسی پویا به همه‌ی کلیدها عادت دارند، غافلگیرکننده باشد.

6.6.14 سناریوهای عملیاتی

در پروژه‌های واقعی، کار با JSON فراتر از تبدیل ساده‌ی struct به JSON است. سناریوهای متعددی وجود دارند که هر کدام نیازمند رویکرد و تکنیک خاصی هستند. آشنایی با این الگوها به شما کمک می‌کند در موقعیت‌های مختلف بهترین تصمیم را بگیرید و از خطاهای رایج جلوگیری کنید. در ادامه پنج سناریوی عملیاتی کلیدی بررسی می‌شوند که هر برنامه‌نویس Go باید با آن‌ها آشنا باشد.

  • مدیریت JSON درخواست/پاسخ API: در REST API معمولاً داده‌های ورودی را به struct تبدیل می‌کنید، اعتبارسنجی انجام می‌دهید و سپس پردازش می‌کنید. در پاسخ نیز struct نتیجه را به JSON تبدیل می‌کنید. استفاده از struct جداگانه برای درخواست و پاسخ بهترین روش است تا فیلدهای داخلی افشا نشوند.
  • به‌روزرسانی جزئی با map[string]any: وقتی API از PATCH پشتیبانی می‌کند و فقط برخی فیلدها ارسال می‌شوند، map[string]any به شما اجازه می‌دهد تشخیص دهید کدام فیلدها ارسال شده‌اند. فیلد غایب در map یعنی عدم تغییر، اما فیلد با مقدار null یعنی پاک کردن.
  • سفارشی‌سازی JSON با MarshalJSON/UnmarshalJSON: وقتی نیاز به فرمت خاص برای تاریخ، رمزنگاری فیلد یا خروجی شرطی دارید، پیاده‌سازی این دو متد کنترل کامل روی تبدیل به شما می‌دهد. از ترفند type Alias برای جلوگیری از حلقه‌ی بی‌نهایت استفاده کنید.
  • مدیریت ساختار ناشناخته با json.RawMessage: در سیستم‌های رویدادمحور که بار متفاوتی دارند، RawMessage اجازه می‌دهد بخشی از JSON را بدون رمزگشایی نگه دارید و بعداً بر اساس نوع رویداد، به struct مناسب تبدیل کنید.
  • جریان JSON با json.Decoder: برای فایل‌های بزرگ یا پاسخ‌های HTTP streaming، Decoder داده‌ها را توکن‌به‌توکن می‌خواند و فقط یک آبجکت در حافظه نگه می‌دارد. این روش مصرف حافظه را به‌شدت کاهش می‌دهد.
نکته‌ی مهم: همیشه از json:"-" برای حذف فیلدهای حساس (رمز عبور، توکن، کلید API) از خروجی JSON استفاده کنید. هرگز فقط به unexported بودن فیلد اکتفا نکنید — در آینده ممکن است متد دسترسی اضافه شود یا نام فیلد به‌اشتباه exported شود. json:"-" صریح و مطمئن است و حتی اگر فیلد exported باشد از خروجی JSON حذف می‌شود.
قانون طلایی: در Go هرگز بر نام فیلد struct برای کنترل خروجی JSON تکیه نکنید — همیشه از struct tag صریح استفاده کنید. json:"-" برای حذف، json:",omitempty" برای حذف شرطی، و json:"name" برای نام‌گذاری صریح.
خلاصه‌ی نکات کلیدی:
  • struct tags با `json:"field_name"`
  • json.Marshal و json.Unmarshal
  • omitempty برای حذف فیلد خالی
  • custom MarshalJSON/UnmarshalJSON برای کنترل کامل
  • yaml.v3 با struct tag مشابه JSON
