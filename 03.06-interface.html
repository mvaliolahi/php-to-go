Interface

چکیده: واسط در Go ضمنی است: نوعی که متدهای لازم را داشته باشد، خودکار واسط را پیاده می‌کند. این بخش تعریف واسط، type assertion، empty interface و کاربردهای عملی را پوشش می‌دهد. تفاوت با interface در PHP و الگوی accept interfaces, return structs بررسی می‌شود.
نکته: یکی از تفاوت‌های بنیادین interface در Go با PHP این است که در Go نیازی به اعلام صریح implements نیست. هر struct که متدهای مورد نیاز یک interface را پیاده‌سازی کند، به‌طور خودکار با آن interface سازگار تلقی می‌شود. این مفهوم را "Duck Typing ساختاریافته" می‌نامند.

در زبان‌های شی‌گرا مانند PHP مفهوم interface برای تعریف قرارداد رفتاری میان کلاس‌ها کاربرد دارد. Go نیز از این مفهوم پشتیبانی می‌کند اما با رویکردی بسیار ساده‌تر، پویا‌تر و بدون وابستگی مستقیم.

تعریف interface

پیاده‌سازی interface

نکته مهم در Go این است که نیازی به اعلام explicit وجود interface نیست. به عبارت دیگر اگر struct شما متدهای لازم را داشته باشد بدون هیچ کلمه کلیدی اضافی این interface را پیاده‌سازی می‌کند یعنی برخلاف PHP نیازی به استفاده از کلیدواژه‌ی implements نیست.

مقایسه با PHP :

از مزایای این رویکرد این است که dependency ها کاهش می‌یابند و coupling بین کدها کمتر می‌شود. پیاده‌سازی interface ها بسیار انعطاف‌پذیر و راحت است و نهایتا نوشتن Unit Test ساده‌تر می‌شود چون به راحتی می‌توان mock و stub ساخت.

یک اصل ساده کمک می‌کند: ماژول‌ها را از هم جدا کنید. اگر بین دو ماژول وابستگی ندارید، نمی‌توانید یکی را با تغییر دیگری بشکنید.

Andy Hunt & Dave Thomas نویسندگان و مهندسان نرم‌افزار | The Pragmatic Programmer

نکته‌ی حرفه‌ای: interfaceهای ضمنی Go نهایت مکانیزم جداسازی هستند. در PHP وقتی کلاسی implements Notifier می‌نویسد، وابستگی صریحی به آن interface ایجاد می‌شود — اگر نام interface یا امضای متد تغییر کند، همه‌ی پیاده‌سازی‌ها می‌شکنند. اما در Go مصرف‌کننده interface را تعریف می‌کند نه تولیدکننده. یعنی بسته‌ی notification اصلاً نمی‌داند بسته‌ی user وجود دارد. این عدم وابستگیِ یک‌طرفه یعنی می‌توانید پیاده‌سازی user را کاملاً بازنویسی کنید بدون اینکه حتی یک خط از بسته‌ی notification تغییر کند.
نکته‌ی حرفه‌ای — اصل «Consume, Don't Produce»: یک الگوی رایج اما اشتباه در برنامه‌نویسان تازه‌کار Go این است که در همان پکیجی که struct را تعریف می‌کنند، interface آن را هم می‌سازند. این کار فلسفه‌ی ضمنی‌بودن interface در Go را نقض می‌کند. قانون تجربی این است: «interface را همان‌طور تولید نکن که مصرف می‌کنی، بلکه همان‌طور تولید کن که نیاز داری». یعنی در پکیج notification واسط Notifier را تعریف کنید (چون مصرف‌کننده است)، اما در پکیج user هیچ واسطی تعریف نکنید. این الگو به Interface Segregation Principle در SOLID نزدیک‌تر است و وابستگی‌ها را حداقل می‌کند. خروجی‌های توابع همیشه struct باشد تا مصرف‌کننده به جزئیات کامل دسترسی داشته باشد، نه اینکه به یک interface محدود شود.

3.6.1 Type Assertion و Type Switch

اگر یک رابط فقط یک متد داشته باشد، احتمالاً نام‌گذاری خوبی شده. هرچه رابط بزرگ‌تر باشد، انتزاع ضعیف‌تر است. رابط‌هایی با متدهای زیاد نشانه طراحی ضعیف هستند — پیاده‌ساز را به جزئیات زیادی متصل می‌کنند و تست و mock کردن را سخت‌تر می‌کنند.

Rob Pike طراح‌ارشد زبان Go | Go Proverbs — GopherCon 2015

یکی از مهم‌ترین توانایی‌هایی که PHP به‌طور رسمی ندارد، Type Assertion است. در Go وقتی یک مقدار از نوع interface دارید، می‌توانید در زمان اجرا نوع واقعی زیرین آن را بررسی و استخراج کنید.

این قابلیت در بسیاری از الگوهای پیشرفته Go کاربرد دارد و درک آن برای برنامه‌نویسان PHP که با type-hinting و instanceof آشنا هستند بسیار طبیعی خواهد بود.

3.6.5 اصل "Accept Interfaces, Return Structs"

از مهم‌ترین اصول Idiomatic Go این است: توابع باید interface بپذیرند و struct برگردانند. این یعنی ورودی‌های تابع شما باید از نوع interface باشند تا هر پیاده‌سازی قابل‌قبول باشد، اما خروجی باید نوع struct باشد تا مصرف‌کننده دقیقاً بداند چه چیزی دریافت می‌کند.

این الگو به‌ویژه برای Dependency Injection و نوشتن تست واحد ارزشمند است. وقتی تابع شما interface بپذیرد، در تست می‌توانید به‌راحتی یک mock بسازید و نیازی به راه‌اندازی زیرساخت واقعی نخواهید داشت.

این به‌طور دقیق همان هدفی است که در PHP با تزریق وابستگی در constructor دنبال می‌کنید، اما در Go بسیار ساده‌تر و صریح‌تر پیاده‌سازی می‌شود.

نمودار زیر جزئیات ساختار iface و itab را به‌صورت بصری نشان می‌دهد — شامل روابط بین جدول متدها، اشاره‌گر داده و سه حالت ممکن برای nil بودن interface:

در نمودار بالا ساختار کامل یک interface غیرخالی (iface) را مشاهده می‌کنید. بخش itab حاوی سه بخش حیاتی است: inter که نوع interface را مشخص می‌کند (مثلاً io.Writer)، _type که نوع واقعی داده را نشان می‌دهد (مثلاً *bufio.Writer) و آرایه‌ی fun که اشاره‌گر به توابع پیاده‌سازی‌شده را نگه می‌دارد.

وقتی متدی مانند w.Write(p) فراخوانی می‌شود Go از itab.fun[0] برای یافتن آدرس تابع واقعی استفاده می‌کند و data را به‌عنوان receiver ارسال می‌کند.

این مکانیزم فقط یک سطح indirection اضافی نسبت به فراخوانی مستقیم متد دارد و به‌لطف کش itab عملاً هیچ هزینه‌ی عملکردی قابل‌توجهی ایجاد نمی‌کند.

سه حالت nil که در پایین نمودار نمایش داده شده‌اند از مهم‌ترین مفاهیم برای برنامه‌نویسان PHP هستند. حالت اول یک interface واقعاً nil است که هر دو فیلد آن nil هستند.

حالت دوم یعنی «nil با نوع مشخص» (typed nil) یکی از رایج‌ترین باگ‌های Go است: وقتی یک اشاره‌گر nil از نوع مشخص به interface اختصاص می‌یابد فیلد tab/itab مقدار غیر-nil می‌گیرد و بنابراین interface دیگر nil نیست حتی اگر مقدار داده‌ی آن nil باشد.

حالت سوم هم یک interface عادی با مقدار غیر-nil است. درک این سه حالت برای جلوگیری از باگ‌های ظریف در کد Go ضروری است.

سناریوهای عملیاتی Interface

  • تزریق وابستگی مبتنی بر interface: در PHP معمولاً از constructor injection با type-hint استفاده می‌کنید: public function __construct(MailerInterface $mailer). در Go همین الگو با interface پیاده‌سازی می‌شود: func NewService(m Mailer) *Service. تفاوت این است که در Go نیازی به ثبت صریح binding در container نیست — هر structی که متد Send() داشته باشد خودکار سازگار است. این سادگی باعث می‌شود dependency injection در Go بسیار سبک‌تر و مستقیم‌تر از Laravel یا Symfony باشد و نیازی به framework سنگین IoC نداشته باشد.
  • تست با پیاده‌سازی‌های mock: یکی از قدرتمندترین کاربردهای interface در Go سادگی ساختن mock برای تست است. برخلاف PHP که به کتابخانه‌هایی مثل Mockery نیاز دارد در Go فقط کافیست یک struct ساده بسازید که interface مورد نظر را پیاده‌سازی کند. مثلاً type MockMailer struct{ Sent bool } با متد Send() یک mock کامل است. این mock‌ها قابل‌ پیش‌بینی و قابل‌اشکال‌زدایی هستند و هیچ جادوی runtime ندارند.
  • معماری پلاگین: با تعریف interface‌های کوچک و مشخص می‌توانید سیستم‌های پلاگین‌پذیر بسازید. هر پلاگین فقط کافیست interface مشخصی را پیاده‌سازی کند و بدون تغییر در کد اصلی قابل بارگذاری است. مثلاً type Storage interface { Get(key string) ([]byte, error); Set(key string, val []byte) error } اجازه می‌دهد Redis, Memcached یا SQLite بدون تغییر در منطق اصلی جایگزین شوند. این الگو مشابه سیستم Service Provider در Laravel است اما بدون نیاز به registration صریح.
  • تفکیک interface — interface‌های کوچک متعدد: به‌جای یک interface بزرگ با ده متد الگوی Go این است که چند interface کوچک تک‌متدی یا دومتدی تعریف کنید و سپس آنها را ترکیب کنید. مثلاً به‌جای type Repository interface { Get(); Save(); Delete(); Find(); Count() } بهتر است type Getter interface { Get() } و type Saver interface { Save() } و type Deleter interface { Delete() } را جداگانه تعریف کنید. این رویکرد انعطاف‌پذیری بیشتری می‌دهد چون هر تابع فقط interface‌ای که واقعاً نیاز دارد را درخواست می‌کند و به اصل Interface Segregation Principle پایبند می‌ماند.
  • برگرداندن interface در برابر struct از توابع: اصل Idiomatic Go می‌گوید «interface بپذیرید struct برگردانید». یعنی ورودی توابع باید interface باشد اما خروجی باید نوع concrete باشد. برگرداندن interface از تابع مصرف‌کننده را محدود می‌کند چون فقط به متدهای interface دسترسی دارد نه متدهای اضافی struct. اما برگرداندن struct به مصرف‌کننده اجازه می‌دهد هم از متدهای interface استفاده کند و هم از متدهای اختصاصی struct بدون نیاز به type assertion.
اصل «accept interfaces, return structs» و تله‌ی typed nil: دو درس عملی که هر برنامه‌نویس Go باید یاد بگیرد: ۱) همیشه توابع شما باید interface بپذیرند تا انعطاف‌پذیر باشند اما struct برگردانند تا شفاف باشند. این یعنی مصرف‌کننده دقیقاً می‌داند چه چیزی دریافت می‌کند و می‌تواند از همه‌ی متدهای struct استفاده کند. ۲) برای بررسی nil بودن یک interface همیشه هر دو بخش (type و value) را بررسی کنید. اگر تابعی interface برمی‌گرداند و ممکن است nil باشد هرگز اشاره‌گر nil از نوع مشخص را مستقیماً برنگردانید — به‌جای آن return nil را بنویسید. همچنین اگر نیاز دارید مقدار زیرین interface را برای nil بررسی کنید از reflection استفاده کنید: if v := reflect.ValueOf(w); v.Kind() == reflect.Ptr && v.IsNil(). این دو اصل ساده اما حیاتی از دسته‌ای از باگ‌های ظریف جلوگیری می‌کنند.
