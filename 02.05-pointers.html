یادداشت: مفهوم pointer در Go بسیار ساده‌تر از C/C++ است. Go از pointer arithmetic پشتیبانی نمی‌کند و اشاره‌گرها فقط برای ارجاع و انتقال مرجع به کار می‌روند. برای توسعه‌دهندگان PHP که با reference passing آشنا هستند (&$var)، اشاره‌گرهای Go مفهومی مشابه اما امن‌تر ارائه می‌دهند.

اشاره‌گرها

یکی از مفاهیم کلیدی و نسبتاً پیشرفته در زبان Go مفهوم اشاره‌گر است. در حالی که در PHP همه چیز به صورت مرجع ولی اغلب به شکل ضمنی و غیرقابل کنترل رفتار می‌کند در Go اشاره‌گرها به‌صورت صریح و قابل مدیریت هستند. این ویژگی در نوشتن کدهای بهینه، کنترل حافظه و طراحی ساختارهای مؤثر کاربرد فراوانی دارد.

به‌طور ساده یک اشاره‌گر متغیری است که به جای نگه‌داشتن یک مقدار آدرس حافظه‌ی متغیر دیگری را در خود ذخیره می‌کند.

a& آدرس حافظه‌ی متغیر a را بازمی‌گرداند. p* مقدار موجود در آدرس ذخیره‌شده در p را می‌خواند یا تغییر می‌دهد.

می‌توان بدون کپی کردن مقادیر بزرگ به‌سادگی آدرس آن‌ها را به توابع فرستاد.

برخلاف PHP که پارامترها به صورت پیش‌فرض by-value هستند در Go برای تأثیر گذاشتن بر مقدار اصلی باید از اشاره‌گر استفاده شود.

با اشاره گر می‌توانید ساختارهای داده‌ای پیچیده مثل لیست پیوندی،‌ درخت و … ایجاد کنید.

توجه داشته باشید اشاره‌گرهایی که هنوز به آدرسی متصل نشده‌اند مقدار nil دارند:

value در برابر reference

از تفاوت‌های مهم Go و PHP که برنامه‌نویسان PHP مرتباً با آن دست‌وپنجه نرم می‌کنند، رفتار متفاوت انواع داده در انتساب و انتقال به توابع است. در PHP آرایه‌ها بر اساس Copy-on-Write عمل می‌کنند، اما در Go رفتار هر نوع داده‌ای متفاوت است و شناخت این تفاوت‌ها برای جلوگیری از باگ‌های ظریف ضروری است.

جدول مقایسه رفتار انواع داده:

Value Types: هنگام انتساب یا انتقال به تابع، یک کپی مستقل ایجاد می‌شود. تغییر کپی، اصلی را تغییر نمی‌دهد.
• انواع پایه: int, float64, bool, string
• struct و array با طول ثابت

Reference Types: هنگام انتساب، همان داده زیرین به‌اشتراک گذاشته می‌شود. تغییر یکی، دیگری را هم تغییر می‌دهد.
• slice, map, channel, pointer, function, interface
نکته حیاتی برای توسعه‌دهندگان PHP: در PHP آرایه‌ها با انتساب کپی می‌شوند ($b = $a یک کپی ایجاد می‌کند). اما در Go رفتار slice شبیه object در PHP است — انتساب باعث به‌اشتراک‌گذاری داده می‌شود. اگر نیاز به کپی واقعی slice دارید از copy() استفاده کنید.

اشاره‌گر در Receiver متدها

وقتی متدی روی struct تعریف می‌کنید، باید تصمیم بگیرید که receiver مقداری باشد یا اشاره‌گری. این تصمیم مستقیماً بر این مسئله تأثیر می‌گذارد که آیا متد می‌تواند struct اصلی را تغییر دهد یا فقط روی یک کپی کار می‌کند.

قاعده کلی در Go این است: اگر نیاز به تغییر دارید یا struct بزرگ است، از pointer receiver استفاده کنید. حتی اگر تغییری نیاز نباشد، برای سازگاری همه متدهای یک struct باید یا همگی مقداری یا همگی اشاره‌گری باشند. در عمل، استفاده از pointer receiver برای همه متدها رایج‌تر و ایمن‌تر است.

چه‌هنگام از اشاره‌گر استفاده کنیم؟

استفاده از اشاره‌گر در Go سودمند است اما نباید بیش‌ازحد به‌کار رود. این راهنما به شما کمک می‌کند تصمیم بگیرید:

  • وقتی باید مقدار اصلی تغییر کند: ارسال اشاره‌گر به تابع اجازه می‌دهد مستقیماً مقدار اصلی را ویرایش کنید.
  • وقتی داده بزرگ است: کپی کردن struct‌های حجیم (مثل بافرهای تصویر یا مستندات JSON) پرهزینه است. ارسال اشاره‌گر فقط ۸ بایت (یک آدرس حافظه) کپی می‌کند.
  • وقتی باید نشان دهید مقداری ممکن است نباشد: اشاره‌گر nil می‌تواند باشد و این روشی برای نشان دادن "مقدار موجود نیست" است (مثل NULL در دیتابیس PHP).
هشدار: نیازی به اشاره‌گر برای slice، map و channel نیست! این انواع ذاتاً مرجع‌دار هستند و ارسال آن‌ها به تابع بدون اشاره‌گر هم باعث به‌اشتراک‌گذاری داده می‌شود. استفاده از *[]int یا *map[string]int هم لازم نیست و هم کد را پیچیده‌تر می‌کند.

Go از نظر ایمنی حافظه بسیار محتاط عمل می‌کند. حتی اگر اشاره‌گری به متغیر محلی یک تابع برگردانید، کامپایلر Go به‌صورت خودکار تشخیص می‌دهد (از طریق Escape Analysis) که متغیر باید روی heap قرار گیرد تا پس از خروج از تابع همچنان معتبر بماند. این برخلاف C است که برگرداندن اشاره‌گر به متغیر محلی باعث رفتار تعریف‌نشده می‌شود.

Escape Analysis: چگونه Go تصمیم می‌گیرد چه چیزی روی Heap قرار گیرد

یک برنامه‌نویس کاربردی باید بداند چگونه با اشاره‌گرها کار کند و حافظه را مستقیماً مدیریت نماید. اگر اشاره‌گرها را نمی‌فهمید، نمی‌فهمید کامپیوترها چگونه کار می‌کنند.

Andy Hunt & Dave Thomas نویسندگان و مهندسان نرم‌افزار | The Pragmatic Programmer

نکته‌ی حرفه‌ای: درک Escape Analysis کلید انتخاب بین pointer receiver و value receiver است. اگر متد شما receiver را به interface تبدیل می‌کند (مثلاً fmt.Println(u) درون متد)، مقدار به heap فرار می‌کند و value receiver هزینه‌ی کپی اضافی دارد. در این حالت pointer receiver بهتر است چون فقط ۸ بایت کپی می‌شود. اما اگر struct کوچک است (زیر ۶۴ بایت) و درون متد فرار نمی‌کند، value receiver سریع‌تر است چون تخصیص heap را حذف می‌کند. از go build -gcflags="-m" برای مشاهده‌ی تصمیمات کامپایلر استفاده کنید.

کامپایلر Go تحلیل فرار را برای تعیین اینکه کدام متغیرها می‌توانند با اطمینان روی پشته به جای هیپ تخصیص داده شوند، انجام می‌دهد. تخصیص‌های پشته اساساً رایگان هستند، در حالی که تخصیص‌های هیپ به جمع‌آوری زباله نیاز دارند. درک تحلیل فرار به شما کمک می‌کند کدی بنویسید که تخصیص‌های هیپ را به حداقل برساند.

Rick Hudson و Austin Clements تیم توسعه کامپایلر Go

از مهم‌ترین بهینه‌سازی‌های کامپایلر Go، Escape Analysis است. این تحلیل تعیین می‌کند که آیا یک متغیر می‌تواند روی stack تخصیص یابد (سریع و خودکار آزاد می‌شود) یا باید روی heap قرار گیرد (نیاز به garbage collector برای آزادسازی).

قواعد اصلی Escape Analysis:

۱. متغیر روی stack می‌ماند اگر:
• فقط در همان تابع استفاده شود
• آدرس آن خارج از تابع منتشر نشود
• اندازه‌ی آن در زمان کامپایل مشخص باشد

۲. متغیر به heap escape می‌کند اگر:
• آدرس آن از تابع برگردانده شود (return &localVar)
• در closure ذخیره شود و closure از تابع فرار کند
• به عنوان آرگومان به interface{} ارسال شود (مثلاً fmt.Println)
• اندازه‌ی آن خیلی بزرگ باشد و روی stack جا نشود
• در زمان کامپایل اندازه‌ی آن مشخص نباشد (مثل slice با اندازه‌ی دینامیک)
نحوه‌ی بررسی Escape Analysis: با پرچم -gcflags="-m" می‌توانید گزارش Escape Analysis کامپایلر را ببینید: go build -gcflags="-m" ./.... این ابزار برای بهینه‌سازی کد بحرانی بسیار مفید است.
مقایسه‌ی مدیریت حافظه در Go و PHP:

Go: متغیرهای محلی روی stack تخصیص می‌یابند (بسیار سریع — فقط حرکت یک pointer). فقط متغیرهایی که «فرار» می‌کنند روی heap قرار می‌گیرند. Garbage Collector مبتنی بر mark-and-sweep بدون نیاز به reference counting. هیچ overhead زمان اجرا برای رهگیری ارجاع‌ها وجود ندارد.

PHP: هر مقدار در ساختار zval با reference counting ذخیره می‌شود. هر انتساب شمارنده‌ی ارجاع را افزایش می‌دهد و هر از بین رفتن متغیر آن را کاهش می‌دهد. وقتی شمارنده صفر شود حافظه آزاد می‌شود. Copy-on-Write نیز از همین مکانیزم استفاده می‌کند. این روش overhead بیشتری دارد اما برای dynamic typing ضروری است.

اشاره‌گر به Interface: یک تله‌ی رایج

برنامه‌نویسان PHP گاهی به‌اشتباه اشاره‌گر به interface ایجاد می‌کنند. در Go این کار تقریباً هرگز لازم نیست و نشان‌دهنده‌ی سوءتفاهم درباره‌ی نحوه‌ی کار interface است:

توضیح: interface در Go از قبل شامل یک اشاره‌گر به داده‌ی واقعی است. بنابراین *Interface عملاً یک اشاره‌گر به اشاره‌گر است و هم لازم نیست و هم کد را پیچیده‌تر می‌کند. به یاد داشته باشید: interface را مستقیم استفاده کنید، اشاره‌گر به آن نگیرید.

چرا Go حساب اشاره‌گر ندارد؟

یکی از تفاوت‌های اساسی Go با C/C++ عدم پشتیبانی از pointer arithmetic است. در C می‌نوشتید p++ تا اشاره‌گر را به عنصر بعدی آرایه منتقل کنید. Go این قابلیت را عمداً حذف کرده است چون دلیل اصلی بسیاری از آسیب‌پذیری‌های امنیتی (سرریز بافر، دسترسی غیرمجاز به حافظه) و باگ‌های ردیابی‌نشده است. به‌جای pointer arithmetic، Go از slice با اندیس‌گذاری ایمن استفاده می‌کند.

اشاره‌گر به اشاره‌گر: **int

گاهی نیاز دارید تابعی بنویسید که خود اشاره‌گر را تغییر دهد (مثلاً تخصیص حافظه‌ی جدید). در این حالت از اشاره‌گر به اشاره‌گر استفاده می‌کنید. این الگو در Go نادر است اما در کار با ساختارهای داده‌ی پیوندی (مثل لیست‌های پیوندی) ضروری است.

چه زمانی از **T استفاده کنیم؟ فقط وقتی تابعی نیاز دارد خود اشاره‌گر را تغییر دهد (مثلاً مقداردهی اولیه یا تخصیص مجدد). اگر فقط می‌خواهید مقدار مورد اشاره را تغییر دهید، *T کافی است. **T در کد معمولی بسیار نادر است و وجود آن معمولاً نشان‌دهنده‌ی نیاز به بازطراحی است.

ارسال struct بزرگ: اشاره‌گر در برابر مقدار

یکی از سؤالات رایج این است: «چه‌وقت باید از اشاره‌گر برای ارسال struct به تابع استفاده کنیم؟» پاسخ به اندازه‌ی struct و نیاز به تغییر بستگی دارد. برای struct‌های کوچک (تا حدود ۶۴ بایت)، ارسال مقداری معمولاً به‌دلیل بهینه‌سازی‌های کامپایلر سریع‌تر یا هم‌سرعت است. برای struct‌های بزرگ، ارسال اشاره‌گر فقط ۸ بایت کپی می‌کند.

اشتباهات رایج با اشاره‌گرها

برنامه‌نویسان PHP که تازه با اشاره‌گرها آشنا شده‌اند مرتکب اشتباهات رایجی می‌شوند. آگاهی از این اشتباهات به شما کمک می‌کند از آن‌ها اجتناب کنید.

خلاصه‌ی قوانین اشاره‌گر برای مهاجران PHP: در PHP از &$var برای ارسال مرجع استفاده می‌کردید. در Go این کار با اشاره‌گر انجام می‌شود اما فرق مهمی دارد: Go هرگز تبدیل خودکار بین مقدار و اشاره‌گر انجام نمی‌دهد. اگر می‌خواهید تابعی مقدار اصلی را تغییر دهد، باید صراحتاً از *Type استفاده کنید. این شفافیت نقطه‌ی قوت Go است نه ضعف آن.
نکته‌ی حرفه‌ای — nil predicate همیشه صریح: در PHP مقادیر falsy با if (!$x) بررسی می‌شوند، اما در Go اشاره‌گر nil به‌طور خودکار به false تبدیل نمی‌شود — باید صراحتاً if p == nil یا if p != nil بنویسید. فراموش کردن این بررسی قبل از *p شایع‌ترین علت panic: runtime error: invalid memory address در کد مهاجران PHP است. در توابعی که اشاره‌گر برمی‌گردانید (مثل FindUser) همیشه مقدار nil را به‌عنوان «یافت نشد» مستند کنید.

تابع new با عبارت مقداردهی — Go 1.26

در Go 1.26، تابع داخلی new که قبلاً فقط یک نوع را به عنوان عملوند می‌پذیرفت و یک اشاره‌گر به مقدار صفر آن نوع برمی‌گرداند، اکنون می‌تواند یک عبارت را به عنوان عملوند بپذیرد که مقدار اولیه متغیر را مشخص می‌کند. این ویژگی به‌خصوص هنگام کار با بسته‌های سریالی‌سازی مانند encoding/json یا Protocol Buffers که از اشاره‌گر برای نشان دادن مقادیر اختیاری استفاده می‌کنند، بسیار مفید است:

این تغییر موجب می‌شود که بتوانید فیلدهای اختیاری اشاره‌گری را در یک عبارت ساده پر کنید، بدون نیاز به تعریف متغیرهای موقت. رفتار new(T) بدون عبارت تغییری نکرده و همچنان اشاره‌گر به مقدار صفر T را برمی‌گرداند.

مطالعه موردی استفاده از new در بسته‌های سریالی‌سازی Uber

تیم Uber در ارائه GopherCon 2024 توضیح داد که چگونه در سیستم سریالی‌سازی داخلی خود از الگوی Optional Pointer به‌طور گسترده استفاده می‌کنند. این الگو زمانی کاربرد دارد که نیاز به تمایز بین «مقدار صفر» و «عدم وجود مقدار» باشد. مثلاً در API‌های gRPC، فیلد *int64 با مقدار nil به معنای «فیلد تنظیم نشده» است، ولی فیلد int64 با مقدار 0 می‌تواند به معنای «مقدار صفر واقعی» یا «عدم وجود مقدار» باشد. این ابهام در سیستم‌های توزیع‌شده باعث باگ‌های ظریف و سختی می‌شد.

با قابلیت جدید new() در Go 1.26، آن‌ها توانستند بیش از ۳۰۰۰ خط کد مربوط به متغیرهای موقت را حذف کنند و خوانایی کد به‌طور قابل‌توجهی افزایش یابد. قبلاً برای ایجاد یک اشاره‌گر به مقدار صفر، باید یک متغیر موقت تعریف می‌شد: v := 0; p := &v. حالا با p := new(int) همان نتیجه با یک خط کد تمیزتر به‌دست می‌آید. این تغییر به‌خصوص در API‌های gRPC که از فیلدهای اختیاری *int64 و *string استفاده می‌کنند، مؤثر بود و خوانایی و نگهداری کد را بهبود بخشید.

آشنایی عمیق با Stack، Heap و آناتومی اشاره‌گر

برای درک کامل اشاره‌گرها در Go، شناخت ساختار حافظه‌ی برنامه ضروری است. همان‌طور که در بخش Escape Analysis دیدید، کامپایلر Go هوشمندانه تصمیم می‌گیرد هر متغیر در Stack یا Heap قرار گیرد. نمودار زیر این تصمیم‌گیری و آناتومی اشاره‌گرها را به‌صورت یکپارچه نمایش می‌دهد — ناحیه‌ی Stack برای متغیرهای محلی (سریع و خودکار) و ناحیه‌ی Heap برای تخصیص‌های دینامیک با مدیریت Garbage Collector.

همان‌طور که در نمودار می‌بینید، متغیر x در تابع main روی Stack قرار می‌گیرد و اشاره‌گر p مستقیماً به همان آدرس اشاره می‌کند. اما وقتی تابع createPtr آدرس متغیر محلی c را برمی‌گرداند، Escape Analysis آن متغیر را به Heap منتقل می‌کند تا پس از پایان تابع معتبر بماند.

نکته‌ی مهم دیگر این است که slice‌ها در Go یک ساختار دو بخشی دارند: header شامل اشاره‌گر، طول و ظرفیت روی Stack قرار می‌گیرد، اما backing array همیشه روی Heap تخصیص می‌یابد. این طراحی هوشمندانه باعث می‌شود انتقال slice به توابع بسیار سبک باشد (فقط ۲۴ بایت کپی می‌شود) اما داده‌های واقعی مشترک بمانند.

سناریوهای عملیاتی اشاره‌گرها

  • ارسال struct بزرگ با اشاره‌گر در برابر مقدار: وقتی struct شما بزرگ است (مثلاً بیش از ۶۴ بایت یا شامل آرایه‌های طولانی)، ارسال با اشاره‌گر فقط ۸ بایت کپی می‌کند اما ارسال مقداری کل ساختار را کپی می‌کند. برای struct‌های کوچک مثل Point{X, Y float64} ارسال مقداری سریع‌تر یا هم‌سرعت است چون داده‌ی کمتری از cache نشت می‌کند. همیشه با benchmark تصمیم نهایی را بگیرید.
  • اشاره‌گری receiver برای متدهایی که وضعیت را تغییر می‌دهند: اگر متدی نیاز دارد فیلدهای struct را ویرایش کند (مثل Increment() روی Counter)، حتماً از pointer receiver استفاده کنید. حتی اگر متدی تغییری ایجاد نکند، برای سازگاری همه‌ی متدهای یک نوع باید یا همگی مقداری یا همگی اشاره‌گری باشند — ترجیحاً همگی اشاره‌گری.
  • جلوگیری از dangling pointers: برخلاف C، Go از dangling pointers جلوگیری می‌کند. اگر اشاره‌گری به متغیر محلی برگردانده شود، Escape Analysis آن را روی Heap قرار می‌دهد. اما مراقب باشید که اشاره‌گر به nil را dereference نکنید — همیشه قبل از *p بررسی p != nil انجام دهید.
  • بررسی Escape Analysis با go build -gcflags="-m": این پرچم پرکاربردترین ابزار بهینه‌سازی حافظه در Go است. خروجی آن نشان می‌دهد کدام متغیرها فرار می‌کنند و چرا. مثلاً "leak(&x): argument does not escape" یعنی بهینه است و "&x escapes to heap" یعنی نیاز به بازبینی دارد. از -gcflags="-m -m" برای جزئیات بیشتر استفاده کنید.
  • استفاده از new() برای تخصیص صریح Heap: تابع new(T) یک مقدار صفر از نوع T روی Heap تخصیص می‌دهد و اشاره‌گر آن را برمی‌گرداند. اما در عمل، کامپایلر ممکن است حتی با new متغیر را روی Stack نگه دارد اگر فرار نکند. تابع make نیز برای slice، map و channel استفاده می‌شود و همیشه روی Heap تخصیص می‌دهد.
نکته‌ی کلیدی — اولویت مقدار برای کوچک، اشاره‌گر برای بزرگ: در Go پیشنهاد می‌شود برای struct‌های کوچک (زیر ۶۴ بایت) از ارسال مقداری استفاده کنید چون cache locality بهتری دارد و overhead GC ایجاد نمی‌کند. اما برای struct‌های بزرگ یا وقتی نیاز به تغییر مقدار اصلی دارید، از اشاره‌گر استفاده کنید. Escape Analysis به کامپایلر کمک می‌کند تصمیمات هوشمندانه بگیرد: متغیرهایی که فرار نمی‌کنند روی Stack رایگان هستند و فقط متغیرهایی که واقعاً نیاز دارند روی Heap قرار می‌گیرند. بنابراین به جای نگرانی درباره‌ی جزئیات تخصیص، کدی تمیز و خوانا بنویسید و Escape Analysis را به کامپایلر بسپارید.
