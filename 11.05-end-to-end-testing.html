مقایسه با PHP: در Laravel با $this->get('/path') و $this->post('/path', $data) تست‌های HTTP می‌نویسید. Laravel به‌صورت خودکار درخواست را به برنامه ارسال کرده و پاسخ را برمی‌گرداند. در Go از httptest.Server برای ساخت سرور واقعی تست و از net/http برای ارسال درخواست استفاده می‌کنید. مفهوم مشابه است اما در Go کنترل بیشتری روی جزئیات HTTP دارید.

تست End-to-End

چکیده: این بخش E2E testing را پوشش می‌دهد: Playwright، Docker و test environment. الگوی isolated test و CI integration بررسی می‌شود. کاربردهای production-grade پوشش داده می‌گردد.

تست‌های End-to-End (E2E) بالاترین سطح هرم تست را تشکیل می‌دهند. برخلاف unit test که فقط یک تابع را بررسی می‌کند، E2E test کل جریان برنامه را از دریافت درخواست HTTP تا بازگرداندن پاسخ تست می‌کند. این شامل Middleware‌ها (معرفی‌شده در بخش ۷.۴)، routing، اعتبارسنجی، منطق کسب‌وکار و پاسخ نهایی است.

اگر سابقه کار با Laravel را دارید، احتمالاً با تست‌های Feature آشنا هستید. در Laravel متدهایی مثل $this->get()، $this->post() و $this->actingAs() به شما اجازه می‌دهند درخواست‌های HTTP واقعی به برنامه ارسال کنید. در Go با httptest.Server همان کار را انجام می‌دهیم.

نکته درباره نسبت تست‌ها در هرم: قانون تجربی پایدار این است: ~۷۰٪ Unit Test، ~۲۰٪ Integration، ~۱۰٪ E2E. در PHP/Laravel تمایل به نوشتن زیاد Feature Test وجود دارد چون ابزار آن ($this->get() + RefreshDatabase) ارزان است، اما در Go به‌دلیل سرعت بالای Unit Test و قابلیت فراخوانی مستقیم هندلر، این نسبت بهتر رعایت می‌شود. اگر بیش از ۳۰٪ تست‌های شما E2E هستند، نشانه‌ای است که منطق کسب‌وکار به‌درستی از لایه HTTP جدا نشده — باید آن را به سرویس‌های مستقل منتقل کنید و با Unit Test بپوشانید.

11.5.1 راه‌اندازی سرور تست با httptest

مطالعه موردی استراتژی تست در HashiCorp

HashiCorp (خالق Terraform، Consul، Vault) رویکرد سه‌لایه‌ای به تست دارد: unit test‌های سریع برای منطق داخلی، integration test‌ها برای تعامل بین کامپوننت‌ها، و end-to-end test‌ها برای سناریوهای واقعی کاربر.

نکته کلیدی: E2E test‌ها فقط در CI/CD اجرا می‌شوند و به‌صورت خودکار منابع مورد نیاز (container‌ها، شبکه) را ایجاد و پاک‌سازی می‌کنند.

این رویکرد مهم است چون E2E test‌ها کند هستند — ممکن است ده‌ها دقیقه طول بکشند — و منابع زیادی مصرف می‌کنند.

اجرای آن‌ها در هر commit توسعه‌دهنده عملی نیست، ولی اجرای خودکار آن‌ها در CI/CD قبل از هر merge تضمین می‌کند که هیچ تغییر تخریبی‌ای وارد main branch نشود.

یکی از تکنیک‌های مهم HashiCorp استفاده از Contract Tests است. هر پروژه رابط‌های خود را به‌صورت قرارداد تعریف می‌کند و Contract Tests بررسی می‌کنند که هر پیاده‌سازی هنوز با قرارداد سازگار است.

این روش مانع از آن می‌شود که تغییر در Terraform باعث شکست Vault شود بدون اینکه تیم‌ها مستقیماً با هم هماهنگ باشند.

نتیجه: HashiCorp توانست با وجود ده‌ها پروژه متن‌باز، release‌های هفتگی با اطمینان بالا ارائه دهد. درصد failure در production به‌دلیل تست‌های ناقص کمتر از ۰.۱٪ گزارش شده است.

این آمار در صنعت نرم‌افزار بسیار چشمگیر است و نشان‌دهنده‌ی این است که سرمایه‌گذاری روی زیرساخت تست، در بلندمدت هزینه‌های ناشی از قطعی و باگ‌های production را به‌شدت کاهش می‌دهد.

11.5.9 تست یکپارچگی مبتنی بر Docker

از چالش‌های اصلی تست‌های یکپارچگی، مدیریت وابستگی‌های خارجی مانند دیتابیس، message queue و cache است. در PHP معمولاً از SQLite in-memory استفاده می‌شود اما این روش محدودیت‌هایی دارد و رفتار دیتابیس واقعی را شبیه‌سازی نمی‌کند.

کتابخانه testcontainers-go این مشکل را حل می‌کند: برای هر تست، یک container Docker واقعی اجرا می‌شود و پس از پایان تست، به‌صورت خودکار حذف می‌شود.

نکته: Testcontainers نیاز به Docker runtime دارد. در CI باید مطمئن شوید Docker در دسترس است. همچنین از testing.Short() استفاده کنید تا بتوانید تست‌های یکپارچگی را با فلگ -short رد کنید: go test -short ./...

11.5.14 معماری تست E2E در Go

معماری تست E2E در Go بر پایه چند مؤلفه اصلی استوار است: کد تست، سرور واقعی روی پورت تصادفی، و دیتابیس واقعی (معمولاً در Docker Container). برخلاف Unit Test که فقط یک تابع را ایزوله تست می‌کند، E2E Test کل جریان برنامه را از دریافت درخواست HTTP تا بازگرداندن پاسخ با دیتابیس واقعی بررسی می‌کند.

این رویکرد شبیه‌ترین حالت به محیط Production است و باگ‌هایی را کشف می‌کند که در تست‌های ایزوله‌شده قابل شناسایی نیستند.

در Go ابزارهای قدرتمندی برای E2E testing وجود دارد: httptest.Server برای ساخت سرور واقعی درون پروسه تست، Testcontainers برای اجرای دیتابیس واقعی در Docker، و build tags برای جداسازی تست‌های E2E از تست‌های واحد.

این معماری تضمین می‌کند که تست‌ها سریع‌تر از محیط Production اجرا شوند اما دقیقاً همان رفتار را نشان دهند.

در Laravel این مفاهیم با Feature Test و RefreshDatabase پیاده‌سازی می‌شوند اما در Go کنترل بیشتری روی هر مؤلفه دارید.

11.5.15 سناریوهای عملیاتی تست E2E

در پروژه‌های واقعی، تست‌های E2E سناریوهایی را پوشش می‌دهند که با هیچ نوع تست دیگری قابل بررسی نیستند. هر سناریو زیر یک چالش عملیاتی رایج است که تیم‌های توسعه‌دهنده با آن مواجه می‌شوند.

این الگوها به‌طور خاص برای توسعه‌دهندگان مهاجر از PHP طراحی شده‌اند تا بتوانند معادل‌های صحیح الگوهای آشنای Laravel را در Go پیدا کنند و تست‌های E2E مؤثری بنویسند.

  • تست API Endpoint با دیتابیس واقعی: مهم‌ترین سناریوی E2E، تست API endpoint با دیتابیس واقعی است. برخلاف mock کردن دیتابیس در unit test، در E2E test یک container واقعی PostgreSQL اجرا می‌شود و درخواست‌های HTTP واقعی ارسال می‌شوند. این کار تضمین می‌کند که کوئری‌های SQL، migrationها و constraintها درست کار می‌کنند. در Laravel این معادل Feature Test با RefreshDatabase است.
  • تست جریان احراز هویت سرتاسری: جریان احراز هویت (ثبت‌نام → ورود → دسترسی به منبع محافظت‌شده → خروج) باید به‌صورت کامل E2E تست شود. با cookiejar.Jar یا JWT واقعی، می‌توانید کل جریان را شبیه‌سازی کنید. در Laravel این کار با $this->actingAs($user) انجام می‌شود اما در Go باید مراحل را صریحاً طی کنید.
  • تست آپلود و دانلود فایل: عملیات فایل نیازمند تست E2E هستند چون multipart/form-data و هدرهای Content-Type فقط در محیط HTTP واقعی به‌درستی کار می‌کنند. با ساخت درخواست multipart واقعی و ارسال به httptest.Server می‌توانید کل فرآیند آپلود، ذخیره و دانلود را تست کنید.
  • تست پردازش همزمان درخواست‌ها: وقتی چندین کاربر همزمان به یک منبع دسترسی دارند (مثل رزرو صندلی یا کاهش موجودی)، فقط تست E2E می‌تواند race condition و رفتار همزمان را کشف کند. با اجرای چند goroutine همزمان که درخواست‌های HTTP واقعی ارسال می‌کنند، می‌توانید رفتار سیستم تحت بار همزمان را تأیید کنید.
  • ادغام CI/CD با Testcontainers: در خط لوله CI/CD، تست‌های E2E با Testcontainers به‌صورت خودکار container دیتابیس را اجرا و پس از تست حذف می‌کنند. با فلگ -tags=e2e می‌توانید تست‌های E2E را فقط در زمان مناسب (مثلاً قبل از merge یا nightly) اجرا کنید و زمان CI را بهینه‌سازی نمایید.
نکته درباره Build Tags: از //go:build e2e برای جداسازی تست‌های E2E از تست‌های واحد استفاده کنید. تست‌های E2E کند هستند و نباید در هر commit اجرا شوند. دستور go test ./... فقط تست‌های واحد را اجرا می‌کند و go test -tags=e2e ./... تست‌های E2E را هم اضافه می‌کند. در CI/CD معمولاً unit testها در هر commit و E2E testها فقط قبل از merge یا به‌صورت nightly اجرا می‌شوند.
